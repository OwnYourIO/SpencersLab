# Permission model

Generated agents carry `permissions:` blocks in their frontmatter (authored in `.rulesync/subagents/`, emitted by `rulesync generate`). Rules are evaluated **in order, last match wins**, so broad rules come early and specific overrides after them. Rule shape: `{ action: "<tool>", resource: "<glob>", effect: allow|deny|ask }`.

- Actions are tool names. MCP tools are permissioned as `"<server>_<tool>"` with unsupported characters (like `-`) becoming `_` — so the pattern `readonly*` matches server `readonly-gpu-kubernetes`'s tools, and `admin*` matches both `admin-*` and `admin_*` spellings.
- Resources are path globs for file tools (`edit`, `read`) and command globs for `shell` (e.g. `git status *`). `**` crosses directory boundaries.
- `subagent` resources are target agent ids, matched **whole-value** — a rule without `*` matches exactly one id. Verified live on OpenCode v2.0.24 (2026-10-14) back when this repo still shipped `-bmad` overlay variants: a coordinator was denied the other variant's agents and allowed only its own four, and the `subagent` tool's "Available subagents" list shown to each coord contained exactly its 4 permitted same-variant agents. The naming scheme stays relevant for any overlay added later: variant names are prefix-free (overlays lead), so `agent-dev` is not a prefix of `agent-dev-bmad` — safe even if a build, saved approval, or hand-added wildcard rule ever behaves prefix-like.
- `ask` pauses for the user; unattended subagents treat it as effectively blocked, so allow-lists decide what runs hands-free.
- `execute` is the Code Mode action (resource `*`). Current builds route MCP tools and the `tools.opencode.*` namespace through Code Mode; the base `* * deny` silently removes it, hiding those tools no matter which MCP actions the agent allows ("nested tools enforce their rules" — V2 permissions doc). An agent that must reach an MCP server therefore needs `execute: * allow` IN ADDITION to its `<server>_<tool>` rule; execute grants nothing by itself — every call inside Code Mode re-checks the agent's allow-list.

## Hand-managed global policy arrays

The machine (`~/.config/opencode/opencode.json`) and project (`.opencode/opencode.jsonc`) `permissions` arrays live outside rulesync and apply to every agent BEFORE its own rules append. Last-match-wins makes their ORDER load-bearing; the shape is broad → blanket → exceptions:

1. **Universal default FIRST** — `{ action: "*", resource: "*", effect: "ask" }` (overrides the built-in base's `* * allow`). Placed at the END instead, it silently converts every allow above it into an ask. The failure is role-shaped: generated agents restate their own rules last and look healthy, while built-ins (`plan`, `build`, `general`) and hand-authored stage profiles without a matching rule prompt on everything they do — the classic symptom is "every new agent asks for skills" while the pipeline runs silently.
2. **Blanket allows next** — `read *`, `shell *`, `skill *`, `webfetch`, `websearch`, `codesearch`, per-`playwright_*`, `external_directory`…
3. **Exceptions LAST** — `read *.env` / `*.env.*` ask, then `read *.env.example` allow (if `read * allow` follows them, `.env` protection is a no-op); the `shell "*>*"` redirect guard AFTER `shell * allow` (before it, dead code).

After editing either array, re-derive the last match by hand for at least: a `skill <new-id>` load (allow), reading `.env` (ask), reading `.env.example` (allow), plain `git status` (allow), `echo x > f` (ask), and one unlisted action (ask).

### Context-file rules (dev)

Repo/agent context files get a per-file policy for the roles that edit the repo — dev (broad `edit * allow` with the trailing overrides below) and test (starts from `edit * deny`, so it gets only the two context **allow** rows plus the machinery asks):

| effect | resources | why |
|---|---|---|
| **allow** | `skills/**`, `.rulesync/rules/**`, `.rulesync/skills/**` | a chunk may legitimately update self-written skills or the repo-context rules (which generate `AGENTS.md`) — dev edits and reports it under `deviations` so the coordinator sees it |
| **ask** | `.rulesync/**`, `.opencode/opencode.jsonc`, `skills-lock.json`, `rulesync.jsonc` | agent machinery (subagent/command sources, repo MCP config — dev-cluster servers + gpu-ai provider, repo permissions, registry lock, generator config): explicit user approval per edit (unattended subagents treat `ask` as blocked). Order matters: the broad `.rulesync/**` ask comes BEFORE the two `.rulesync/{rules,skills}/**` allows, so those allows win for context sources while everything else under `.rulesync/` still asks |
| **deny** | `AGENTS.md`, `.opencode/agents/**`, `.opencode/commands/**`, `.opencode/skills/**` | generated surfaces — `rulesync generate` owns them; a hand-edit is silently overwritten on the next generate, so the change belongs in the `.rulesync/` source instead |
| **deny** | `.agents/**` (and `.kilo/**`, its symlink) | plans are coord/plan-owned; third-party skills in `.agents/skills/` are registry-managed — never hand-edited (self-written, in-repo skills live in top-level `skills/`) |

(`.kilo` is a symlink to `.agents`; both spellings are listed because matchers differ on symlink resolution. Order matters: these denies come last, after `edit * allow`, because last match wins.)

### MCP allow-lists

This repo's servers follow the `<priv>-<cluster>-<service>` naming (`readonly-*` / `admin-*` / `global-*`), so the agents use the prefix rules `admin* deny, readonly* allow, global* allow` — subagents never mutate cluster state; mutations are a user step. Tier-less servers match none of those prefixes, and unlisted servers fall through to `ask` (= blocked in unattended runs), so the dev-cluster utility fleet (`dev-playwright`, `dev-renovate`, `dev-searxng`, `dev-boards`) is granted by a `dev*` allow added AFTER the `admin*` deny (2026-10-24, ticket 2026-10-feat-dev-mcp-fleet): under last-match-wins the deny stays effective for admin tool ids because no `dev-*` server id starts with `admin` — MCP tool ids are `<config server name>_<tool-name>` with the server name verbatim, HYPHENS INCLUDED (opencode.ai MCP docs, "Glob patterns": `my-mcp*` matches `my-mcp_search`), so separator-free family prefixes like `dev*`/`readonly*`/`admin*`/`global*` match by leading segment under any reading while a per-server allow MUST reuse the server name's exact spelling — a `dev_boards*`-style underscore respelling matches nothing and dies silently behind a deny-all (the D21 misbelief, corrected 2026-10-27 by ticket 2026-10-bug-board-coord-dev-boards-allow) — and no tier-less `dev-*` name may shadow an `admin`-capable server; if the fleet ever gains one, put a specific deny after the `dev*` allow. A repo whose servers lack that naming needs explicit per-server allow-lists instead, with anything that can mutate systems the repo shouldn't touch denied.
Exception: the `board-coord` family — `board-coord` (the commit-only alias), `board-coord-local` and `board-coord-pr`, the first coord variants with any MCP access — gets an explicit allow for the `dev-boards` wekan-mcp server (`dev-boards*` — server-name spelling, corrected 2026-10-27 by ticket 2026-10-bug-board-coord-dev-boards-allow; D21's narrow scoping unchanged) and NOT the fleet-wide `dev*` the other agents carry; board ops are their intake and exit (card pickup, lifecycle, hand-back), not fleet tooling, so least privilege scopes it to the AI-Dev board and they get no `readonly*`/`admin*` rules either. The four `opencode_*` kickoff naming rows the whole coord family carries are a namespace transport, not an MCP server grant.

## Audit checklist (run after files move or servers are renamed)

1. Extract every resource: `grep -hE 'resource: "?[^ "]' .rulesync/subagents/agent-*.md | sort | uniq -c`.
2. For each path-shaped resource, confirm the target exists in the current layout (`ls`/`git ls-files` globs). Plans live per-ticket now: coord needs `.agents/plans/**/STATE.json` style, NOT root `.agents/plans/STATE.json` — with coord's leading `* * deny`, a stale root path silently locks coord out of its own state files.
3. For each MCP prefix rule, list live servers (the `mcp` keys across BOTH fleet locations — the regular fleet in the machine-local global config `~/.config/opencode/opencode.json` + the dev-cluster servers in `.opencode/opencode.jsonc`) and confirm the intended servers match a rule; anything unintended should hit deny or `ask`.
4. Confirm the dev context-file denies are present and ordered AFTER `edit * allow` (last match wins), and the `.rulesync/**` ask precedes the two `.rulesync/{rules,skills}/**` allows.
5. Confirm kick-off commands' state lookup matches the layout: `find .agents/plans -mindepth 2 -maxdepth 3 -name STATE.json` (month/ticket levels).
