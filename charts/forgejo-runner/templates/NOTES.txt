Forgejo Actions runner ({{ .Release.Name }})
============================================

Nothing to browse or port-forward — this is a client-only service. One
StatefulSet runs here; every pod is a privileged DinD sidecar + hardened
runner container dialing the Forgejo instance its release was pointed at
via runner.url (the dev release: in-cluster dev-forgejo-http, the infra
release: the public infra host). Jobs run in each pod's privileged DinD
sidecar; docker images are cached on the per-pod docker-data PVC so
re-runs don't re-pull.

Identity (D61): the release uses ONE shared runner token and every pod
registers itself with it on its first boot. An init container POSTs the
registration (name = that pod's own name, the release's full label set,
and never ephemeral — the v13 daemon refuses ephemeral records) to the
instance's runner-registration endpoint; the server answers with that
pod's own identity, which is persisted on the pod's data PVC. A restart
re-attaches from the PVC and never re-registers. So a 10-replica release
shows ten rows in Admin -> Actions -> Runners, each named after its pod,
all advertising the identical labels; scaling works by pod count, each
pod holding its own slot at capacity 1.

One-time user action (before any pod can register): mint a runner token
on the target Forgejo instance (Admin -> Actions -> Runners, instance
scope; the token is displayed once at creation and cannot be retrieved
later) and store it in this release's Bitwarden item's login PASSWORD
field. The login username field (the uuid of the old single shared
pair) is no longer read by the fetch. The ExternalSecret reads only the
login username and password fields; values in custom fields, notes, or
the URI are not read. That item's Bitwarden ID goes in
custom-values/dev/prod-values.yaml under
<app-key>.bitwardenIds.runner-token — the fetch is by item ID, not
item name, so a similarly-named item never syncs.
