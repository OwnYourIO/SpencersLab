# wekan-mcp tool call shapes — the full table

Tool → args → response shape for all 39 tools registered by
`containers/wekan-mcp/wekan_mcp/server.py`. Rows are anchored on the server's
**function names**, never line numbers — lines drift with every build, names
survive. One row per registered tool, one evidence stamp per row:

- `live probe 2026-10-27` — the tool was exercised read-only through
  `dev-boards` that day: `list_boards`, `get_board`, `list_swimlanes`,
  `list_lists`, `list_custom_fields`.
- `source-only` — the row reads the current source signature and docstring
  only; it was not exercised by that probe. Facts earlier runs observed live
  are noted inline with their date.
- `source-only 2026-11` — the cf-96 rows (dependency tools, `preload_board`,
  `set_card_labels`, and — since C11 — the re-stamped `list_rules`/`get_rule`
  projection) plus cf-106 C07's `get_card_details`: repo-source and
  upstream-v12.65 facts only, never probed — no
  pipeline session holds a bearer; the C10 deploy-chain user probe upgrades
  these stamps after the pin bump.

The deployed build can lag the repo source (observed 2026-10-26: the
`default_checked` parameter was rejected on a v4.1.3 deployment while the repo
implemented it). Re-check `tools/list` before trusting any optional
parameter; the direct-probe recipe is in
`skills/wekan-api/references/wekan-mcp-ops.md`.

## Read tools — registered by `mcp.tool`, present on every tier

| tool | required args | optional args | response shape and gotchas | evidence |
|---|---|---|---|---|
| `list_boards` | — | — | `[{id, title}]` — boards the service user is a member of; membership scopes every other call. | live probe 2026-10-27 |
| `get_board` | `board_id` | — | `{id, title, key, permission, color, archived, labels: [{id, name, color}]}` — the only read that carries the board's label list; `key` is the board key: 2-10 capitals, auto-assigned on insert, REST-immutable. | live probe 2026-10-27 · key source-only 2026-11 (deploy pending) |
| `list_lists` | `board_id` | — | `[{id, title, swimlane_id}]` — the `swimlane_id` is hydrated per list from the single-list route (WeKan's collection route projects lists to `{_id, title}` only, see `list_lists`); no sort field; titles repeat across swimlanes. | live probe 2026-10-27 |
| `list_swimlanes` | `board_id` | — | `[{id, title}]` — every board has at least one. | live probe 2026-10-27 |
| `list_cards_in_list` | `board_id`, `list_id` | — | cards in board order, top first; the by-list projection strips `card_number` (null), `custom_fields` and `label_ids` (empty) and — since cf-96 — `card_dependencies` (empty) and `parent_id` (null); `get_card` per candidate for those. Both ids are required together (observed live 2026-10-26). | source-only |
| `get_card` | `board_id`, `card_id` | — | the full slim card: only source of `card_number`, `custom_fields` `[{id, value}]`, `label_ids`, and — since cf-96 — `card_dependencies` (the raw stored `[{cardId, type, color, icon}]` entries on the source card) and `parent_id` (creation lineage). `board_id` is interface-consistency only — the route is `/api/cards/{card_id}` and WeKan enforces board access via the card's own board. Returns archived cards too; check `archived`. | source-only |
| `get_card_details` | `board_id`, `card_id` | — | the single-card preload the claim-time block is written from: `{id, card_number, title, description, list_id, swimlane_id, archived, sort, parent_id, label_ids, labels: {label id: name}, custom_fields: {field name: raw value}, slug_stack: [oldest … newest], current_slug, checklists: [{id, title, items: [{title, finished}]}], dependencies: [{to_id, type, color}]}` — EVERY checklist with its items in stored order (no kickoff-vocabulary filter, unlike `preload_board`, so a follow-up card's inherited answers are readable without touching the parent), label names from the board document and field names from the board's field list (the card document carries only ids; an orphaned field keeps its id as the key), edges from the card's own `cardDependencies` (`to_id` is the target card id, no icon), `slug_stack`/`current_slug` both from the single combined-value authority — the stack oldest first, the current slug its newest entry; archived cards come back FLAGGED, never dropped; a card that does not read as a card document RAISES (an empty payload would be indistinguishable from an empty card), and a checklist whose items route cannot be read RAISES the same way — the C06 fail-the-call ruling covers this sub-read, so an empty `items` list always means the checklist genuinely has no items. Block format home: the Card details block section of `SKILL.md`. | source-only 2026-11 (cf-106 C07; `/api/cards/{card_id}` + board + custom-fields + per-checklist routes as pinned by the `get_card`/`list_checklists`/`get_checklist` rows) |
| `list_comments` | `board_id`, `card_id` | — | `[{id, comment, author_id, created_at}]` — the body key is `comment`; live runs observed `created_at: null` (2026-10-26), so treat listing order as time order. | source-only |
| `list_checklists` | `board_id`, `card_id` | — | `[{id, title}]` only — card-scoped, so checklist ids cannot be pre-collected board-wide; item ids come from `get_checklist`. | source-only |
| `get_checklist` | `board_id`, `card_id`, `checklist_id` | — | `{id, title, items: [{id, title, finished}]}` — `finished` is the read-side name of the REST `isFinished` flag; the item ids are what `toggle_checklist_item` and `delete_checklist_item` require. | source-only |
| `list_rules` | `board_id` | — | `[{id, title, trigger, action, extra_actions, extra_triggers, enabled}]` — trigger and action embed inline; since cf-96 C11 the checklist extras and the enabled flag pass through as the routes return them; rule ids feed `get_rule`, `update_rule`, `remove_rule`. Key vocabulary and recipes: `skills/wekan-api/references/wekan-mcp-ops.md`. | source-only 2026-11 |
| `get_rule` | `board_id`, `rule_id` | — | one rule document, same shape as a `list_rules` item — full embedded trigger, action, checklist extras and enabled flag. | source-only 2026-11 |
| `list_custom_fields` | `board_id` | — | `[{id, name, type}]` — the name key is `name`, not `title` (the board-level list route projects to these three; verified on the deployed v9.99 API). | live probe 2026-10-27 |
| `get_custom_field` | `board_id`, `custom_field_id` | — | `{id, name, type, settings, show_on_card, automatically_on_card, always_on_card}` — dropdown options live in `settings.dropdownItems`; `always_on_card` is read-only through this server (see `create_custom_field`). | source-only |
| `list_board_members` | `board_id` | — | `{board_id, title, members: [{user_id, username, is_admin, is_active, is_no_comments, is_comment_only, is_worker, is_normal_assigned_only, is_comment_assigned_only, is_read_only, is_read_assigned_only}], username_resolution}` — nine normalized booleans (present⇒true, absent⇒false); `username` is always null because usernames ride only site-admin-gated REST routes, and the `username_resolution` note says so; ownership is the entry with `is_admin=true`; `grantedBy` provenance is omitted. | source-only (v12.65 source-check 2026-10-30; live tools/list probe post-merge, user-owned) |
| `list_board_dependencies` | `board_id` | — | the board's Red Strings lines in one call, passed through as the route answers: `[{from, fromTitle, fromCardNumber, to, toTitle, toCardNumber, type, color, icon}]` — each line is the stored spelling from its source card, the board view carries no synthesized inverse, so consumers match both `blocks` and `is-blocked-by` spellings (type-inverse, consumer-side); archived cards excluded server-side (the route filters). | source-only 2026-11 (upstream v12.65 source-check; user probe post-C10) |
| `list_card_dependencies` | `board_id`, `card_id` | — | the source card's stored entries, passed through: `[{cardId, type, color, icon}]` — `cardId` is the TARGET id (references key on ids, `card_number` is display-only); only this card's own edges — the inverse direction comes from the board-wide read. | source-only 2026-11 (upstream v12.65 source-check; user probe post-C10) |
| `preload_board` | `board_id`, `swimlane_titles` | `swimlane_titles=None` (every swimlane) | `{board_id, swimlanes: [{id, title, lists: [{id, title, cards: [...]}]}], dependencies: [{from_id, to_id, type, color, icon}], label_names: {id: name}, field_names: {id: name}}` — ONE GET of the board export (`attachments=false`, `fields=board-header,labels,custom-fields,dependencies,sort,checklists`); per-card dict EXACTLY `{id, card_number, label_ids, slug, archived, sort, parent_id, checklists}` with `checklists` = `[{id, title, items: [{title, finished}]}]`, filtered to the kickoff vocabulary (Services, Type, Model(s), Lifecycle, Human in the Loop, plus the legacy `Research` checklist and an 8-item legacy Lifecycle spelling) — checklist state rides the same request because the export streams `checklists`/`checklistItems` as top-level arrays, so there is no per-card fan-out and no `get_checklist` round-trip; no card titles, no descriptions; `slug` parsed by the single combined-value authority down to the NEWEST stack entry — the bracketed text of the LAST `[…](…)` line of the `[<slug>](<link>)` value (bare legacy value passes through); archived cards FLAGGED, never dropped (pickup filters consumer-side); linked cards excluded by the exporter's own selector; empty lists not emitted; unresolved parents surfaced at the tail under their own id (`title: null`) on the unfiltered read only — with `swimlane_titles` the answer is exactly the named swimlanes and an unmatched title yields `swimlanes: []`, never an error (a title miss is a data miss); a malformed, bodyless or `{}` export body and a 200-with-error body RAISE — the payload carries no degradation flag, so the empty grouping stays reserved to a genuinely empty board and the consumer's present-but-failed degrade branch can only fire on a call that actually failed. | source-only 2026-11 (upstream v12.65 exporter source-check — `models/lib/exportFields.js` section names plus `models/exporter.js` array streaming; user probe post-C10) |

## Write tools — registered by `_write_tool`, absent from the readonly tier

| tool | required args | optional args | response shape and gotchas | evidence |
|---|---|---|---|---|
| `create_card` | `board_id`, `list_id`, `swimlane_id`, `title` | `description`, `default_checked`, `parent_id` | `{id, title}`; with `default_checked` (checklist title → item titles to arrive checked) the response gains per-checklist `{checked, missing, failed}`. Board rules create the standard checklists asynchronously after the create response, so the tool bounded-polls for them; a malformed map is rejected before the card exists, but nothing rolls back a missed check — read the buckets instead of assuming. With `parent_id` (follow-up lineage) the create is followed by a PUT of `parentId` on the single-card route (the single-card POST ignores a body parentId); a lineage miss reports `parent_id_set: false` + `parent_id_error` and never rolls back; no typed edge is drawn for it (parentId-only). | source-only (cf-96 `parent_id` extension 2026-11) |
| `update_card` | `board_id`, `list_id`, `card_id` | `title`, `description`, `due_at`, `start_at`, `end_at` | `{updated, card_id, fields}` — an omitted argument stays unchanged; dates are ISO 8601 strings. `list_id` must be the card's current list or WeKan 404s (playbook: fresh `get_card`). Covers title/description/dates only — no label or custom-field parameters exist here. | source-only |
| `move_card` | `board_id`, `from_list_id`, `card_id`, `to_list_id` | `to_swimlane_id` | `{moved, card_id, to_list_id}` — `from_list_id` is where the card lives NOW (a stale one 404s "Card not found", observed 2026-10-26); there is no bare `swimlane_id` parameter. The card re-inserts at the TOP of the destination list — round-trip order effects: `skills/wekan-api/references/wekan-mcp-ops.md`. | source-only |
| `create_list` | `board_id`, `title` | `swimlane_id`, `position` | `{id, title, swimlane_id, sort, positioned, position_error}` — the create POST APPENDS (WeKan sets `sort` from the board-wide live-list count, so on multi-swimlane boards the new column is not necessarily last inside the swimlane); an omitted `swimlane_id` binds the board's default (first) swimlane and the read-back returns which one was bound; `position` (0-based from the left, among the board's live lists) is a second, non-atomic same-board move POST — a failed reposition reports `positioned: false` + `position_error` and leaves the appended list live, never fails the create; a failed read-back nulls the echoed `swimlane_id`/`sort`. | source-only (v12.64 source-check 2026-10-29; live `tools/list` probe post-merge, user-owned) |
| `add_comment` | `board_id`, `card_id`, `comment` | — | `{id, comment}` — the body argument is `comment`, not `text`; authored by the service user. | source-only |
| `add_checklist` | `board_id`, `card_id`, `title` | `items` (list of titles) | `{id, title, items_added}` — the manual way to add a checklist when the board rules did not (rules are never retroactive). | source-only |
| `add_checklist_item` | `board_id`, `card_id`, `checklist_id`, `title` | — | `{id, checklist_id, title}` — appends one UNCHECKED item (extend option sets on older cards; toggle it to check); WeKan 404s when the checklist does not belong to the card. | source-only |
| `toggle_checklist_item` | `board_id`, `card_id`, `checklist_id`, `item_id`, `done` | — | `{item_id, done}` — the boolean argument is `done`; the read-side `finished` is not an accepted input name. | source-only |
| `delete_checklist_item` | `board_id`, `card_id`, `checklist_id`, `item_id` | — | `{deleted, item_id}` — DESTRUCTIVE, no undo, bounded to one item; WeKan 404s when the item does not belong to that card/checklist. | source-only |
| `create_rule` | `board_id`, `title`, `trigger`, `action` | — | `{id, title}` — trigger/action are dicts; only the presence of their kind key is validated server-side (no whitelist), omitted matchers wildcard to any value, and execution order is unspecified. Do not author rules from this row — the vocabulary and proven recipes are owned by `skills/wekan-api/references/wekan-mcp-ops.md`. | source-only |
| `update_rule` | `board_id`, `rule_id` | `title`, `trigger`, `action` | `{updated, rule_id, fields}` — a supplied trigger or action REPLACES the stored document wholesale; include every field the rule must keep matching. | source-only |
| `remove_rule` | `board_id`, `rule_id` | — | `{removed, rule_id}` — DESTRUCTIVE, no undo; recreation only via `create_rule`. | source-only |
| `create_custom_field` | `board_id`, `name`, `type` | `settings`, `show_on_card`, `automatically_on_card`, `show_label_on_minicard`, `show_sum_at_top_of_list` | `{id}` — `type` is text/number/date/dropdown/checkbox/currency/stringtemplate; `settings` must be a JSON object (`{"dropdownItems": [...]}` for dropdowns), never the dumped-string form. Server-side, create ignores the always-on-card flag and does not backfill existing cards — `automatically_on_card=true` covers future cards, `set_card_custom_field` attaches existing ones. | source-only |
| `set_card_custom_field` | `board_id`, `card_id`, `custom_field_id`, `value` | — | `{card_id, custom_field_id, value, attached}` — upsert: the dedicated value route silently no-ops on an unattached field, so the tool attaches-if-missing with a whole-array write (documented read-modify-write race; both legs skip archived cards). `value` is stored verbatim — text/date as strings, dropdown as an option id; number/checkbox coercion is not expressible through this typed schema (raw REST via `/wekan-api`). The `slug` field's stack growth is consumer-side read-modify-write (read the current value, append the new line, upsert the whole) — this tool does no server-side append. | source-only |
| `update_board` | `board_id`, `title` | — | `{id, title, key, color, permission, archived, renamed}` — title-only rename via the dedicated title route (bare whole-board PUT is 405 upstream: never rebuild it from POST+DELETE); the board id and the cardNumber sequence survive by construction; gate `checkBoardAdmin` at v12.65 (plain member ⇒ 403, title unchanged; 404 board not found); a failed read-back nulls the echo fields without failing the rename. | source-only (v12.65 source-check 2026-10-30; live tools/list probe post-merge, user-owned) |
| `create_swimlane` | `board_id`, `title` | `sort` | `{id, title, sort}` — an explicit `sort` is honored (the key is gated on `sort is not None` so the legal `sort=0` survives), omitted appends at max(live sibling sort)+1; `sort` is read back from the single-swimlane route because the collection route projects it away; a POST answer without `_id` is a failure regardless of status. | source-only (v12.65 source-check 2026-10-30; live tools/list probe post-merge, user-owned) |
| `create_label` | `board_id`, `name` | `color` (default `green`) | `{label_id, name, color}` — (name, color) is the idempotency key: an existing pair returns its id, the same name with a different color creates a SECOND label (no rename-by-name); `color` must be one of the 25 named colors (white included) and hex is rejected client-side with the allowed list before any request; gate is board-admin-or-site-admin, and the handler's answer is the bare label-id string. | source-only (v12.65 source-check 2026-10-30; live tools/list probe post-merge, user-owned) |
| `add_card_dependency` | `board_id`, `card_id`, `target_card_id` | `type`, `color`, `icon` | `{id, target_card_id, type, color, icon}` — UPSERT keyed on (source card, target): a repeat add with new props UPDATES the edge, never duplicates it; same-board target only (400 otherwise); `type` is one of the 7 (`related-to`, `blocks`, `is-blocked-by`, `fixes`, `is-fixed-by`, `duplicates`, `is-duplicated-by`), gated client-side before the request like `create_label`'s colors; omitted props ride upstream defaults (related-to / #eb144c / link); the route's `dependsOn` body alias exists — the tool sends `cardId`. | source-only 2026-11 (upstream v12.65 source-check; user probe post-C10) |
| `edit_card_dependency` | `board_id`, `card_id`, `target_card_id` | `type`, `color`, `icon` (at least one) | `{updated, card_id, target_card_id, fields}` — re-types/re-styles an EXISTING edge (PUT target-scoped route); only supplied properties change; an empty change set is rejected client-side; same 7-type gate as `add_card_dependency`. | source-only 2026-11 (upstream v12.65 source-check; user probe post-C10) |
| `remove_card_dependency` | `board_id`, `card_id`, `target_card_id` | — | `{removed, card_id, target_card_id}` — DESTRUCTIVE, no undo: $pulls the single edge off the source card (neither card is touched); recreation is `add_card_dependency`; the third bounded destructive op, docstring-marked like `remove_rule`/`delete_checklist_item`. | source-only 2026-11 (upstream v12.65 source-check; user probe post-C10) |
| `set_card_labels` | `board_id`, `card_ids` | `add_label_ids`, `remove_label_ids` | `{applied, card_count, add_label_ids, remove_label_ids}` — the bulk labels route in ONE POST (retires the rules-engine label round-trip); an omitted list is a no-op, add-only/remove-only legal; ≤500 cards per call enforced client-side before sending; label ids checked against the board's own labels first (the route's board-membership gate stays the authority); the route answers an acknowledgement, not per-card results. | source-only 2026-11 (upstream v12.65 source-check; user probe post-C10) |

## Surface deliberately absent

`delete_board`, `delete_card`, `delete_list`, `remove_member`, attachments,
webhooks, imports/exports, member/user administration — by design (server.py
module docstring). Use raw REST through the `wekan-api` skill for those.
