# Error signatures — log line → meaning → first probe

Triage table for SeaweedFS log vocabulary: a grep-able literal, what the line actually means,
the one next action, and where the full procedure lives. Durable knowledge only — every
incident repair SEQUENCE has its single normative home in the dated runbook
`.agents/plans/2026-11-10-dep-seaweedfs-ec-removal.md` ("runbook Phase N" below), never
restated here. Meaning evidence: `RESEARCH.md` §R1/§R2 of
`.agents/plans/2026/2026-11-feat-seaweedfs-debug-skill/` (anchor cited per row).

Pin: behaviors verified at weed **4.50** (`ec8f97935`, the deployed build). Flag names and log
wording change between versions — re-check the running build (`help <cmd>`, see
weed-shell.md) after any bump before trusting a row (renovate carries 4.53.0 pending).

Loki surface in this lab: seaweedfs pods carry the stream label
`app_kubernetes_io_name="seaweedfs"` (no `app` label); `pod` rides structured metadata.
Rate fresh windows — a verification query THROUGH Loki that touches index objects stored on
SeaweedFS can regenerate the lines it measures.

| Signature (grep for this) | What it actually means | First probe / next action | Procedure lives |
|---|---|---|---|
| s3 `retry reading` loop: repeated 404 on one fid even with `readDeleted=true` | The needle is lost on ALL replicas of that volume — a data-plane loss, not a transient miss. The loop only persists while some filer entry still references the dead fid. | Map fid → object path via admin `/api/files/properties`. Entry gone → fast `NoSuchKey`, nothing to delete. Entry live → that object drives the loop. | runbook Phase 4 |
| `filer: no entry is found in filer store` | Two faces: (1) the filer entry genuinely does not exist — deleted or garbage, nothing to repair. (2) API misuse: a TRAILING SLASH on `/api/files/properties?path=…` returns exactly this text as a 500. | Strip the trailing slash / URL-encode the path and re-query; same answer twice = the entry is truly gone. | mcp-server-spec.md §3 (route rules); runbook Phase 4 uses both faces |
| `Failed to save/delete task state for ec_balance_…: invalid task ID` | EC balance task IDs embed `host:8080` and the state sanitizer (`^[A-Za-z0-9_.-]+$`) rejects colons — proposals can NEVER persist. Log-only churn (~8k lines/day); nothing is being lost. | None — confirm the lines are on the admin server and EC groups still exist. | runbook Phase 0 suppresses new proposals; Phases 1–2 kill the churn by removing the groups |
| `placed with relaxed placement constraints` and `EC Detection: stopping early after 10 consecutive placement failures` | EC 10+4 needs distinct servers per shard; 8 volume servers on ONE rack on one node make placement impossible — the admin detection loop thrashes forever. | Shard distribution per node: master `/dir/status` `EcShards` counts. | runbook Phase 0 (`WEED_MAINTENANCE_ERASURE_CODING_ENABLED=false`); placement math in collections-and-ec.md |
| `skip vacuuming: not enough copies for volume` | The auto-sweep refuses any volume holding fewer replicas than its placement expects — 8-byte/0-file husk volumes survive every sweep forever. | `volume.list` the named id: size ≈ 8 B and zero files = husk. | runbook Phase 3 step 3; §R1.3 |
| `skipping readonly volume %d on %s` | `volume.check.disk` refuses to touch read-only replicas; only the EXPERIMENTAL, uni-directional `-fixReadOnly` would, and it is unsafe on diverged pairs. Filer-side companions: `volume is read only` + `max retry attempts (10) reached` — deletion-queue entries drop out of the queue after 10 retries into the durable ledger; no Prometheus metric exists for this queue, the logs ARE the designed surface. | `volume.list -readonly` for the current mark set. | runbook Phase 3 step 1 (mark writable BEFORE check.disk); §R1.1/§R1.2/§R1.5 |
| `error writing JSON status /status 200: … connection reset by peer` | Benign kubelet-probe RST noise: probes close with the body unread, the server-side write fails after the 200 header. ~1.5–1.7k lines/h is STEADY STATE, not a health signal — do not alert. | None (pods are Ready and `/status` answers in tens of ms). HTTP clients must read bodies to completion — an early disconnect adds a line. | mcp-server-spec.md §3; §R2.4. No repair |
| `volume %d: idx references end=%d but .dat is %d bytes; marking readonly` | Load-time structural check caught an `.idx` referencing past the `.dat` end (a crashed batched write). Re-detected on EVERY restart while the pair is inconsistent — `volume.mark -writable` does not survive the next restart. | Grep the volume-server log since its last restart — this line distinguishes idx>dat re-detection from a persisted `.vif` mark. | runbook Phase 3 step 1 (probe U4); the real repair is stop-server `weed fix` — onprem flow in mcp-server-spec.md §5; §R1.2 |
| `summed delete_count=… exceeds file_count=…; skipping object count` | Admin-dashboard display-only quirk: EC tombstones are summed across shard holders while the live count is deduped by max — the volume is just excluded from the collection's object total. No EC-side action. | None — resolves by itself once the group is decoded. | runbook Phases 1–2; §R1.3 |
| `failed to stream logs/index` | A Loki querier is reading a corrupt/lost index object stored on SeaweedFS: the GET hangs, the querier times out and re-issues — looks like a respawned retry loop. | Pull the fid from the message, map fid → path via the properties API. One key recurring across a 7-day sweep = the live bad file; one-off hits = cancel noise. | runbook Phase 4 |
| `maybeReadHardLink` | INFO noise from filer hardlink resolution during library scans of `/buckets/media` (~38k/h on one filer observed). Not an error class. | None — ignore. | — |
| `not resurrecting %d needle(s) absent on %s` | The check.disk resurrection gate refused: the receiving replica's compaction revision is > 0 (it was vacuumed at some point), so an absent needle cannot be PROVEN a missing write rather than a vacuumed delete. Refusal by design — every vacuum hardens the divergence. | Re-read the simulate-pass verdict: it prints each replica's revision (the live-unknown probe U2). | runbook Phase 3 step 2 (fsck orphan-classification branch); §R1.1 |
| `TWO-SIDED (split-brain) divergence … Do NOT auto-repair` | CORRECT protective behavior, not a tool failure: both replicas hold unique live needles, so re-copying either direction can destroy the only copy of live data. | Classify each side's uniques: `volume.fsck -collection <pool> -volumeId <vid> -findMissingChunksInFiler` (hours; `-v` for progress). | runbook Phase 3 step 2 (all three verdict branches); §R1.1 |
| `ec decode volumes: []` with exit 0 | Silent no-op that LOOKS like success: the `-collection` pattern matched zero groups. Usual cause: the literal `default` against the unnamed pool — the admin UI display alias, which the shell matcher does not share. | Re-issue `ec.decode -collection="" -volumeId <vid>`. | runbook Phase 1; §R1.4; collections-and-ec.md |
| `need to run "lock" first to continue` | A mutation verb ran without the cluster-wide admin-shell lock held in the SAME piped session. Read-only verbs never require the lock. | Re-run the block wrapped `lock` / `<cmd>` / `unlock`; if `lock` blocks, someone else holds it (admin maintenance worker or a human shell). | weed-shell.md lock-first law; §R2.1 |
| `The specified key does not exist` / `NoSuchKey` on `load chunk` (Loki `parallel_chunk_fetch`) | The chunk object's filer entry is already gone — the read fails fast and stays failed: recorded data loss, not a live loop driver. Distinguish from the `failed to stream logs/index` row above (entry LIVE → deleting that object stops the hang). | Query the object path via the properties API — `no entry is found in filer store` confirms this face. | runbook Phase 4 (the already-gone casualty) |
| `corrupted mount` / `not a live mount` (consumers see ENOTCONN — `transport endpoint is not connected`) | A FUSE mount died when the SeaweedFS or host underneath it went down while the consumer pod kept running. The data may be perfectly intact — the mount must remount; warnings cluster on host-reboot timestamps and CSI sidecar restart counts track weed downtime. | Mount-pod restart counts + weed health underneath. | outside this runbook — the reboot-window precedent: `.agents/plans/2026-10-25-debug-seaweedfs-csi-vac-http.md` and the findings-note CSI/mount section |
| `collection default does not exist` (master `/collection/info?collection=default`) | The correct answer, not a fault: no collection literally named `default` exists. The cluster's main pool is the UNNAMED one and this endpoint cannot query it at all (empty param → `collection is required`). | Query a genuinely named pool (`collection=logs`) to compare. | collections-and-ec.md; mcp-server-spec.md §3; §R2.11 |

Reading a row: the probe column is the ONE next action, never a procedure. "Meaning" claims
trace to weed 4.50 source via the cited §R1.x/§R2.x sections of the ticket's `RESEARCH.md`;
`—` means there is nothing to repair.
