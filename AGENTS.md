# Comments and code quality

- Comments explain **why** (constraints, invariants, trade-offs, links to issues). Never restate what the code does, narrate history ("now we…", "updated to…"), or describe planned work.
- When writing or editing comments/docstrings, or before handing back a change, apply the `comment-slop` skill (rulesync-managed, vendored from `dashed/claude-marketplace` — see `.rulesync/skills/comment-slop/VENDORED.md`). It auto-selects when comment work is in scope.
- Before declaring a task done, run the `aislop` skill (`$aislop`; manual-only by design — it is hidden from auto-selection). Resolve every error and every fixable warning, or explain why a finding is a false positive.
- The `aislop-gate` plugin (`.opencode/plugin/aislop-gate/index.ts`, hand-written — NOT rulesync-generated) may append "aislop findings" to edit/write tool results. Treat them as review comments on your own diff and fix them in the same turn.
- CI runs `aislop ci --changes` on PRs (`.github/workflows/aislop.yaml`, gate config in `.aislop/config.yml`): every file a PR touches must clear the score floor and have no error-severity findings. A change that fails it is not done.
- The vendored skills are pinned: to update one, re-fetch at a new SHA, re-apply the aislop frontmatter patch (see its `VENDORED.md` note), diff, and bump the recorded SHA. `.rulesync/skills/.curated/` (rulesync fetch cache) stays out of git.

# AGENTS.md — SpencersLab

GitOps repo for the homelab: Helm charts (`charts/`), ArgoCD ApplicationSets
(`services/`), per-environment value overrides (`custom-values/`), custom
container images (`containers/`). **ArgoCD applies everything — never
`kubectl apply` from this repo.**

## Where things live

- `charts/<name>/` — Helm charts, all built on the bjw-s app-template library.
- `services/<category>/<env>/` — ApplicationSets + values per category
  (gpu, home, infra, media, monitoring, proxy-local, proxy-remote, …).
- `custom-values/<category>/` — private overrides (Bitwarden UUIDs) via `bitwardenIds`.
- `containers/<name>/` — custom images (Dockerfile + CI in `.github/workflows/`).
- `scripts/` — repo-machinery scripts launched by pipeline surfaces; `agent-board-coord-gate.sh` answers the session operand of the `/pipeline-boards-hourly` scheduled gate (see Agents).
- `.agents/agents/` — agent definitions; a symlink to `.opencode/agents/`
  (generated by rulesync from `.rulesync/subagents/` — see below). `.agents/plans/` — plan documents named
  `yyyy-mm-dd-<type>-<short-desc>.md` (date prefix, **never** a unix epoch;
  `<type>` = `feat`|`bug`|`debug`|`dep`|… so the goal is visible at a glance),
  plus per-feature pipeline folders `<yyyy>/<yyyy-mm>-<type>-<slug>/` used by
  the `agent-*` pipeline (see below). Folders created before 2026-10-17 keep
  the legacy `yyyy-mm/<feature-slug>/` layout until migrated per-ticket.
  **One plan per piece of work**: plans are always dated files
  (`yyyy-mm-dd-<type>-<slug>.md`) — at the plans root for standalone work,
  inside the ticket folder (as its plan of record) for pipeline work. Never
  two plan files for the same work, and no other plan-file names. The single
  sanctioned exception is a fusion plan `<plan-file>-fusion.md`, which
  `agent-fuser` writes into a ticket folder when parallel runs of the same
  ticket get fused.
- `.agents/plans/templates/` — blank boilerplate (the plan boilerplate
  `PLAN.md`, copied into tickets renamed as the dated plan file;
  `STATE.json`,
  `DECISIONS.md`, `FRICTION.md`, `chunks/`) that `agent-plan` copies into
  each new feature folder. `RESEARCH.md` has no template — `agent-research`
  writes it on demand, next to the plan file.
- `.agents/commands/` — slash commands for the pipeline (`/pipeline`,
  `/pipeline-resume`); a symlink to `.opencode/commands/`, which rulesync
  generates from `.rulesync/commands/`.
- `skills/` — self-written skills (`helm-chart-creation`, `container-creation`,
  `llama-swap`). `.agents/skills/` — third-party skills, tracked in git and
  synced from their GitHub sources (provenance + integrity hashes in the root
  `skills-lock.json`); don't hand-edit those.
- `.kilo` — tracked symlink to `.agents/`, so kilo loads the same agents,
  plans, and skills.
- `.opencode/` — tracked dir holding the **generated** surfaces: `agents/`,
  `commands/`, `skills/` (rulesync output — never hand-edit; `.agents/agents`
  and `.agents/commands` symlink into the first two) plus hand-managed
  `plugin/` (`aislop-gate` quality gate on edits; `question-notify` pushes a
  Home Assistant notification to the user's phone whenever an `agent-*`
  session asks a question) and `opencode.jsonc` (dev half of the agent tool
  config — see below).
- `.rulesync/` — the single source of truth for AI-tool config: `rules/`
  (→ this `AGENTS.md`), `subagents/` (→ `.opencode/agents/`), `commands/`
  (→ `.opencode/commands/`), `skills/` (→ `.opencode/skills/`: the
  `agents-sync` pipeline skill, the hidden `pipeline-*` contract skills the
  agents compose via `/skill` loads, plus the vendored, SHA-pinned
  `comment-slop` and `aislop` quality-gate skills). Edit here, then `rulesync generate`
  (targets/features per `rulesync.jsonc`); `rulesync generate --check`
  verifies the committed output is current. Commit sources and generated
  files together — generated files are tracked so a fresh clone/worktree
  works without running rulesync first. Third-party skills stay in
  `.agents/skills/` (discovered via the `skills` paths in `opencode.jsonc`)
  — rulesync does not own them.
- `.opencode/opencode.jsonc` — version-controlled OpenCode project config,
  the "dev" half of the agent tool config: the dev-cluster MCP servers
  (`mcp.dev.scifi.farm`), the gpu-ai provider (this repo's llama endpoint,
  `llama.spencerslab.com` — its model catalog churns with this repo's
  llama-swap work), permissions, skills paths and the default agent.
  Merged over the machine-global config (project entries win; non-conflicting
  global settings are preserved), so this repo sees the regular fleet too.
- `~/.config/opencode/opencode.json` — machine-local global OpenCode config,
  NOT version-controlled: the regular MCP fleet (visible to every project on
  this machine), the gpu-moe provider, agents and global permissions. Both
  providers' model catalogs set per-model `limit.context`, fixing OpenCode's
  200k fallback for uncataloged models. Regular-fleet/gpu-moe changes are
  machine-local edits — record them in this file's table in the same change.
  `~/.config/kilo/kilo.jsonc` is a separate machine-local file with an older
  fleet copy.
- `.aislop/` — quality-gate config (`.aislop/config.yml`) consumed by
  `aislop ci` in CI and by local scans; `.opencode/plugin/aislop-gate/` is a
  hand-written OpenCode plugin (never rulesync-generated). Both enforce the
  "Comments and code quality" rule above.
- `.agents/notes/` — free-form repo notes (SpencersLab-specific extra).

## Agents

- `planner` (`.agents/agents/planner.md`) — writes implementation-ready
  plans to `.agents/plans/`. Use before any non-trivial change. (Named
  `planner`, not `plan`, to stay clear of the built-in plan mode.) Its
  contract makes a `## Commands` validation section mandatory in every plan,
  records verified facts with evidence, and recommends the pipeline over
  mega-plans; read-only git — no commits.
- `code` (`.agents/agents/code.md`) — executes plans. Runs in fresh sessions:
  the plan file tells it which skills and MCP servers to load. Explicitly no
  pipeline context: a ticket folder or chunk id is redirected to the `dev`
  family.
- `dev` family (`.agents/agents/dev.md`, `dev-local.md`, `dev-pr.md`) —
  standalone one-session-sized implementers carrying the pipeline's
  discipline: `dev-local` commits, never pushes; `dev-pr` additionally
  pushes the branch for remote build/test under `pipeline-push-pr`; plain
  `dev` is a commit-only alias of `dev-local` — an edit to one lands on both
  in the same commit. Handed a ticket folder + chunk id they run pipeline
  work; the `role-dev` skill is their contract.
- `ask` (`.agents/agents/ask.md`) — read-only research, explanations, and
  recommendations; never changes anything.
- `debug` (`.agents/agents/debug.md`) — systematic diagnosis and minimal
  targeted fixes; role contract rewritten with the agent-* guidance (method,
  repo validation, quality gate, git hygiene — add/commit at `ask`, push
  denied — scope tripwire, RESULT-shaped reporting).
- `review` (`.agents/agents/review.md`) — advisory code review; never edits.
- `0-pipeline` + stages `1-`…`7b-` (`.agents/agents/0-pipeline.md` …
  `.agents/agents/7b-docs-dev.md`) — gated 7-stage SDLC pipeline for large
  features. Start at `0-pipeline`.
- `agent-*` (`.agents/agents/agent-{coord,plan,research,test,dev-pr,dev-local,review,fuser,board-coord}.md`;
  the implementer ships as `agent-dev-local`/`agent-dev-pr` — local commits only,
  pr additionally pushes the ticket branch; coords launch their matching dev) —
  chunk-based pipeline: `agent-coord` (primary) runs an approved plan through
  fresh `agent-plan`/`agent-test`/`agent-dev`/`agent-review` subagents (plus
  `agent-research` on demand), one chunk at a time, with files as the only
  shared memory; when all chunks are done it runs a final whole-plan review
  before marking the plan complete, then offers to plan fixes for the open
  friction items. `agent-fuser` (user-launched, on demand) compares parallel
  runs of the same ticket across branches and writes a user-confirmed fusion
  plan back into the chosen base branch for that session to execute.
  `agent-board-coord` — board-driven variant of `agent-coord` (manual launches run ungated via `/pipeline-boards`; the hourly scheduled launch runs the gated `/pipeline-boards-hourly`): pulls work from
  the WeKan AI-Dev board via the `dev-boards` MCP server, takes its intake from
  the card's standard checklists plus the `slug`/`session` custom fields
  instead of the live kickoff questions, and defers user questions to a single
  batched plan-question round; launch with `/pipeline-boards`. Artifacts
  live in `.agents/plans/<yyyy>/<yyyy-mm>-<type>-<slug>/`. Launch with the
  `/pipeline` commands.

## Feature pipeline (agent-*)

A chunk-based pipeline for multi-step work, complementary to the standalone
`planner`/`code` agents (single-shot planning/implementation) and the
`0-pipeline` SDLC stages (large features with docs). `agent-coord` runs an
approved plan chunk by chunk through fresh `agent-plan`/`agent-test`/
`agent-dev`/`agent-review` subagents; files are the only shared memory.
Launch with `/pipeline` (plan if needed, then run) or `/pipeline-resume`
(feature folder as argument).

Each feature lives in `.agents/plans/<yyyy>/<yyyy-mm>-<type>-<slug>/`
(the dated plan file, `STATE.json`, `DECISIONS.md`, `FRICTION.md`, `chunks/`
— boilerplate copied from `.agents/plans/templates/` — plus `RESEARCH.md`
when the coordinator commissioned deep research). The operational
contract — plan-folder layout, read order, the RESULT handoff schema, the
role processes, kickoff, model routing, gates — lives in the hidden
`pipeline-*` skills (`pipeline-conventions` + one `pipeline-role-<role>`
per agent, plus `pipeline-kickoff`/`pipeline-models`/`pipeline-gates` for
the coordinator) that every pipeline agent MUST-loads at run start; the
agent files themselves are thin frontmatter + skill-call skeletons. The
role × permission matrix is in the `agents-sync` skill references
(`permissions.md`). Edit those, not this summary.

### Pipeline specifics in this repo

- There is no unit-test suite. For the pipeline, "Commands" and "tests" mean
  validation: `helm lint charts/<name>` and `helm template charts/<name>`,
  grep checks for the service trio (chart entry + ApplicationSet values entry
  + proxy values entry), and every `OVERRIDE_VIA_CUSTOM_VALUES` placeholder
  matched 1:1 by a `custom-values/` entry. `agent-plan` records these in
  the plan file's "Commands"; `agent-test` writes every chunk's test files
  in one session after planning (before any dev), `agent-dev` runs them
  while implementing and `agent-review` re-runs them as the first step of
  every review; `agent-coord` gates a chunk done only when they pass. A test
  judged faulty is never fixed by the reviewer — coord asks the user and
  routes the fix back to the test session.
- Deep research is commissioned, never ad hoc: any agent that needs it
  reports the need via RESULT, `agent-coord` launches `agent-research`
  (storm skill + `global-searxng`), and the summary lands in the feature
  folder as `RESEARCH.md` (next to the plan file — the coordinator passes
  the folder's absolute path in the launch) for every later agent to read.
- Parallel runs of one ticket can be fused: `agent-fuser` compares the runs
  (planning quality, branch code diffs, research findings, friction), the
  user confirms the base branch and every conflicted sourcing choice (always
  with a follow-up confirmation — a single answer is never trusted), and the
  fuser writes `FUSION-REPORT.md` plus `<plan-file>-fusion.md` into the base
  branch's ticket folder and hands the confirmed plan back to that branch's
  pipeline session (its `coord_session` in `STATE.json`) for execution.
- `agent-board-coord` is the board-driven variant: card intake from the WeKan
  AI-Dev board replaces the live kickoff — pickup walks
  `Rework → Not Started → Low Priority` (top card first), the
  Services/Type/Model(s)/Research checklists plus the `slug` and `session`
  custom fields supply the kickoff answers, the Model(s) checklist alone
  routes models, `cf-<card-number>-<type>-<desc>` slugs name the feature
  folder, worktree, branch and session alike;
  card-driven runs carry no run tag (`agent-coord` keeps run tags);
  `Research`-labeled cards run the iterative research-only loop and end at
  Review — see the `boards` skill.
- All Hard rules below (no hand-bumped versions, ExternalSecret+Bitwarden
  secrets, ArgoCD — never kubectl apply, git safety, MCP privilege tiers)
  apply to every pipeline agent unchanged.

The agent files themselves are repo-agnostic on purpose (they work the same
in HomeAssistant/CuratedForest); repo grounding lives in this file, which is
loaded into every session automatically.

## MCP servers

Servers are split across two places. The regular fleet lives in the
machine-local global config (`~/.config/opencode/opencode.json`, NOT
version-controlled) — visible to every project. The 6 dev-cluster servers
(`mcp.dev.scifi.farm`) are project-local in `.opencode/opencode.jsonc`
(version-controlled); this repo sees the full fleet because project config
merges over global. Dev-cluster server changes flow through this repo's
normal branch→merge flow; regular-fleet changes are machine-local edits —
record them in this repo's AGENTS.md table in the same change.
`~/.config/kilo/kilo.jsonc` keeps its own older fleet copy, unmanaged — don't
expect it to match.

Servers are named `<priv>-<cluster>-<service>` in the client config
(e.g. `readonly-gpu-kubernetes`, `readonly-home-postgres-immich`); servers
without a privilege tier are just `<cluster>-<service>` (e.g.
`global-searxng`). `<cluster>` is one of gpu, ai-gpu, dev, grow, home, infra,
media, monitoring, proxy-local, proxy-backup — or `global` for shared utility
servers (wekan, grafana, searxng, playwright, renovate, homeassistant). `<priv>`
is `readonly` (inspection) or `admin` (mutations: restart/scale/patch/delete).
Kubernetes, Home Assistant, Grafana, and WeKan come in both tiers
(HA/Grafana/WeKan enforced server-side: ha-mcp `READ_ONLY_MODE`,
mcp-grafana `--disable-write` + token roles, wekan-mcp
`WEKAN_MCP_READ_ONLY`). Postgres servers are read-only by design.
**No tier grants pod exec** — if a task needs commands run inside a pod,
present the exact command (e.g. `kubectl exec -n <ns> <pod> -- <cmd>`) to the
user and let them run it.

**Agent privilege rules:** planning agents (plan, dependency-map, and the
read-only pipeline stages) may use `readonly-*` servers only — never
`admin-*`. The code agent may use `readonly-*` freely but must ask the
user for explicit confirmation before using any `admin-*` server.

| Server | Use when |
|---|---|
| `readonly-<cluster>-kubernetes` | Nearly always — inspect cluster state, ApplicationSets, pod logs, events |
| `admin-<cluster>-kubernetes` | Only when cluster mutations are required |
| `readonly-<cluster>-postgres-<db>` | Querying a cluster's Postgres DB |
| `global-searxng` | Web search: docs, chart research, image versions |
| `global-playwright` | JS-heavy doc sites, UI verification |
| `global-renovate` | Renovate dry-runs and config validation against this repo |
| `readonly-global-grafana` / `admin-global-grafana` | Grafana dashboards/datasources/alerting (admin needs the admin SA token) |
| `readonly-global-homeassistant` | Only for Home Assistant work (`charts/home-assistant`, zigbee2mqtt, music-assistant, or the live HA instance) — inspection |
| `admin-global-homeassistant` | Home Assistant changes (automations, entities, service calls) |
| `readonly-global-wekan` / `admin-global-wekan` | WeKan boards/cards — readonly for inspection, admin for card mutations |
| `dev-<service>` (playwright, renovate, searxng, boards) | Dev-cluster utility MCPs over the public ingress `mcp.dev.scifi.farm/<name>/mcp`; tier-less, allowed to pipeline agents via a `dev*` allow rule |

**Keep these lists current:** when a task uses a skill or MCP server not listed
above, add a line to this file (or the relevant agent file) as part of your
change.

## Hard rules

- **Never hand-edit generated surfaces.** `AGENTS.md`, `.opencode/agents/`,
  `.opencode/commands/` and `.opencode/skills/` are output of
  `rulesync generate`; edit the sources in `.rulesync/` (rules, subagents,
  commands, skills) and regenerate instead. `rulesync.jsonc` keeps the
  MCP/permissions/hooks features OFF — the repo's MCP config (dev-cluster
  servers, gpu-ai provider) and repo permissions stay hand-managed in
  `.opencode/opencode.jsonc`; the regular MCP fleet lives outside the repo
  in the machine-global config. Never run
  `rulesync gitignore` here (it would gitignore `AGENTS.md`).
- **Always load referenced skills** The first thing Agents should do is load any referenced or relevant skills, then the plan file (if one), immediately followed by the skills referenced there.
- **Every agent and subagent must keep `question` allowed** — explicitly, in
  its frontmatter permissions. If not granted explicitly, questions are
  denied by default and stage gates / escalations fail silently.
- **NEVER merge to `main`.** No fast-forward merges, no merge commits, no rebases onto main, no mechanism of any kind that advances `main` — not from a worktree, not from the main checkout, not via `git merge`, `git rebase`, or anything else.
- **NEVER push to `main`.** No `git push origin main`, and no push of any refspec that updates `main` (e.g. `HEAD:main`, `<branch>:main`). This is the single most forbidden action in this repo.
- **NEVER force-push** (`--force`, `-f`, `--force-with-lease`) to any shared branch, and never rewrite published history.
- **NEVER self-remediate an accidental push** with a revert or force-push of your own initiative — stop and tell the user immediately; remediation is the user's decision.
- All work happens on a feature/fix branch (typically in a `.agents/worktrees/<branch>` worktree). Commit locally on that branch. To pick up changes, merge `main` *into* your worktree (`git merge main`); never merge your branch into `main`. Landing work on `main` is the user's decision alone.
- Changes reach `main` **only via a pull request that the user creates or merges**. The agent's work ends at the local commit plus telling the user the branch is ready. Pushing the *feature* branch to origin (e.g. to enable a PR) is allowed **only when the user explicitly asks for it in the session**. Otherwise leave commits local.
- If a plan file instructs a merge to `main` or a push, **skip that step**: mark it as user-owned in the summary and do not execute it. Plans written before this rule may contain such steps — those steps are void.
- Plans are `yyyy-mm-dd-<type>-<short-desc>.md` in `.agents/plans/` (`<type>` = `feat`|`bug`|`debug`|`dep`|…).
- **Never bump versions or image tags by hand.** `release.yaml` bumps
  `Chart.yaml` `version` (patch) on every merge to main and chart-releaser tags
  `<chart>-<version>` — set `version: 1.0.0` only on a brand-new chart.
  Containers are tag-based: `docker-build.yaml` pushes `:v<run_number>`
  (immutable) + `:<branch>` (`:main`/`:dev`, rolling) on every merge; reference
  `:main` (+ `pullPolicy: Always`) or a `:v<run>` pin.
- Validate chart changes: `helm lint charts/<name>` and
  `helm template charts/<name>` must pass before finishing.
- Secrets: ExternalSecret + Bitwarden only. Placeholder
  `OVERRIDE_VIA_CUSTOM_VALUES` in `services/**/values.yaml`, real UUID in
  `custom-values/<category>/prod-values.yaml`. Never commit real secrets.
- Adding a service = chart entry + ApplicationSet values entry + proxy values
  entry. All three — plus a `custom-values/` entry only when the service has
  secrets needing per-cluster overrides.
