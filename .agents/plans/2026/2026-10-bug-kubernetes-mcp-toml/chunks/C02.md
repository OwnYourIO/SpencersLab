## Goal

`ghcr.io/containers/kubernetes-mcp-server` while keeping semver tag bumps on
the TOML side flowing. Independent of C01 (no shared files).

Semantics (focus 2) — proven empirically with node-semver 7 (Renovate's
docker versioning delegates range evaluation to it, v-prefix handled on both
the comparator and tag side):
- `>= v0.0.68` parses as a valid range; rejects `0.0.65`/`0.0.67` (flag era),
  accepts `0.0.68`, `0.0.69` (current pin — so updates are NOT suppressed: the
  range contains today's version and the live tag set), `v0.0.70`, `v0.0.100`
  (numeric, not lexicographic, patch order).
- Effect for a pinned-tag dep: every candidate bump Renovate may propose is
  filtered through the range — jumps INTO the flag era (from any future re-pin
  or rollback scenario) are impossible; semver bumps on the TOML side keep
  flowing, exactly D3's intent. Prerelease tags are excluded by node-semver
  defaults — benign for this package's plain-tag scheme.
- **Residual risk, plainly:** the floor bounds BELOW only. `0.1.0`, `1.0.0`, or
  a future TOML-again-changing 0.0.x all satisfy the range, so the floor cannot
  stop a crossing of an UNKNOWN future boundary — the same incident class could
  recur from above. What covers it: no automerge applies to this package (MCP-
  proven above), so any such bump arrives as a PR that needs a human merge, and
  the C01 t7 sweep binds the repo-side contract if one lands. This is exactly
  the posture the user approved ("keep semver, ignore the known-breaking range",
  digest pinning declined) — recorded, not a defect.
- D3's rejected alternatives all still hold on this evidence: `ignoreDeps`
  violates "keep semver bumps flowing" (kills all proposals); `pin:ignore`
  governs pin-type PRs only (this dep's PR is patch-type — exercised above);
  excluding only v0.0.68 leaves flag-era 0.0.66/67 proposable; regex floor
  fragile across tag formats while the semver range empirically handles the
  v-prefix. Nothing found weakens any rejection.
