## TL;DR

**RQ1: PASS — the VSCODE_PROXY_URI-derived `!`-block is reliable on both coders.** Both deployments run the *identical* build (v2.35.2+5c2838a), the env var is coderd-generated per workspace by source, and coderd provably accepts the derived agent-labelled named-app host on BOTH (303 auth-redirect, agent segment dropped, `?session=` preserved). **RQ2: NO — OpenChamber has no instance-level public address**; its "public address" is each browser's `window.location.origin`, sent per integration event — nothing headless or `!`-block can read is better than the env. **RQ3: named-app host wins outright** — a slug in the `{PORT/APP_SLUG}` slot is the native grammar (agent label optional-and-discarded for slugs), while port hosts need an active port-forward and do not even resolve in the gpu DNS view. **Material contradiction found: the shipped D20 literal is malformed** — dev coderd answers it **400** (single-dash `dev-thehackmeister`); the real host is the double-dash form, so every historical board link with the literal is broken, and the dynamic mechanism is the correct fix.

## Verdict (the question the launch asked)

**The planner's best guess survives research and is RETAINED as the mechanism** — a `Session origin:` `!`-block expanding `$VSCODE_PROXY_URI` with `{{port}}` → `openchamber` (lowercased) — with three refinements:

1. **Reliability by construction, not by coincidence**: the env value is built by coderd itself (`AppSlugOrPort:"{{port}}"` + agent + workspace + owner substituted into the deployment's wildcard) [S1][S2] — same code on both coders (same build) [S5][S6]. A run on ANY Coder deployment emits its own origin; no label-order assumption survives in the mechanism.
2. **The agent label (`--main--`) that the substitution carries is provably inert for named apps** — `ParseSubdomainAppURL` parses it and then drops it for non-numeric slugs [S3]; live 303-normalization confirmed on gpu AND dev this pass [S12]. The block does NOT need to strip it (and shouldn't — stripping would re-introduce label assumptions into the sed).
3. **The fallback the plan documented (port-label base from the run-state port) is the weakest alternative, not a peer** — see RQ3; prefer UNRESOLVED fail-closed over the port-label fallback if the named derivation ever fails.

**Claim 1 — the env var exists on every agent, on both coders, with the deployment's own host tail.** coderd builds the agent manifest with `ApplicationURL{AppSlugOrPort: "{{port}}", AgentName: agent.Name, WorkspaceName: workspace.Name, Username: owner}` and `vscodeProxyURI = accessURL.Scheme + "://" + ReplaceAll(appHost, "*", app.String())` — empty ONLY if the deployment has no wildcard app hostname, which both lab coders do [S1]. The agent binary then injects it into shell/env contexts (`envs["VSCODE_PROXY_URI"] = manifest.VSCodePortProxyURI`) [S2]. This is the *only* cross-coder behaviour that had to be proven; it is proven by the shared build, not by inspection of two deployments.

**Claim 3 — humans land on the working OpenChamber.** Following the chain unauthenticated: app host → 303 `…/api/v2/applications/auth-redirect?redirect_uri=…` → 303 `/login?message=…&redirect=…` (a real, clickable login page) → after OIDC the app-token is minted for the host and the browser returns to `redirect_uri` with the query intact [S12]. `share=owner` [S19] means only the workspace owner's browser session passes — the intended audience (the single human on the board) — same posture the intake recorded ("exact 200 un-fetch-verifiable", but auth-redirect proves routing + login landing, which is all a board click needs).

**Per-run-instance behaviour (launch's requirement).** agent-board-coord runs today on gpu (this env), historically on dev. Because the origin is *read from the running workspace's own env*, both legs emit their own deployment's origin: gpu runs → `…-coder.spencerslab.com`; dev runs → `…-coder.dev.scifi.farm`. There is no cross-contamination path: the old literal pointed every run at dev regardless of where it ran — exactly the defect the user demanded fixed. Parity of the dev leg is additionally supported (not merely assumed) by: same build [S6], same wildcard scheme [S8], dev app-host probes above, and the fact the dev coder's DNS view is a true wildcard (`zz-test.dev.scifi.farm` resolves; `1234--main--dev--thehackmeister-coder.dev.scifi.farm` resolves) [S12].
**Residual for the dev leg (be honest):** no dev-coder workspace shell was inspected from here, so the literal string of a dev workspace's `VSCODE_PROXY_URI` is inferred from [S1] applied to that coder's DB values (`main`/`dev`/`thehackmeister`). The dev 303 probes used that inferred target name and coderd answered it as a valid, normalizing app host. C03's live control (a) run from a dev-coder launch closes the last inch.

## RQ2 — Does OpenChamber expose its public address? No.

The intake §10 line ("integrations post session links when the instance has a public address") sounds like an instance setting. Reading the pinned bundle (`@openchamber/web@2.1.0`, the exact version the workspace templates install [S19-tfvars]) and the current main docs:

- **The origin is per-event, client-reported.** The browser UI POSTs `{kind, sessionId, issueIdentifier, sessionOrigin}` to `/api/linear/session-status`; `sessionOrigin` = `window.location.origin` in the web runtime (desktop/remote runtimes may supply a configured URL — not applicable to the Coder-served web UI) [S15][S17]. The server *validates* (`readSessionOrigin`: http(s), no path/query/credentials; `isPublicSessionOrigin`: rejects loopback, private/CGNAT IPs, `.local/.lan/.internal` suffixes, single-label hosts — with an explicit comment that private addresses "reach nobody else") [S15][S16] and **skips** as `origin-not-public` otherwise [S16]. There is no stored "instance public address" setting anywhere: the settings.json/env surface covers Linear client ids, broker URL, chats dir, UI password — no URL field [S14][S16].
- **The persisted copy is a non-starter as a source.** `~/.config/openchamber/linear-session-status.json` stores the last sessionOrigin per session [S15][S16] — but only after (a) a Linear workspace is connected, (b) session-comments opted in, (c) a session linked to a Linear issue *posted from a browser*. This lab's tracker is WeKan, not Linear; the file is integration state that may not exist and, when it does, records a **historical browser origin** — precisely the "remembered/historical host" that this ticket's D20(r2) forbids re-using. Rejected; a `!`-block COULD cat it but must not.
- **`connect-url` / tunnels don't help.** `openchamber connect-url --json` resolves a *server* URL from the bind host / LAN detection / loopback fallback — with the template's `--host 127.0.0.1` bind it yields loopback or a LAN IP, never the coderd app origin [S17]; Coder's app proxy, not OpenChamber, is the public layer (template comment: "Loopback only, no UI password: Coder's app proxy handles auth") [S19].
- **Bonus mutual confirmation:** OpenChamber's own integration link is exactly `${origin}/?session=<sessionId>` [S15][S16], and its PWA shortcuts/notification deep links use the same `/?session=` relative route [S17]. The flow's pinned link shape IS OpenChamber's native contract — no drift risk there.

**Verdict: VSCODE_PROXY_URI derivation remains the primary and only sound `!`-block source.** (Nothing OpenChamber-side is *more* reliable; nothing is reachable headlessly at all.)

## RQ3 — Port-label vs named-host proxy posture

- **Grammar (source, v2.35.2)** [S3]: `{PORT/APP_SLUG}[--{AGENT_NAME}]--{WORKSPACE_NAME}--{USERNAME}`. The first slot is *one* slot typed by `PortRegex ^\d{4,5}s?$`; **a slug in the "port" slot is the native named-app form, not an error**. Agent label: **required for ports, optional AND DISCARDED for app slugs** (`ParseSubdomainAppURL`: non-numeric slug ⇒ `agentName = ""` unconditionally). Canonical generated host for a subdomain app (what the dashboard links) is `{slug}--{workspace}--{owner}` [S4] — which on dev for ws `dev`, owner `thehackmeister`, app `openchamber` is **`openchamber--dev--thehackmeister-coder.dev.scifi.farm`** (double-dash), matching the observed 303 exactly.
- **Case:** pattern matching and host comparison are case-insensitive (`CompileHostnamePattern` lowercases; `HostnamesMatch` EqualFold) [S3] — and live: the mixed-case derived host 303s, normalizing with its case preserved [S12]. The block's `tr 'A-Z' 'a-z'` is therefore *cosmetic-consistency* (links look canonical), never load-bearing for routing. Keep it (test pins prefer deterministic bytes), but it is not a correctness risk if a future label were mixed-case.
- **Port hosts are strictly worse** [S20][S3][S12]: dashboard/wildcard port access requires the port actually **forwarded** (Open Ports UI / `coder port-forward`), default listening-port visibility `owner`, a 63-char first-label limit, and on the gpu side the observed DNS view does not even resolve port-label names (`3000--main--…` NXDOMAIN without `--resolve`; 303 *with* `--resolve`, i.e. coderd accepts but the lab DNS does not route it to humans). So the plan's documented fallback ("port-label base from the run-state port") is a **worse** base than UNRESOLVED: it resolves-to-nothing on gpu humans and forward-depends on dev humans. Recommend the plan text say so explicitly.
- **Deep link behind each:** `/?session=<id>` is client-side (OpenChamber router; integrations build the identical URL) [S15][S17] and the auth-redirect chain preserves the query verbatim through agent-dropping normalization on both coders [S12]. The written link may carry `--main--` while the browser's final URL bar shows the canonical host — harmless redirect, same SPA, same session opened. No token-vs-browser-session asymmetry affects humans: agent tokens never touch these routes (and are rejected on user-scoped ones [S21]).

## Contradictions vs the planner's local evidence — called out explicitly

1. **The shipped D20 literal is a dead host (400), not "auth-beyond-unfetchable" (400-recognized-routed).** `openchamber--dev-thehackmeister-coder.dev.scifi.farm` (single dash) fails coderd's application-url regex (needs ≥3 `--` segments) — dev coderd answers **400 Bad Request**; the double-dash canonical and the agent-labelled forms answer **303** [S12][S3]. The plan's interpretation "the dev-host family answers 400 → recognized-routed, auth unfetchable from plan-time" is **wrong**: 400 means *malformed hostname*, and it was observed on exactly the literal. Consequence: (a) the intake's "user-browser-confirmed" `{app}--{workspace}--{user}` order is right, but the *recorded string* dropped one dash in transcription — the working host the user saw was `openchamber--dev--thehackmeister-coder…` (which also matches the 2026-09-28 gpu evidence pattern `openchamber--main--spencerslab-claud--thehackmeister-coder…` [S10]); (b) **the `session` custom-field values and comments on card #50 written from the literal are broken links** (a human clicking gets a 400 page, not OpenChamber). R2's out-of-scope rule keeps history byte-frozen — keep it — but the landing note should let the user fix card #50's session CF manually. (c) The negative-literal test pin (t19: absence of the single-dash literal) is still correct, but a *positive* pin of the double-dash dev host would now be wrong too — the dynamic contract bans both.
2. **"Derived named host matches the intake-D20 label order" (plan's survey wording) is half right.** It matches the *order*, but the derived host additionally carries the agent segment; parity holds only because coderd *ignores* it for slugs — verified by source + probes, not assumed. The mechanism's reliability statement should be "routes identically (agent label parsed-away)", never "string-equal to the dashboard host".
3. **gpu DNS view is not a wildcard** (plan suspected "quirk; re-verify"). Measured: workspace-view DNS on gpu resolves ONLY the exact current app host (`openchamber--…-coder.spencerslab.com`); `foo.spencerslab.com`, `bar-coder.spencerslab.com`, hypothetical `openchamber--anything--here--me-coder…`, and port-label hosts are NXDOMAIN; Cloudflare DoH confirms these are all split-horizon names invisible to the public root [S12][S13]. The 2026-09-28 debug's wildcard fix is evidently not (or no longer) present in this view. **Impact:** the derived host resolves today *for this workspace*, but a NEW/RENAMED gpu workspace's derived host would not resolve for lab humans until a DNS record exists. The `!`-block cannot see this (it expands regardless of DNS) — the plan's live control (b) (`curl -sI` expects 303/401-family, NXDOMAIN/404 ⇒ fail) is the right catch, and the durable fix is a landing-note recommendation: add split-horizon wildcard `*-coder.spencerslab.com → 10.0.22.205` (the gpu coder's ingress already serves `*.spencerslab.com` from the 2026-09-28 change [S10]). Dev side needs nothing (true wildcard already).
4. **OpenChamber "instance has a public address" ≠ configuration.** Intake §10's phrasing implied a server-side address possibly readable by an agent; source shows browser-reported per-event origins only [S15][S16][S17]. RQ2 candidate: resolved-and-rejected; the plan's survey row can be marked NO (not UNRESOLVED) in the rework.

**Where everything agrees (confidence anchors):** same build on both coders; env always injected (source); grammar + agent-discard (source + live 303 both sides); query preserved through auth; link shape matches OpenChamber's own; only single source for the origin readable from the launch path is `$VSCODE_PROXY_URI`.
