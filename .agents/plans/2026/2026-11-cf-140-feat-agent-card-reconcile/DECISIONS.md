## Resolved by research (supersedes an earlier scout finding — do not re-derive)
- 2026-11-24 coord (R3, corroborated by R4): **`GET /api/session/active` WORKS on the live v2.3.2 build.** `EXPLORE-session-api.md` recorded it as proven-unusable (a v2.0.32-era fact, cf-50) — that is superseded. The surviving caveat R4 proved: it is **process-local**, and this host runs TWO opencode server processes, so a single-port read silently under-reports. Design must read every server, not one.
- 2026-11-24 coord (R3): **review risk B1 is dissolved, not mitigated.** A pending question IS durable data — the `question` tool creates a Form (`metadata.kind==="question"`), readable at `GET /api/session/:id/form` with `state.status==="pending"`. A blocked session stays busy forever and never self-times-out, so the 15-minute rule has a real clock and a paused run can no longer be mistaken for a dead one. Events (`form.created/replied/cancelled`) are volatile-by-contract: the durable form read is the authority, the event is a hint.
- 2026-11-24 coord (R4, corrects its own brief): per-card activity reads ARE possible on WeKan v12.99 via a **scoped export** (`cardId` is a first-class export scope key) — the scout's "full-board fetch cost" read the non-streaming `build()` path. There is still no per-card activities REST route.
