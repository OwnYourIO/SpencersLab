# C08 — Follow-up-card lineage: `parent_id` **and** a child→parent `fixes` edge, superseding the parentId-only ruling

size: **M** · wave 3 · depends_on: **C06** · model: `gpu-ai/qwen3.8-flash-next-strata-q4` (both tiers)

## Goal

Change the follow-up-card protocol so a new card carries **both** lineage representations (owner
ruling OQ13 → D25): `parent_id` on `create_card` (the shipped single representation, kept) **and** a
**`fixes` edge drawn from the child to the parent at creation** — while `fixes` stays **non-gating**
(C06's set) and **non-grouping**, and the supersession of the shipped "parentId is the ONLY
representation" ruling is written **where that sentence lives**, not only in DECISIONS.

## Ground truth the text must not overstate

- The sentence being superseded: `.rulesync/skills/boards/SKILL.md:426` — "`parent_id` is the ONLY follow-up lineage representation (the batched-round ruling — no dependency edge is drawn for a follow-up and none is expected back)"; the same law is echoed in the grouping section (`:375`, which **C06** has already re-cut to "`parent_id` lineage is never a grouping trigger" — that half **stays true** and must not be re-written here).
- The tool exists: `add_card_dependency` is an **UPSERT** (a repeat add updates the edge, never duplicates it), posts the card dependencies route with the pinned `cardId` key, documents the `dependsOn` alias, and **rejects an unknown type before the POST** — `fixes` is one of the seven accepted types (`skills/wekan-mcp/SKILL.md:58`, `tests/wekan-mcp/dependencies.sh:174-210`). Direction: the edge is stored on the card whose route is posted, so **child → parent** is an `add_card_dependency` call **on the child** — which, under C06's direction law, is exactly "the stored source is the dependent".
- `related-to` is the only gating type and grouping triggers on inbound `related-to`; a `fixes` edge therefore changes **nothing** about pickup or grouping — the text must say that explicitly so nobody "discovers" a new gate.
- Degrade posture for the whole follow-up leg is already shipped (probe `tools/list` once; absent/failed ⇒ body-line degrade + RESULT note, never a stall), and `create_card`'s `parent_id` has no degrade — it rides the create call.
- `parent_id` stays the representation the **claim-time block** reads for inherited checklist answers (`:324`), so the edge is additive context for humans and the dependency lists, not a replacement: dropping `parent_id` would break the preload/block inheritance path.
- The `dev-deploy` protocol's hand-off card is the one follow-up that already names its parent explicitly — it gets the edge too, same shape.
