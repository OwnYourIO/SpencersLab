# C01: containers/vllm-rocm overlay image (v0.33.0-rocm100 base + vllm-gguf-plugin)
size: M   wave: 1   depends_on: []

## Goal

A single thin overlay image: upstream `vllm/vllm-openai-rocm:v0.33.0-rocm100` (the
R1-verified image class — ROCm 10.0, PyTorch 2.13.0, py3.12, kernels for gfx1201+gfx1151)
plus the out-of-tree `vllm-gguf-plugin` (GGUF weight loading — the only 32 GiB path that
fits the 3–4-session envelope, R1 §3/§4), pinned to a GIT REF, not a PyPI release (the
newest release v0.0.5, 2026-08-10, has no Qwen3.5 adapter — PR #98 is main-only — and
plugin main is import-broken against the pinned base until a 2-line compat patch is
applied: RESEARCH Post Research V1) and the R1 recipe env pins. Repo container
conventions apply: manual tag→digest ledger, zero renovate directives on the image pins
(strata C01 contract — the one sanctioned directive is the plugin ARG's `git-refs`
comment, repo convention per `containers/gpt-researcher`), CI-primary build.

1. `docker build containers/vllm-rocm` => `no-daemon, CI-deferred` line in
   `commands_run` (the designed passing gate shape per AGENTS.md); CI on the pushed
   branch is authoritative.
2. The Dockerfile pins the base by TAG and the README ledger carries the full
   `sha256:` digest; the ledger's re-verify command (registry API probe) is documented
   and its output captured in `commands_run`.
3. `vllm-gguf-plugin` is pinned to a GIT REF — a full commit SHA on the git-URL ARG
   with the `# renovate: datasource=git-refs` comment (in-repo shape, `containers/
   gpt-researcher` precedent) — NOT a PyPI release (none exists with the Qwen3.5
   adapter) and NOT a bare branch name; the 2-line import-compat patch is vendored
   under `carry/`, applied in the Dockerfile, and documented in a Dockerfile comment
   (strata carry-patch precedent); the README carries the vLLM-0.33-compatibility note
   (ref + patch + why no release exists).
4. The env pins from the Goal are present in the Dockerfile; no other runtime behavior
   is changed relative to the base (the overlay adds the plugin + env, nothing else).
5. Zero renovate directives/comments anywhere in `containers/vllm-rocm/` EXCEPT the
   one sanctioned `git-refs` comment on the plugin ARG (the manual-ledger contract
   covers the image pins; the plugin git ref is renovate-tracked by the post-research
   ruling).

## Notes for dev

- No docker daemon in agent sessions — do NOT attempt `docker build`; capture the
  registry facts with `curl` (or webfetch) and report `docker build => no-daemon,
  CI-deferred`.
- The base image is 18 GB with zstd layers (needs containerd ≥1.5 — the node has
  2.3.4, R1 Q5.2); nothing to do about it here, it's a runbook fact (C06).
- Watch for a `vllm-gguf-plugin` release (v0.0.6?) or main commit carrying PR #98 +
  the #60623 import fix — when one ships, point the ARG pin at it, drop the `carry/`
  patch, and re-record the ledger (RESEARCH Post Research open question 2). Until
  then the git ref + patch is the designed path; the C06 step-3 import probe is the
  acceptance.
- The chart never imports the plugin — vLLM loads it at serve time via the
  `vllm.general_plugins` entry point, so an import break surfaces as engine startup
  failure, not a chart error.
