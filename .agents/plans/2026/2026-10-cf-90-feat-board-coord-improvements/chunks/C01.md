# C01: Board provisioning command (lists → labels → rules, idempotent)
size: L   wave: 1   depends_on: []

## Goal
Ship the AI-Dev board initialization/update process the card asks for: an
idempotent read-then-create flow that syncs Planning's lists from Backlog
(never deleting extras), creates one `Bucket: <list>` label (color
`darkgreen` — the board's live "Bucket Color" swatch) plus the two rules
(createCard + moveCard, both scoped `swimlaneName: Planning`) per Planning
list, and creates the `Provider: API` / `Provider: Local` labels. It ships as
a deterministic offline engine script + a hand-written skill + a slash
command, with dry-run-first validation and a raw-REST fallback for tools the
DEPLOYED dev-boards surface lacks.

## Tasks
- [ ] `scripts/provision-board.py` — offline engine, stdlib only, no network,
      no credentials. Inputs: `--fixture <snapshot.json>` (swimlanes+ids,
      lists as `{swimlane_id: [titles]}`, labels `{name: color}`, rules as
      normalized `{title, trigger, action}` records) and the built-in spec
      (source swimlane `Backlog`, target swimlane `Planning`, bucket color
      `darkgreen`, provider labels `Provider: API` + `Provider: Local`,
      two-rule-per-list template, and the **Inbox rules** below). Output: an
      ordered action list —
      `create_list(title, swimlane)`, `create_label(name, color)`,
      `create_rule(title, trigger, action)` — or empty; `--format json|text`.
      Idempotent by construction: it diffs snapshot vs spec and emits only
      missing pieces. Title matching is case-insensitive; it never renames.
      **Inbox rules (batched-round ruling):** (a) ensure the `Inbox` list
      exists in the BACKLOG swimlane — emit `create_list(Inbox, Backlog)`
      only when absent; (b) the mirror set is Backlog list titles MINUS
      `Inbox` — Inbox is never copied into Planning; (c) no `Bucket:` label
      and no rule pair is ever emitted for Inbox.
- [ ] `skills/wekan-board-provision/SKILL.md` (hand-written skills/ surface,
      NOT rulesync-managed) — the operational procedure:
      1. collect the snapshot via dev-boards reads (`list_swimlanes`,
         `list_lists`, `get_board`, `list_rules`);
      2. `python3 scripts/provision-board.py --fixture <snapshot>` → the
         action plan (this IS the dry run — print it, human confirms);
      3. apply: probe the live tool catalog first; `create_rule` via
         dev-boards (present in the deployed surface); `create_list` /
         `create_label` via dev-boards when present, else emit the raw-REST
         recipes (`POST /api/boards/:id/lists` with `{title, swimlaneId}`;
         `POST /api/boards/:id/labels` with `{name, color}` — human shell,
         `WEKAN_BASE_URL` + `WEKAN_TOKEN` per the wekan-api skill convention,
         or the admin surface) and stop cleanly for human confirmation;
      4. verify: re-collect the snapshot, re-run the engine → expect ZERO
         actions. Additive-only invariant in the text: never delete a list
         absent from Backlog. The skill states the Inbox contract: Inbox is
         a Backlog-swimlane list the engine ensures exists, it is EXCLUDED
         from the Backlog→Planning mirror, and it never receives a Bucket
         label or rule pair.
- [ ] `.rulesync/commands/wekan-board-provision.md` (new command, default
      agent — no `agent:` frontmatter; dev-boards calls ride the project MCP
      config with interactive ask-approval) → `rulesync generate`.
- [ ] `.rulesync/rules/overview.md` — one line in the commands/agents-surface
      section naming `/wekan-board-provision` (AGENTS.md discoverability).
- [ ] `tests/wekan-board-provision/` — fixtures + surface suite (## Tests).

## Acceptance criteria
1. On the live-state fixture (Inbox present in Backlog) the engine emits
   EXACTLY: 2 `create_list` (Planning: `Outside Process`, `Wekan`), 8
   `create_label` (`Bucket:` × each Planning list including the 2 new), 16
   `create_rule` (createCard+moveCard per list, each trigger carrying
   `swimlaneName: Planning`), 2 provider `create_label` (`Provider: API`,
   `Provider: Local`) — and nothing else.
2. On the fully-provisioned fixture the engine emits ZERO actions
   (idempotence — the update path the card asks for).
3. Inbox contract: with Inbox present in Backlog the engine emits NO action
   for it (no mirror into Planning, no `Bucket: Inbox` label, no rule pair);
   with Inbox ABSENT from Backlog it emits exactly one
   `create_list(Inbox, Backlog)` and still never mirrors/labels/rules it.
4. The script imports no network module and accepts no credential argument;
   applying is the skill's job, never the engine's.
5. The skill text pins: dry-run-first, additive-only (never delete lists not
   in Backlog), case-insensitive title match with never-rename, tool-probe
   before apply, raw-REST fallback recipe, zero-action verify step, and the
   Inbox contract of AC3.
6. `rulesync generate --check` clean; second `rulesync generate` is a no-op;
   generated command parses (frontmatter `description` present).
7. `bash tests/wekan-board-provision/surface.sh` green.
8. No live board mutation happens in this chunk — the one live provisioning
   run is the post-merge, human-confirmed hand-off (DECISIONS.md).

## Notes for dev
- WeKan rules cannot derive a label from the destination list (RESEARCH F1):
  one label + two rules per list is the design, not a shortcut.
- Card creation emits `createCard`, not `moveCard` — hence BOTH rules per
  list. Bucket rules are single-action, so rule-order concerns don't apply.
- Rule title convention for idempotent comparison:
  `Bucket: <list> — <activityType>` (the engine normalizes existing rules the
  same way before diffing).
- The Farm swimlane carries a human typo list `Outside Proccess`
  (RESEARCH adjacent) — the matcher must leave it untouched; case-insensitive
  compare, never auto-rename.
- Deployed dev-boards today LACKS create_list/create_label/create_swimlane
  (live-probed 2026-10-31: `Unknown tool 'dev-boards.create_label'`) — the
  REST fallback is not theoretical; the ledger card L4 tracks the pin bump
  that makes the MCP path whole.

Findings (non-blocking):
- minor — scripts/provision-board.py:97–118 `existing_rule_keys`: the
  canonical-key fallback judges a bucket rule pair "already present" from
  the TRIGGER ALONE (swimlaneName=Planning + listName + activityType)
  without consulting the rule's action. A human-made Planning-scoped
  createCard/moveCard rule on a mirrored list with a different action (e.g.
  addChecklists) would suppress the list's Bucket rule pair, and the step-4
  zero-action verify would then report the missing pair as done. Fix: gate
  the canonical key on the normalized record carrying
  `action.addLabel == "Bucket: <listName>"` (case-folded) in addition to
  the trigger — the title key already covers the stated convention.
- nit — scripts/provision-board.py `load_snapshot`: the `schema` key is
  never version-checked (`wekan-board-snapshot/99` plans happily, probed
  rc=0). Required-key failures are precise, so impact is limited to a future
  v2 snapshot silently diffed as v1. Fix candidate: `fail` when
  `snapshot.get("schema")` is present and != `"wekan-board-snapshot/1"`.
- nit — skills/wekan-board-provision/SKILL.md:70: "Apply the plan in its
  emitted order — lists, then labels, then rules" describes phase groups,
  but the engine emits label→pair interleaved per list with the two
  unreferenced provider labels last. Harmless (every bucket label precedes
  its own rules), but could mislead an applier into re-sorting. Fix: reword
  to "in emitted order (lists first; each Bucket label precedes its rule
  pair; provider labels last)".
