# C06: -deploy variant (definition only)
size: L   wave: 3   depends_on: [C05, C03]

## Goal
Create the new `-deploy` variant the card describes — the agent that runs
after the final review comes back clean and owns the git/deploy/debug loop —
plus the coordinator hook that launches it. It ships as DEFINITION ONLY:
nothing in this ticket runs it; the stage fires when a card checks the
`Deploy` Lifecycle stage (boards Stage map unchanged — cite it).

      skill, disable-model-invocation, MUST-loaded by both deploy agents):
      the expectation that the initial deployment is broken in one or more
      ways; per issue — identify it (readonly cluster MCP, logs, events),
      produce A COUPLE of solution options; if interactively working with the

      `question` the user to pick; otherwise (unmanned/pipeline) take its
      own recommendation, implement it in the current session, deploy, and
      examine the result; loop until satisfied or ~90% context, then hand the
      work back to the coord (RESULT) for reintegration with the plan and
      tests, after which everything gets re-reviewed; on hand-back it closes
      its OWN worktree (branch stays coord-owned, landing-gated per C03).

      hook: when the final review returns APPROVED AND the run has a Deploy

      (roster widens: coord may launch `agent-dev-deploy` /
      `agent-dev-deploy-pr`); on its RESULT, fold the changes back into the
      plan/tests and RE-RUN the final review. User-cancel path: if the deploy
      session comes back cancelled by the user, the coord raises ONE
      `question` whose answer hands control back to the coord (never silently
      relaunches).
- [ ] `.rulesync/rules/overview.md` — the Agents section names the new pair
      (definition-only status stated).
- [ ] Tests: new `tests/agent-dev-deploy/surface.sh` (+ agent-perms matrix
      extension if that suite enumerates agents).
