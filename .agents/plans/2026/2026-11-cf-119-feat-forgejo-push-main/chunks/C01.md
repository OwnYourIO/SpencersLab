# C01: `main-sync.yaml` workflow + offline contract suite
size: M   wave: 1   depends_on: []

## Goal

Land the entire in-repo surface of the cf-119 main-sync design: one Forgejo Actions workflow
with two instance-guarded jobs — `push-main` (infra instance only: non-force push of `main` to
GitHub `OwnYourIO/SpencersLab` and to `git.scifi.farm`, failing the job if either push fails)
and `backup-proxy-merge` (dev instance only: merge `main` into `backup-proxy`, creating the
branch from `main` if absent, on the automatic `FORGEJO_TOKEN`, no secrets) — plus the offline
bash contract suite that pins the workflow's invariants (triggers, guards, no-force, targets,
secrets, runner labels) with no network. The suite is written red-first INSIDE this chunk
(no separate test session — Test Writing unchecked; plan P-2 / DECISIONS #4), then the
workflow is written to make it green.

## Notes for dev
- pyyaml (YAML 1.1) parses the top-level `on:` key as boolean `True` — t2 must read the trigger
  block as `doc.get(True) or doc.get('on')`; asserting on the string key `'on'` reddens a
  correct file (plan suite spec, t2 note).
- Forgejo (not GitHub) semantics: the running instances are 15.0.10 (v15.0 LTS line).
  `startsWith` in job `if:` and `forgejo.server_url` are confirmed for that line (plan
  Authority table). Job-level `permissions:` and `continue-on-error` are ignored by Forgejo —
  don't write them.
- `runs-on`: choose one of the five runner labels (`ubuntu-latest`, `ubuntu-24.04`,
  `ubuntu-22.04`, `docker`, `node22`) — `ubuntu-24.04` suggested (explicit over `latest`);
  t7 pins the set, not the member. `ubuntu-26.04` (GitHub-hosted style) routes to nothing.
- The automatic `FORGEJO_TOKEN` is same-repo-only — it may serve the checkouts and Job 2's
  branch push, and never Job 1's external pushes (EXPLORE §2).
- Token handling: URL-embedded credentials in the push commands only; no `git config`
  credential writes, no tokens in the checkout step.
- Step order in `push-main`: diag → GitHub push → dev push (GitHub lands first during the
  expected-red window while the dev instance is down).
- The workflow will be inert until the owner bootstraps it onto infra `main` (plan UA5) and
  sets the two infra Actions secrets (UA3) — nothing in this chunk goes live.
- Comments: why-only, no ticket/round narration (aislop scans both new files on the PR).

### Design conformance (plan "Design" + DECISIONS)

- One file, two jobs, mutually-exclusive `startsWith(forgejo.server_url, …)` guards with the exact
  planned literals; `push.branches == [main]` + `workflow_dispatch: {}` (P-1 kept).
- `actions/checkout@v6` both jobs (v15.0 quickstart pin); `runs-on: ubuntu-24.04` (suggested
  member of the pinned five-label set).
- Diag steps as specified: `server_url` (+ `forgejo.repository` in `push-main` only).
- Step order `diag → GitHub push → dev push` — GitHub lands first during the expected-red window.
- Failure contract intact: every external push its own `run:` step beginning
  `set -euo pipefail`, plain `git push`, no swallowing, no `continue-on-error`.
- Merge semantics per the OQ-2-confirmed state: `ls-remote --exit-code --heads` present →
  fetch/checkout/`git merge --no-ff main`/push; absent → `git push origin main:backup-proxy`;
  conflict or refusal exits non-zero, never `--force`, never auto-resolve. The else-branch comment
  honestly records that a transport error lands there too and fails via the push.
- Token handling per plan: URL-embedded credentials in the two push commands only; no
  `git config` writes, no token in either checkout; job 2 references no secret at all
  (automatic same-repo token).
- Secrets of record match the plan's table: `GITHUB_PUSH_TOKEN` for the GitHub leg,
  `FORGEJO_DEV_PUSH_TOKEN` for the dev leg.
- Header comment carries all three required whys (ping-pong guard + `startsWith` tolerance + diag
  recoverability; non-force card contract + deliberate non-use of the built-in force-push mirror;
  same-repo automatic token suffices for job 2, conflicts fail for a human). Why-only, no
  ticket/round narration; every inline comment in both files passed the comment-slop three-clause
  test (each justifies something that looks removable: `fetch-depth: 0`, `-B main`, the `-c`
  merge identity, the file-wide guard/secret counts).

### Deviations (all five reviewed, none interface-changing)

1. t5 boundary-anchored regex — verified load-bearing by the extending/truncating rename
   mutations above; the spec's assertion is unchanged, only actually enforced.
2. `fetch-depth: 0` on both checkouts — required hardening (the checkout action's default is a
   one-commit shallow clone); no contract leg pins checkout params, the comment carries the why.
3. `HEAD:refs/heads/main` refspecs + `git checkout -B main` in job 2 — makes both jobs
   independent of a detached-HEAD checkout while keeping the push plainly non-force.
4. Merge identity via `git -c user.name/user.email=…` — no config write, no credentials.
5. AC4 environmental (branch mint lag + plan commit on branch) — accurate as assessed above;
   coordination follow-up, not a chunk defect.
