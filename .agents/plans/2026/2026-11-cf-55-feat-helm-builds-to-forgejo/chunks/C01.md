# C01: Move the helm release pipeline to Forgejo Actions (dual publish)

size: L   wave: 1   depends_on: []

## Goal

`.forgejo/workflows/release.yaml` becomes the single chart bump+publish authority
running on the prod Forgejo instance's runner: detects changed charts, test-builds
them, commits Chart.yaml patch bumps to Forgejo `main` (single-writer,
idempotent, fast-forward-only loop — two-runner-safe), and publishes DUAL:
GitHub Releases + gh-pages index via `cr` with `PUSH_TOKEN_GH` (primary, consumer
contract byte-stable) AND the prod instance's Helm package registry via the
same-forge `PUSH_TOKEN_FJ` user-PAT (D22 — independent job, fails loudly-but-
separately) — while
`.github/workflows/release.yaml` is deleted in the same commit.

### Findings

**BLOCKER 1 — `changes` job outputs can never resolve: detect step has no `id`.**
`.forgejo/workflows/release.yaml:35-36` maps the job outputs to
`${{ steps.detect.outputs.CHARTS }}` / `…detect.outputs.HAS_CHANGES`, but no
step in the file carries an `id:` (verified: `grep -n "^\s*id:" release.yaml`
empty; the deleted twin had `- id: charts`/`- id: check_changes`). `steps.detect`
resolves against a nonexistent id → outputs render empty (context errors on the
stricter engines). Consequences on every fire: `test-build`
`fromJSON(needs.changes.outputs.charts)` over `''` fails the job (or yields zero
combinations), `bump`'s `json.loads('')` raises, and both publish gates
`if: needs.changes.outputs.has_changes == 'true'` are false — the whole workflow
either reddens at test-build or no-ops silently. Nothing can ever publish.
**Fix:** add `id: detect` to the "Detect changed charts" step (:45).
**Suite note (test session, not a weakening):** forgejo-release.sh has no leg
pinning that every `${{ steps.<x>.outputs… }}` reference names a declared step id —
suggested extension (mutation M12 below proved both the broken and the fixed file
pass t1-t12, so a wiring leg is the only real guard here).

**MAJOR 2 — `forgejo-publish` upload issues PUT but Forgejo 15.0 registers the
helm upload route as POST-only.** `.forgejo/workflows/release.yaml:445`:
`curl -f --user "…" --upload-file "$pkg" "$pkg_api"` — curl's `--upload-file`
defaults the HTTP method to **PUT**. Verified against the lab's exact lineage
(codeberg forgejo `v15.0/forgejo` branch, `routers/api/packages/api.go:510`):
`r.Post("/api/packages/{owner}/helm/api/charts", reqPackageAccess(write), …,
helm.UploadPackage)` — there is no PUT handler, so every upload 404/405s, `curl -f`
fails, and the leg goes red on every fire: the instance Helm registry would stay
permanently empty (loud-but-isolated per D13, so the GitHub leg still works — but
the chunk's DUAL-publish goal never lands). RESEARCH B2 [13]'s call form shows the
`-X POST` explicitly. **Fix:** `curl -f -X POST --user "${FJ_PACKAGE_USER}:${FJ_PKG_TOKEN}" --upload-file "$pkg" "$pkg_api"`.
Same-source verification also settled two open RESEARCH flags: the handler reads the
body via `ctx.UploadStream()` (raw body — `--upload-file` is the right carrier, not
multipart), and `OverwriteExisting: true` in `CreatePackageOrAddFileToExisting`
confirms RESEARCH B4's (then-unverified) overwrite-on-re-push semantics — which makes
the leg's authenticated index pre-check the load-bearing anti-churn guard, and it is
correctly implemented (`routers/api/packages/helm/helm.go`).
**Suite note (test session):** t10 pins the URL shape but not the method — suggested
extension to pin `-X POST` alongside the charts route.

**MINOR 3 — published-index idempotency guard is keyed by directory name.**
`release.yaml:219` does `published.get(chart, (0,0,0))` with `chart` = the
`charts/<dir>` name, but the index keys entries by Chart.yaml `name:`. Repo scan:
exactly one divergence, `charts/traefik-zerotrust/Chart.yaml` → `name: traefik` —
for that one chart the "patch above the published index" limb is inert (a cutover-
window skew would produce a benign extra bump, not a re-mint: `cr upload
--skip-existing` stays the hard guard). Optional fix: key the published lookup by the
tree Chart.yaml `name:` instead of the directory name. Not blocking.

**NIT 4** — the `RELEASES_HOST` comment (`:22-25`) justifies the composed asset host
with the no-forge-URL portability law, but github.com is not the forge; the law's
ownable limb is the t8 literal ban, which the composition satisfies. Comment wording
only.
