# Decisions

Append-only. Newest at the bottom. Format: date, who (plan|coord|human), decision, alternatives rejected, why.

## Conventions
- Renders run on COPIES under `/tmp/opencode` + `helm dependency build` there (worktree never written; the tracked `Chart.lock` stays byte-identical — cf-104's dance).
- `export PATH=$HOME/.local/bin:$PATH` in every shell that renders (cf-104 trap: silent empty output).
- Suites run SOLO (cf-104 friction: concurrent helm renders degraded counts via registry skips).
- Pinned baselines are MEASURED numbers (cf-104 plan-number lesson): re-pin what you measure, never what you expect.
- `{{ include "…" }}` returns a STRING — gate conditions must be `eq (include …) "true"` (a bare `if include` is always-true; cost the planning round an hour, 2026-11-07).
- No cluster mutation by pipeline agents (render + MCP reads only); merge/sync/PR are user-owned.

## Decisions

- 2026-11-06 human (coord-relay, verbatim): "we need to make the S3 component optional. It should just write lfs junk to a 10gb volume if s3 is not enabled (default). We need to apply this not enabled stance to the dev forgejo at git.scifi.farm."
- 2026-11-06 coord (interpretation ruling, relayed in the plan launch): the forgejo chart's S3 (SeaweedFS-gateway) LFS storage component becomes OPTIONAL, DEFAULT OFF. Default off = LFS server still on, objects stored LOCALLY on the instance's data volume. An instance opts INTO S3 by carrying `STORAGE_TYPE: minio` + endpoint + TLS flag + the `forgejo-s3` vault UUID in its custom-values slice. DEV gets the not-enabled stance (drops its S3 config); INFRA keeps S3 exactly as cf-104 shipped it (zero infra regression = acceptance criterion); runner charts/apps untouched. No-questions run: new questions → plan Open questions best-guess-first, never the `question` tool.
- 2026-11-07 plan: D1 — the gate is the merged `gitea.config.lfs.STORAGE_TYPE == "minio"`, evaluated by a NEW wrapper named helper `forgejo.lfs.s3.enabled` (`charts/forgejo/templates/_helpers.tpl`), `get`/`default`-guarded, consumed as `eq (include …) "true"`. Alternatives rejected: a new boolean flag (coord ruling 1: the instance's own declaration IS the switch); evaluating the gate per-template inline (three call sites — DRY + one testable surface); a values-map "mode" key (same wall as the boolean, more values surface to fork).
- 2026-11-07 plan: D2 — the four shape constants (`MINIO_BUCKET: git-lfs`, `MINIO_BUCKET_LOOKUP: path`, `MINIO_CHECKSUM_ALGORITHM: default`, `SERVE_DIRECT: "false"`) move OUT of chart `values.yaml` into a NEW whole-gated wrapper `Secret/forgejo-lfs-shape` (template-injected constants, single source — plan A14 values unchanged from cf-104's user answers), reaching app.ini via four optional `secretKeyRef` env legs. Alternatives rejected: (i) keep them in chart values (renders on dev — violates the zero-artifacts AC); (ii) carry them in infra's slice (violates the blast-radius AC `custom-values/infra` untouched + forks for any future opted-in instance, which then must copy 7 keys instead of 3); (iii) `gitea.additionalConfigSources` file mount (infeasible — A2: Secret volumes have no `optional`, a dangling reference wedges the dev pod in CreateContainerConfigError, the live A11 failure mode).
- 2026-11-07 plan: D3 — the two pre-existing credential env legs gain `optional: true` on their `secretKeyRef`; the list stays the chart's single static `gitea.additionalConfigFromEnvs` (no slice override, cf-104 lesson intact). Alternative rejected: a separate values key the wrapper template "merges when gated" or a template-side filter of the env list — both INFEASIBLE (A1: the pinned subchart renders the pod env verbatim from static values; the wrapper's templates cannot touch the subchart's pod spec; helm values cannot be conditional). `optional: true` is the only k8s-native soft dependency (A2) and it is what un-wedges dev (A11) while leaving infra's effective config identical (A9). Documented consequence (plan Risks): if infra's ESO Secret were ever missing at pod start, the pod boots without cred envs and crash-loops in storage init instead of waiting in CreateContainerConfigError — self-healing, loud, bounded by the ESO's 1h refresh.
- 2026-11-07 plan: D4 — the coord ruling's AC3 wording "infra effective render byte-identical on [lfs]/[server]/ESO/env legs" is RE-WORDED to "infra EFFECTIVE S3 config identical; whole-render delta == exactly the A9 four-item list" — the ONLY adjustment to the coord ruling, with evidence: "whole render byte-identical" is unachievable by any design that removes the shape keys from dev's render (A1: the inline `[lfs]` string is built solely from the merged `gitea.config.lfs` values map, so the 4 shape keys must either stay in chart values — ruled out by the zero-artifacts AC — or leave the inline string — the A9 delta). The zero-regression property survives as a mechanical, reviewable assertion (A9 + AC3): `[server]` byte-identical, ESO byte-identical, effective `[lfs]` = same 7 keys + same 2 cred legs, render diff pinned line-for-line.
- 2026-11-07 plan: D5 — the `forgejo-s3-secret` ExternalSecret gets a WHOLE-OBJECT gate (body otherwise byte-untouched); the chart's `bitwardenIds.forgejo-s3: OVERRIDE_VIA_CUSTOM_VALUES` sentinel STAYS (coord ruling 2 — infra consumes it; dev simply stops providing a value; the sentinel's only consumer is gated, so it can never leak into a gate-closed render — verified in the bare render, A10). Alternative rejected: dropping the sentinel from the chart (would force `custom-values/infra` to keep feeding it some other way and changes infra's blast radius).
