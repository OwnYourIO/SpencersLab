## TL;DR

1. **Q1 (Gateway API): technically possible, not the cheapest path.** Gateway API CRDs are already installed on both clusters by k3s's `traefik-crd` chart — **dev has `tcproutes` (k3s v1.36.5 bundles gateway-api v1.6.1, where TCPRoute graduated to Standard), infra does NOT (k3s v1.36.2 bundles gateway-api v1.5.1)** [11][6]. Traefik 3.7.x runs on both but `--providers.kubernetesgateway` is not enabled; enabling it (+ `experimentalChannel`, still required by Traefik despite upstream promotion) goes through the **already repo-managed** `HelmChartConfig` in `charts/base/templates/traefik-config.yaml` [11][12][5]. Gateway listeners can only bind EXISTING entrypoint ports, so external exposure still means a new entrypoint + a new port on traefik's LoadBalancer service → ServiceLB hostPort [1][2].
2. **Q2 (ServiceLB): yes, proven in-lab.** ServiceLB works on all three clusters (live svclb evidence incl. the repo-managed proxy-local qbittorrent precedent, port 58462 → hostPort 58462, LB IP = node IP) [11]. Mechanism: per-service DaemonSet, **hostPort = service port**; **a port busy on the node → svclb pod can't start → LB stays Pending** [5]. Node sshd holds :22 on every node → **any port-22 LoadBalancer/NodePort/hostPort design is a dead end unless the user moves node sshd** [5][11].
3. Non-22 port (e.g. 2222) is forced on every viable design. Forgejo renders the port in clone URLs via `server.SSH_PORT`; the chart hardcodes `SSH_PORT: 22` in its values, so the plan **must set `gitea.config.server.SSH_PORT` explicitly** (the chart's SSH_PORT←service.ssh.port auto-follow never fires when the key is already set) [9].
4. Host keys persist (built-in SSH server, keys under `/data` on the persistent PVC, generated once), and `git.*` already resolves to the node IPs that ServiceLB advertises — so a non-22 endpoint on the same host keeps known_hosts continuity; clients just gain a new `[host]:port` entry [10][13].
5. Recommended default: **ServiceLB directly on the forgejo-ssh service with a non-22 port** (smallest diff, no traefik changes, in-lab precedent). traefik `IngressRouteTCP` on a new entrypoint is the alternative if the user wants traefik in the path. Gateway+TCPRoute only if Gateway API is a strategic direction (it solves nothing extra for one fixed port, and needs an infra CRD fix first).

### F2 — Q1: Gateway API + Traefik on this stack

- **Traefik 3.7 supports Gateway API spec v1.6.3**: HTTPRoute/GRPCRoute/TLSRoute/BackendTLSPolicy from the Standard channel **and TCPRoute** — but Traefik still gates TCPRoute/TLSRoute watching behind `providers.kubernetesGateway.experimentalChannel=true` (default false). Enabling `experimentalChannel` **without** the CRDs present kills the entire Gateway provider (traefik keeps running; other providers unaffected) [2].
- **Gateway listener ports must match existing Traefik entrypoint ports**; mismatch → ERROR + rejected status. A Gateway cannot open a new port by itself [1].
- External exposure chain for a Gateway listener: entrypoint (static config) → chart `ports.<name>` (`expose.default: true`, `exposedPort`) → traefik's LoadBalancer Service → **ServiceLB svclb hostPort on the node** [5][7][11]. So Gateway API changes nothing about the port-22/node-sshd problem or the ServiceLB dependency.
- **k3s officially documents this exact path**: HelmChartConfig `traefik` with `providers.kubernetesGateway.enabled: true` (+ `experimentalChannel: true` for TCPRoute) [5]. The lab already has that HelmChartConfig surface, repo-managed and ArgoCD-applied (`charts/base/templates/traefik-config.yaml`); the live traefik args on dev/infra prove the HelmChartConfig values are applied (e.g. infra's `seaweedvolume` entrypoint :8080 comes from it) [11][12].
- Enabling the provider also flips on the chart's default **GatewayClass + Gateway** (chart defaults `gateway.enabled: true`, `gatewayClass.enabled: true`, default web listener :8000) [6][7] — the planner should explicitly keep or disable these.
- **The CRD gap on infra is a k3s point-release artifact, not a channel issue**: k3s's `traefik-crd` chart = the CRDs split out of the bundled traefik chart [8]; `40.1.3+up40.1.0` (infra) bundles `gateway-standard-install.yaml` **v1.5.1** (no TCP/UDPRoute), `40.1.5+up40.1.0` (dev) bundles **v1.6.1** (includes tcproutes+udproutes — they graduated to the Standard channel in gateway-api v1.6.0) [6][3]. Infra gets tcproutes on its next k3s upgrade, or they can be installed by a repo template (caveat: k3s's helm release owns the CRD set with `forceConflicts: true` [11]; k3s docs warn gateway CRDs get removed if traefik is disabled — fixed only in April-2026+ releases [5]).
- The official **forgejo chart already ships a `tcpRoute` template** (`gateway.networking.k8s.io/v1alpha2` TCPRoute, disabled by default, `parentRefs` + port → `<fullname>-ssh` service) [9]. v1alpha2 is still served (deprecated) by the v1.6.3 standard CRDs [4], and Traefik claims v1.6.3 support [2] — but whether 3.7.13/3.7.4 accepts v1alpha2 TCPRoute objects specifically is untested here; verify at implementation.
- k3s also ships a separate optional **`gateway-api-crd` chart** (v1.6.x, `experimental.enabled` toggle) in k3s-charts [6] — a second, k3s-native lever for CRD management if needed.

### F3 — Q2: ServiceLB (klipper-lb)

- Mechanism (k3s docs [5], confirmed live [11]): each `type: LoadBalancer` service gets a `svclb-*` DaemonSet in kube-system; pods run `rancher/klipper-lb:v0.4.17` with **`hostPort = service port`** and forward to the service's nodePort (live: SRC_PORT 58462 → DEST_PORT 31839). Pods only land on nodes **where the port is free; if no node has it free, the LB stays Pending** [5].
- External IP: node external IP if configured, else internal IP, `ipMode: VIP` — live: every LB service in the lab advertises its node's 10.0.77.x IP (traefik on all clusters, samba/seaweedfs on infra, qbittorrent on proxy-local) [11].
- **Lab precedent (repo-managed)**: proxy-local qbittorrent `bittorent` service — `type: LoadBalancer`, `externalTrafficPolicy: Local`, port 58462, ArgoCD tracking-id `proxy-local:/Service:...`; svclb pod healthy, LB IP 10.0.77.54. Defined entirely in values (`services/proxy-local/prod/values.yaml`) [11][12]. Infra additionally proves LB services on 445/55355/3702 and 18880 via raw Service templates.
- **Port-22 collision**: node sshd binds :22 on every lab node (debug session finding; consistent with k3s nodes running openSUSE sshd). A LoadBalancer service with port 22 → svclb hostPort 22 → bind fails → pod never Ready → LB Pending forever [5]. Same kills NodePort-22 (below range anyway) and pod `hostPort: 22`. **Only escape: move node sshd off :22** — a host-level change outside GitOps, with lockout risk; strictly a user decision.
- Workarounds per docs [5]: non-22 port (trivial), `svccontroller.k3s.cattle.io/enablelb` / `lbpool` node labels (pointless on single-node clusters), `--disable=servicelb` (only if replacing it, e.g. MetalLB). Known issue: NAT + `externalTrafficPolicy=Local` + configured `node-external-ip` misbehaves — not applicable here (no node-external-ip; mesh traffic arrives unrouted-via-NAT at the node IP) [5].
- **NodePort alternative**: k3s default range 30000–32767 (all live nodePorts within it [11]; k8s default). Works without ServiceLB (kube-proxy DNAT), but clone URLs carry a 5-digit port and ports are allocated, not declared, unless pinned via `nodePort:`.
- Single-node failure modes (apply to every option equally): node down = SSH down regardless of mechanism; ETP=Local is mandatory for source-IP and is automatically satisfied (one node, pod always local).

### F4 — Forgejo side

- Config semantics (forgejo.org cheat sheet [10]): `SSH_PORT` = "SSH port **displayed in the clone URL**" (default 22); `SSH_LISTEN_PORT` = built-in server port, defaults to `SSH_PORT` but the chart forces 2222 for rootless; `SSH_DOMAIN` defaults to `DOMAIN` (set per instance in custom-values: `git.scifi.farm` / `git.spencerslab.com`). `USE_COMPAT_SSH_URI` can force ssh:// URIs always.
- Clone-URL shape: scp-style `git@host:user/repo.git` carries no port; when the advertised port ≠ 22 the URL necessarily becomes `ssh://git@host:PORT/user/repo.git` (ssh(1) URI form `ssh://[user@]host[:port]` [13]; chart README: "This helm chart automatically configures the clone urls to use the correct ports" [9]). So the port appears in clone URLs exactly when `SSH_PORT != 22` — which every viable design here implies.
- Chart mechanics (forgejo 17.2.0, inspected locally [9]): `service.ssh.{type,port,nodePort,hostPort,externalTrafficPolicy,loadBalancerIP,...}` map 1:1 into the `<fullname>-ssh` Service; container port is always `SSH_LISTEN_PORT` (2222 rootless) with Service `targetPort: ssh` (named), so changing the **service port does not touch the container**. `_helpers.tpl` auto-sets `SSH_PORT ← service.ssh.port` **only if unset** — but the chart's own values.yaml already sets `gitea.config.server.SSH_PORT: 22`, so with a values deep-merge the auto-follow NEVER fires. **The plan must set `gitea.config.server.SSH_PORT` explicitly alongside any service port change** (and must NOT change `SSH_LISTEN_PORT`).
- Built-in SSH server: `START_SSH_SERVER` auto-true for the rootless image [9]. **Host keys**: `SSH_SERVER_HOST_KEYS` default `ssh/gitea.rsa` relative to `APP_DATA_PATH=/data`; auto-generated (4096-bit RSA) if absent [10] → keys live on the 10Gi `forgejo` PVC (`persistence.create: true`, `helm.sh/resource-policy: keep` [12]) → **key material survives redeploys; the "verify the assumption" flag from the coordinator resolves to: yes, persisted, and already generated on both live instances** (both have been running since the 2026-10 dev/infra buildout — assumption marked verified-by-docs, confirm-by-fingerprint at rollout is cheap).
- Chart guidance: "SSH and Ingress: ingress is not able to forward SSH Ports. You will need a LoadBalancer…" [9] — upstream concurs with the L4 conclusion.

### F5 — Client/DNS side

- **URL form**: clients move from scp-style to `ssh://git@host:PORT/...`; git handles the port natively (passes `-p` to ssh) [13]. Existing https remotes and CI/runner clones are untouched (runners use the http services [12]).
- **known_hosts**: keyed by the name the user typed; a change of *port* creates a separate `[host]:PORT` entry (first-connect prompt, one-time); a change of *IP behind the same name* causes no warning as long as the host key is unchanged (ssh verifies the key against the hostname entry) [13]. Here the target IP stays the node IP the host already resolves to → **continuity is good**; only clients that pinned the IP in known_hosts or that reconnect on port 22 (now: node sshd, wrong key) see warnings. Port-22→node-sshd confusion actually *decreases* once git moves to a distinct port.
- **Mesh DNS**: the git host records are user-owned split-horizon records; **no DNS change needed for a port move** (same host). Only a target-IP change (not proposed) would touch DNS.
- **`coder gitssh`** (dev workspaces): an ssh wrapper injecting the workspace's git key; it forwards normal ssh args incl. `-p PORT` (e.g. `coder gitssh -p 2222 git@server`) [14]. `ssh://` remotes with a port therefore work through it transparently; scp-form remotes to `git.scifi.farm` would keep hitting node sshd on :22 and fail auth — any coder templates/docs assuming port 22 need updating (a caveat, verified only via GitHub issue/discussion snippets [14]).
- Public-internet exposure is NOT implied by any of this: the lab's public edge carries only the autossh :443 HTTP tunnel → raw TCP SSH cannot ride it [12]. SSH here means mesh/LAN clients unless a new edge design is opened (open question).

## Contradictions & weighting

- **TCPRoute channel status**: Traefik v3.7 docs call TCPRoute "Experimental channel only" [1][2]; upstream gateway-api says TCPRoute is Standard since v1.6.0 [3], and k3s v1.36.5 ships it in the *standard* install bundle (live on dev) [6][11]. Weighting: the CRDs are unambiguously available via the standard bundle — but **Traefik's runtime gate is its own code**, so `experimentalChannel: true` is still required to make traefik *watch* TCPRoute. Plan for both: CRDs (present on dev, missing on infra) AND the provider flag.
- **k3s docs staleness**: the k3s Gateway-API section references gateway-api v1.4 and "install v1.4 experimental-install.yaml for TCPRoute" [5] — outdated for the running v1.36.x bundles (v1.5.1/v1.6.1) [6]. Live state + k3s-charts sources outweigh the doc paragraph.
- **`charts/traefik` wrapper appVersion 2.11.10** vs live proxy-local image v3.6.15 — stale metadata in the wrapper Chart.yaml; ignore appVersion, trust the image [11][12].
- **`traefik-config.yaml` header comment** "Pretty sure this just gets ignored when a custom Traefik chart is used instead" — true only for proxy-local (stock traefik disabled there); on dev/infra the HelmChartConfig IS the applied config surface (live args match it) [11][12].

## Implications for the plan (decision tree)

**Facts that constrain every option:** external port must be ≠ 22 (node sshd occupies :22 → ServiceLB Pending / hostPort bind fail) unless the user moves node sshd; `SSH_PORT` must be set explicitly in `gitea.config.server` (auto-follow is dead code once the chart default exists); SSH_PORT ≠ 22 ⇒ clone URLs switch to `ssh://host:PORT` form everywhere; host keys persist on the PVC; no DNS change needed; mesh-only reachability unless the user wants a new public-edge design.

1. **Recommended baseline — ServiceLB on the forgejo-ssh Service (non-22 port, e.g. 2222).**
   Changes: `charts/forgejo/values.yaml` → `forgejo.service.ssh: {type: LoadBalancer, port: <P>, externalTrafficPolicy: Local}` + `forgejo.gitea.config.server.SSH_PORT: <P>` (per-instance override still possible via custom-values if dev/infra should differ). No base-chart, no traefik, no CRD, no template changes. Precedent: proxy-local qbittorrent [11][12]. Verification: svclb pod + LB IP + `ssh -p <P> git@host` banner. Dead end variant: port 22 (Pending forever [5]).
2. **Alternative — traefik IngressRouteTCP on a dedicated entrypoint.** Add to `charts/base/templates/traefik-config.yaml`: entrypoint `gitssh` + `ports.gitssh` (exactly the existing `seaweedvolume` pattern [12]) on a non-22 port; one IngressRouteTCP per service umbrella routing to `<cluster>-forgejo-ssh:22`; same `SSH_PORT` override. Buys: traefik visibility/middleware surface (TCP middlewares CRDs exist [11]), uniformity with the HTTPS path. Costs: touches the cluster-wide base chart (affects ALL clusters — gate the entrypoint if it shouldn't appear everywhere, e.g. via a per-service values flag like `seaweedVolumePort`) + 2 new templates; one extra hop. Same port-22 dead end applies.
3. **Strategic only — Gateway + TCPRoute.** Requires: provider + experimentalChannel via HelmChartConfig (both clusters), decide chart-default Gateway/GatewayClass (enabled by default once provider on [6][7]), infra CRD gap (wait for k3s upgrade past v1.36.2, or install v1.6 standard/experimental CRDs by repo template — mind k3s traefik-crd ownership/`forceConflicts` and the remove-on-disable caveat [5][6][11]), then either forgejo chart `tcpRoute.enabled` with parentRefs (v1alpha2 — verify traefik accepts it) or a hand-written Gateway+TCPRoute. Still needs the same entrypoint+LB port plumbing as option 2 (listener port = entrypoint port [1]). **Adds nothing over option 2 for a single fixed port** (TCPRoute has no host matching; one listener = one route [3]). Choose only if the user wants Gateway API as the lab direction.
4. **Rejected:** NodePort (5-digit clone-URL port, no upside over ServiceLB which also allocates nodePorts internally); pod `hostPort` (chart supports `service.ssh.hostPort` [9], but it bypasses Service/traefik, couples pod lifecycle to a node port, and offers no benefit); anything on port 22 without moving node sshd.

Rollout order suggestion: dev instance first (its cluster already has the tcp CRDs and it's the throwaway instance), infra second; keep both instances' ports consistent to keep client muscle-memory/simple docs.

## Open questions (user-only)

1. **Port choice**: 2222? (note: proxy-remote's VPS edge already uses 2222 for its own sshd [12] — no collision on the mesh nodes, but matters if public SSH exposure is ever added through the edge; 2223/2200/etc. avoid future confusion.)
2. **Move node sshd off :22?** The only path to bare `git@host:22` clone URLs. Host-level, outside GitOps, lockout risk — explicit yes/no needed; default assumption: no.
3. **Public exposure**: mesh/LAN only (all options above), or also from the internet (requires a NEW edge design — the autossh :443 tunnel can't carry raw SSH [12])?
4. **Gateway API direction**: is Gateway+TCPRoute wanted strategically (option 3) or should the plan stay minimal (options 1/2)?
5. **Scope**: SSH on both instances (dev + infra) from day one, or infra-only first?
6. If option 2/3: should the new traefik entrypoint/port exist on ALL clusters (base chart is cluster-wide) or be gated to dev/infra only?
