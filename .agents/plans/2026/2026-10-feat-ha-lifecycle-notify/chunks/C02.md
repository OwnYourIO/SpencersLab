# C02: Approval-ask HA notifications on `permission.asked` (all sessions)
size: M   wave: 2   depends_on: [C01]

## Goal
Extend the question-notify plugin so that when ANY session — top-level OpenChamber
session or pipeline `agent-*` child — raises a permission approval ask (the agent
is blocked until the user approves the tool/privilege), the user's phone gets one
Home Assistant push titled "needs approval", reusing the existing subscribe loop,
per-session 15 s cooldown map, notify plumbing and 240-char excerpt contract from
C01. Question and lifecycle behavior stay exactly as shipped (the existing 35
tests must remain byte-identical and green).

Difference from C01 by design: NO topology filter here. A blocked session needs a
human no matter who started it; the lifecycle top-level-only suppression exists to
damp turn-end noise, which does not apply to rare, actionable approval asks
(DECISIONS 2026-10-26: scope-all-sessions).

## Tasks
- [ ] Export a second test seam from `.opencode/plugin/question-notify/index.ts`:
  `approvalTitle(agent)` → `OpenCode: <agent> needs approval`, `approvalExcerpt(data)`
  (pure precedence function below), and `handlePermission(deps, event)` (async, never
  rejects, same invariant as `handleLifecycle`).
- [ ] Excerpt precedence (intake #3; payload fields grounded in plan Grounding #8/#10/#11):
  1. `data.message` when a non-empty string;
  2. else `data.action` when a string → `"<action>: <r1, r2, r3>"` using at most the
     first 3 entries of `data.resources` (string entries only; empty/absent →
     just the action word);
  3. else the V1-compat twin — `data.permission` with the same join over `data.patterns`;
  4. else `"permission request"` (documented degrade; the event payload never carries
     a tool display name beyond action).
  Never render `metadata` (edit asks embed whole diffs in it — noise on a phone).
  Cap at 240 at the notify boundary via the existing `truncate`.
- [ ] Implement `handlePermission(deps, event)`: dispatch only on
  `event?.type === "permission.asked"`; resolve `sessionID` with the C01 dual read
  (`event.data?.sessionID ?? event.sessionID`), bail silently when absent; check the
  injected per-session cooldown gate BEFORE the session lookup; then
  `deps.getSession(sessionID)` for the agent name used in the title — a rejected
  lookup or missing agent degrades to the existing `"session"` label and STILL
  pushes (unlike lifecycle's suppress-on-unknown: no topology decision is needed
  and dropping the push is the worst outcome for an approval block — DECISIONS);
  notify once with `approvalTitle` + truncated `approvalExcerpt`. Swallow all
  errors to stderr like `handleLifecycle`.
- [ ] Share ONE cooldown gate with the question path: extract the setup-closure
  `lastNotified` Map test into a `const allowPush = (key) => ...` (same
  `COOLDOWN_MS`, same key namespace — sessionID) created once in `setup`, used by
  BOTH the existing `execute.before` question hook and the permission dispatch, so
  a question push and a near-simultaneous approval ask on the same session yield a
  single phone push (intake #2). Behavior in the question path is unchanged: same
  filter, same timing, same title.
- [ ] Route `permission.asked` events in the existing subscribe loop: each streamed
  event dispatches `handleLifecycle` as today AND `handlePermission` fire-and-forget
  (`void handlePermission(deps, event).catch(log)`), either order — the handlers
  self-filter on `event.type`. Extend the one-shot debug-log convention: first
  `permission.asked` event logs its envelope keys + `data` keys once (separate flag
  from `lifecycleDebugLogged`), mirroring the existing pattern so the user-owned
  smoke can confirm the real payload shape.
- [ ] Create `tests/opencode/permission-ask-notify.test.ts` covering the Tests list
  below. Do NOT touch `tests/opencode/question-notify.test.ts` — its md5 is an
  acceptance criterion.
