# C04: heartbeat & lifecycle engine — hooks, events, timers, lock-lost
size: L   wave: 3   depends_on: [C03]

## Goal

Keep live locks alive and let dead ones die: the heartbeat points of handoff
B.4 (tool hooks, child-session creation, execution started, 5-min timer,
manual beat), the subagent→root mapping (B.9), the failed/interrupted
lifecycle (D12), and lock-lost detection + signaling (B.6, D16) — all on top
of C03's store seams, all offline-testable through injected deps.
Human-stop policy per D20 (user ruling): NO waiting-detection machinery —
the clock keeps ticking through stop points; only executing sessions get
timer heartbeats, and an idle lock simply goes stale after `staleMs` (2 h,
D21) like any other.

## Tasks

- [ ] Session graph seam: `sessToRoot` cache + storage-backed
      `resolveRoot(sessionID)` with the deferred parent-walk (deferred
      `ctx.session.get` — NEVER inline in the event loop; negative results
      cached 60 s). Rebuild from `ctx.storage.scan` at setup (C01 shape).
- [ ] Heartbeat seam `heartbeatSet(rootID, source, force)`: beats EVERY lock
      file of the root's claim set (30 s throttle per pipelineKey unless
      force); per file: re-read, missing/stolen → lock-lost path; else
      rewrite atomic + utimes + audit sampling (1-in-10 non-forced beats
      logged, all forced).
- [ ] Lock-lost is SET-wide (D18): if ANY member file is missing or stolen,
      mark the whole claim lost — delete the surviving member files
      immediately (freeing those pipelines for other cards), clear
      maps/storage, pin the LOCK-LOST instruction, audit `lock_lost` with
      the set, NEVER recreate a file.
- [ ] Tool hooks: `execute.before`/`execute.after` → beat the caller root's
      set (skip `pipeline_*` tools themselves); the before-hook also carries
      the optional strict lock-lost guard (config `strictLockLoss`, default
      ON): throw `Error("PIPELINE LOCK LOST — stop; do not commit or move
      the card")` for `edit`/`write`/`bash` in a lock-lost session
      (throwing blocks the tool — C01 fact 2). No question/permission
      tracking of any kind (D20).
- [ ] Event subscription (no `types` filter — DECISIONS): dual-read
      envelope; `session.created|updated` with parentID → map child to a
      locked root (storage write + immediate force beat + audit
      `child_mapped`); `session.execution.started` → executing set + force
      beat; terminal events → clear executing; root failed/interrupted →
      `state:"failed"` in every member lock file + audit `exec_failed`
      (timer stops beating it; releaseOnFailure=true → immediate set release
      instead). ALL session reads deferred via `setTimeout(..., 0)` —
      handoff #55318. Location scoping: ignore sessions not in the
      graph/rootLock map (#58707-safe).
- [ ] Timers: beat timer (5 min default, config) over locks whose root or a
      descendant is currently EXECUTING (started seen, no terminal yet) —
      idle roots get nothing, which is exactly what lets human-stop and
      abandoned runs go stale (D20); reap timer (10 min) calling the C05
      reaper; both cleared in the cleanup fn together with the
      AbortController on the event stream.
- [ ] Instruction pin maintenance: claim pin `pipeline-lock` (C03) updated
      on lock-lost to the STOP message; removed on release (C01 fact 6
      fallback per D16 when absent).

## Acceptance criteria

1. `node --test tests/opencode/pipeline-locks-engine.test.ts` passes; core
   suite + the four pre-existing suites still green.
2. Throttle: 3 beats within 30 s (non-forced) on one pipeline → 1 file
   write; forced beats always write; a 2-pipeline set gets both files beaten
   (fake clock).
3. Lock-lost: one member file deleted under a live 2-pipeline claim → next
   hook logs `lock_lost` naming the set, DELETES the surviving member,
   clears the maps, signals STOP through the degraded channel
   (capability-gated instruction pin when present; on v2.1.4 the tool
   responses + strict execute.before guard are PRIMARY — D28), and never
   recreates a file; with strictLockLoss ON the before-hook throws for
   edit/write/bash and only those tools.
4. Child mapping: a `session.created` with parentID of a locked root maps
   the child + force-beats the set; a child of an UNLOCKED or unknown root
   maps nothing (location-isolation leg); a child first seen via
   `session.updated` behaves identically (dual-event coverage).
5. Idle-stale semantics (D20): a locked root with NO executing member
   receives zero timer beats (fake clock across one timer interval); after a
   `session.execution.started` it beats again — heartbeats resume with
   activity, no special state in between. Root failure: terminal
   non-succeeded event on the root sets `state:"failed"` in every member
   file and stops timer beats; with releaseOnFailure=true the set is
   deleted immediately instead. Child failures change nothing.
6. Grep ACs on the module: no `await ctx.session.get` (or storage read)
   textually inside the `for await` event-loop body; every event payload
   read is dual-read (`d?.x ?? d?.info?.x` shape); the subscribe call passes
   no `types:` key; ZERO occurrences of question/permission-wait tracking
   (`grep -c "question" index.ts` matches only comments if any).
7. Cleanup: the returned fn aborts the stream and clears both timers (test
   observes the abort signal + a fake clearInterval count).

## Findings

**MAJOR-1 — `handleLockLost` deletes member files it does not OWN (safety: destroys a live foreign
claim).** index.ts:499–505: the survivor-cleanup loop rm's EVERY path in `entry.pipelineSet`, including
the STOLEN trigger member. In the designed flow this file exists and belongs to a DIFFERENT healthy
claim (different sessionID, different setId, different card): the reap (C05) renames our file to
`.reaped/` (reap suite contract, tests line 31), another card claims the freed pipeline (O_EXCL — new
file at the same path), and the resumed ghost's next tool hook (D20's own "stops at its next PIPELINE
LOCK LOST signal" flow) classifies it `stolen` → `handleLockLost` rm's the NEW claimant's file → that
run's next beat sees `missing` → its whole set dies + guard stops it + Timeout/alert on a healthy run.
The suite pins deletion in its theft leg (engine test 303–312, `lockFiles(env) === []`), but that
fixture is OUR record with only `sessionID` swapped — the `setId` is unchanged — so an ownership-guarded
delete satisfies the pin AND the chunk's own wording ("delete the surviving MEMBER files", the ones
still ours; AC3: "DELETES the surviving member"). Fix: in the rm loop, re-read via
`checkMember(env, path, root)` and delete only when the file is missing (force no-op) or the record is
ours (`rec.sessionID === root || rec.setId === entry.setId` — the E2 fixture passes on the setId arm);
a foreign record → leave the file, `logNote` it (that pipeline is already freed — we own nothing there).
Reachability today is nil (no reaper until C05) but C04 owns this code — fix here, not as a C05
follow-up. No validation at fault: every current leg stays green under the fix.

**Minor-1 — manual heartbeat can report success on a skipped beat.** When any member verifies
`unreadable`, `heartbeatSet` skips the whole pass (558) and the claim survives — `toolHeartbeat`
(809–822) then sees the claim still present and returns `ok:true, beaten:set` although nothing was
written (transient EMFILE). Honest fix: have `heartbeatSet` return a per-set outcome
(`{beaten, skipped, lost}`) and let the manual response reflect skips. Non-blocking (self-heals next
beat; no state corruption).

**Minor-2 — the scan adapter (953) + rebuild loop (1056–1075) have zero offline execution.** E8's

one setup-level leg (fake storage with scan → claims/sessToRoot repopulated, malformed rows skipped)
