## Conventions

- Naming (card note 1): everything the handoff calls "ralph" ships as "pipeline" — plugin dir `.opencode/plugin/pipeline-locks/` (repo's hand-managed singular `plugin/` dir, NOT the handoff's `.opencode/plugins/ralph/`), plugin id `local.pipeline-locks` (the `local.<name>` id shape of the two shipped precedents), tools `pipeline_claim` / `pipeline_release` / `pipeline_heartbeat` / `pipeline_status`, commands `/pipeline-tick` / `/pipeline-reap` / `/pipeline-status`, runtime dir `.pipeline/` at the canonical repo root (`locks/`, `locks/.reaped/`, `timeouts.jsonl`, `events.log`, optional `config.json`), loop file `.agents/loops/pipeline-worker.md`.
- Reuse the repo's proven precedents instead of the handoff's from-scratch shapes (card note 1): plain-object plugin export `{ id, async setup(ctx) }` (NOT `Plugin.define` — the shipped plugins' working shape, pinned by tests/opencode/board-context.test.ts); raw MCP JSON-RPC for board + HA calls (question-notify + board-context); `node --test` seam-export test pattern (Node v26 type-strips .ts); the boards skill stays the single flow authority for board semantics.
- Event subscription without the `types` filter (opencode v2.1.4 installed; the handoff says the filter needs @opencode/plugin ≥ 2.2.0) — filter in code, question-notify precedent. Dual-read envelope (`event.data?.X ?? event.X`) for compat-twin tolerance.
- Board writes from the reaper go through the `dev-boards` MCP server (server-side login-mint; no credentials in the plugin); HA alerts through `admin-global-homeassistant` (the readonly ha-mcp rejects service calls) — both URLs discovered at runtime, never hard-coded (question-notify/ board-context precedent).
- One commit per chunk, made by the coordinator (code + tests + state together) — see D7.

- 2026-10-29 plan: D3 — the **Timeout** list is created by a human in the WeKan UI (swimlane "In Process"); the wekan-mcp surface has no `create_list` (source-checked 2026-10-29) and the boards skill's never-mutate posture plus the image-rebuild/redeploy cost rule out an in-run tool addition (OQ4; a follow-up card may add it). - 2026-10-29 plan: D4 — the `pipeline` custom field IS created through the `dev-boards` MCP `create_custom_field` as a card-authorized operator step during C07 (the card description explicitly requests the field; custom-field VALUES are already agent-written by the boards flow — slug/session — so field creation is the same surface one level up). ## Decisions (r2 — batched question round 2026-10-29; answers applied)

- 2026-10-29 plan r2: D17 (supersedes D2) — pipeline identity is board LABELS, not a custom field (user directive): a card's lock set = every label whose name starts with `Pipeline:` — the trimmed remainder of the label name is the pipeline/lock name; one card can block MULTIPLE pipelines. Labels are matched case-sensitively on the exact `Pipeline:` prefix; a `Pipeline:` label with an empty remainder is ignored; duplicates dedupe. Cards with NO matching label run on the single `default` pipeline (one-line constant `DEFAULT_PIPELINE = "default"` — this carries the user's earlier blank-field note).
- 2026-10-29 plan r2: D18 — the claim is ALL-OR-NOTHING over the set: `pipeline_claim(cardId, pipelines[], cardTitle?)` sorts the sanitized pipelineKeys, acquires sequentially with O_EXCL, and rolls back every lock already taken on the first contention (`{ok:false, reason:"locked", pipeline, holder}`) — consistent ordering means no deadlock between overlapping sets. Every lock file of a claim carries the shared identity: same `sessionID` + `cardId` + a per-claim `setId` (uuid) + the full `pipelineSet[]`, so release, status, reaper and alerts can correlate the set. Release deletes the whole owned set. Losing ANY member of the set (reaped/stolen) loses the WHOLE set: the engine deletes the surviving members immediately (freeing those pipelines) and signals PIPELINE LOCK LOST.
- 2026-10-29 plan r2: D19 (supersedes D4) — NO `pipeline` custom field is created; that operator step is retired entirely. Labels are human-owned on this board (the existing Research-label posture) — the human creates `Pipeline:<name>` labels in the WeKan UI; the plugin/worker only READS them: label ids on the card via dev-boards `get_card` (`label_ids`), names via `get_board` labels. wekan-mcp has no `create_label` tool either and this plan does NOT ask for one.
- 2026-10-29 plan r2: D20 (supersedes D5 — user REJECTED the keep-alive design) — human-stop policy: the clock keeps ticking while a run blocks on a human stop point. All question/permission-wait detection machinery is removed from the plan. If the user answers within the stale window, ordinary tool/turn heartbeats resume and the lock is fine; if the window passes, the lock goes stale and the reaper treats it like any other stale lock (reap → Timeout → HA alert). No special states, no release-at-stop, no re-claim dance — a run whose lock was reaped stops at its next PIPELINE LOCK LOST signal; a re-picked card is a fresh claim via the normal Resume-vs-new-run rule.
- 2026-10-29 plan r2: D21 — STALE WINDOW IS 2 HOURS, not 3 (user ruling): `staleMs` default `7200000`; the reaped card comment and HA alert texts say "no heartbeat for 2h"; loop cadence stays hourly (a 2h window spans two tick periods).
- 2026-10-29 plan r2: D22 (Q4 ruling) — the **Timeout** list creation is resolved via FOLLOW-UP CARD: the coordinator creates a card (list **Not Started**) requesting a `create_list` tool addition to `containers/wekan-mcp` so deterministic code can create/move-to the Timeout list itself. Until that follow-up lands, the reaper uses the `.pipeline/timeouts.jsonl` fallback + the card comment (C05 degrade). The card creation is a coordinator task recorded in C07 — not a plan/dev deliverable.
- 2026-10-29 plan r2: Q1 KEEP slug `cf-76-feat-parallel-pipeline-loops`; Q2 tick model = `openrouter/qwen/qwen3.8-flash` (C06 constant); Q3 commit-policy reading CONFIRMED (C02 stands); Q5 transition CONFIRMED (loop ships `enabled:false`, gate kept, user re-points after live smoke); Q7 `releaseOnFailure:false` CONFIRMED; Q8 `maxWorkers` DEFERRED confirmed (config key reserved). All r1 open questions are resolved — the plan carries no open questions.
