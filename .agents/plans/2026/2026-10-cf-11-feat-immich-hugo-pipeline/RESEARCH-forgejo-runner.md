# RESEARCH — Forgejo runner vs CronJob as the Immich→Hugo→Netlify orchestrator

Ticket: WeKan AI-Dev card #11 (`cf-11-feat-immich-hugo-pipeline`) · **Round 3 (isolated)** 2026-10-31 · fresh STORM audit, own source sequence `[1]…[55]` (independent of RESEARCH.md's numbering; prior-round findings are referenced **by name**, e.g. "RESEARCH.md R2.1 recommendation (d)").
Method: STORM (5 perspectives × grounded interviews; 55 sources, all pulled 2026-10-31; primary sources: Forgejo v17.0.1 docs source on Codeberg, live Forgejo v17 swagger, Forgejo Runner source/releases, Immich `main` OpenAPI spec + server/plugin source, official release blogs; practitioner reports used where primary docs are silent).

## TLDR (card-postable)

- **Verdict: the Forgejo runner route genuinely fits this user better than the standalone CronJob — as the pipeline SPINE — provided the runner pod gets a PVC and runs in `host` backend mode (no privileged DinD).** Since in-cluster Forgejo + runner are coming anyway, the marginal cost is one chart + one toolchain image, and it buys what a CronJob can't: `on: schedule` (hourly) **+** `on: push` ("when the files change") **+** `on: workflow_dispatch` (API-triggerable) in one workflow [1], an Actions UI with 365-day logs/rerun/cancel [3][7], and first-class checkout of the site repo.
- **Immich webhook reality (resolves the prior round's flagged weak spot): a native "Trigger Webhook" workflow action EXISTS, verified in server source** (PR #29258, shipped v3.0.0-rc.3 June 2026): POST/PUT a JSON `{type, trigger, data}` to any URL with one optional auth header [36][37][41][42]. **BUT** workflow triggers are still only `AssetCreate | AssetMetadataExtraction | AssetOcrExtraction | AssetTagged` — **there is NO album-changed trigger** (an "added to album" trigger was WIP "top of the list" in June 2026 and had not shipped as of v3.4.0-rc.0/main, 2026-10-31) [35][39][42][44][46]. So "Immich calls a Forgejo hook whenever an album changes" is **not natively possible today**.
- **Also, webhook→Forgejo-dispatch does NOT work directly**: Forgejo has no inbound generic-webhook trigger [6], and its dispatch API requires a JSON body with `ref` [7][10] which Immich's fixed webhook payload can't provide [37]. The working seams are: **(a)** runner-side hourly cron doing the incremental `updatedAfter`/`lastModifiedAssetTimestamp` pull (zero new parts), **(b)** a ~100-line in-cluster **shim** consuming Immich's socket.io `on_album_update` event (source-verified: emitted on every album add/remove/edit [48][49][50]) that debounces and calls `POST /api/v1/repos/{o}/{r}/actions/workflows/site.yml/dispatches` [1][7][10], and **(c)** an Immich `AssetTagged`+tag-filter→webhook workflow feeding that same shim for tag-curation latency. Recommend (a)+(push) as phase 1, (b) as phase 2; (c) optional sugar.
- **State make-or-break**: Forgejo's actions cache lives **on the runner's own disk** ("never sent to Forgejo") [3][19] and artifacts can't be read across runs (#8004) [2] — so the derivative library + `resources/_gen` + sync-state must sit on a **PVC mounted into the runner** (trivial with the `host` backend: `host.workdir_parent` + `cache.dir` on the PVC [18][19][55]). With that, state handling reaches CronJob+PVC parity; without it, the runner route is strictly weaker than the earlier RESEARCH.md CronJob recommendation.
- **Security caveat**: the common k8s runner shape is privileged Docker-in-Docker [20][27][28][29] — against this repo's hardening posture (VSHN paused a product over exactly this [31]). Native k8s job-execution exists only as an **alpha gRPC plugin protocol** (runner ≥13.1, "not production-ready", third-party plugins) [22][24][25][26]. A dedicated **host-backend runner pod** (jobs run directly in the pod; "no isolation" is acceptable when the only workflows are your own site repo's [18]) is the hardened-cluster sweet spot.
- **Keep the cron watchdog**: schedule triggers are the fragile leg of Actions-type systems (default-branch-only, DST skip/double-run documented [1]; real-world silent-disable reports [13][14][15][16]).

## 1. Forgejo Actions capabilities vs the CronJob shape

Current stable: **Forgejo v17.0.1** (2026-10-15); LTS: **v15.0.11** (EOL 2027-07-15); quarterly majors [8]. Forgejo Runner is versioned separately — current **v13.2.1** (2026-10-29) [23].

### 1.1 Schedule triggers — supported, with documented edges

- `on: schedule: - cron: '30 5,17 * * *'` works; the workflow must exist **on the default branch** (schedules on other branches/PRs are ignored); POSIX cron, UTC by default, optional `timezone:` IANA key (v16 also accepts the `CRON_TZ=` prefix syntax) [1][9].
- DST caveat, documented: runs scheduled during a spring-forward jump are **skipped**; fall-back runs **twice** [1].
- Scheduling is a server-side per-minute task in the Forgejo instance (not the runner) [14]; a job then waits for a matching runner label — if no runner with the label is online, the run **hangs until one appears** [1].
- Fragility evidence (weigh, don't panic): Forgejo fixed a bug where one corrupted scheduled workflow broke scheduling for all (v12: now only the bad one is disabled) [15]; Gitea-lineage report of schedules not firing while dispatch worked (empty `event.schedule`) [14]; Codeberg (downstream fork) had recurring silent schedule disabling [13]; GitHub disables public-repo schedules after 60 days' inactivity and may drop runs under load [16]. No documented Forgejo inactivity-disable, but the pattern across the ecosystem says: **monitor the schedule** (an external watchdog that dispatches if no successful run in N hours closes the gap completely).
- No documented catch-up for runs missed while the instance was down (same as GitHub's behavior) [16].

### 1.2 Manual/API triggers — `workflow_dispatch` is first-class

- Workflow side: `on: workflow_dispatch` with typed inputs (`choice`/`boolean`/`number`/`string`, `required`/`default`/`description`) rendered in the UI or read from the API request body [1].
- API side (verified in the live v17 swagger): **`POST /api/v1/repos/{owner}/{repo}/actions/workflows/{workflowfilename}/dispatches`**, body `DispatchWorkflowOption`:
  - `ref` — **required**, git ref the workflow runs on [7][10]
  - `inputs` — string map matching the workflow's declared inputs [7]
  - `return_run_info` — bool (default false): returns the created run's info — useful for a shim to log/track what it triggered [7]
- Auth: standard token auth — `Authorization: token <PAT>`; a working curl example is in Forgejo issue #4765 (`--json '{"ref":"main"}'`) [10]. PAT scope: Forgejo has **no dedicated `actions` scope**; the dispatch route is a `/repos/*` route → **`write:repository`** scope suffices (GitHub, by contrast, wants `actions:write`) [12][17].
- Version gate: the dispatch API appears in the v11.0 docs and is absent from v9/v10 docs → **requires Forgejo ≥ v11 (Apr 2025)**; any supported version today (v15 LTS / v16 / v17) has it [8].
- Historical bug worth knowing: `push` triggers were once ignored when `workflow_dispatch` was also declared — fixed and backported through v7–v9; combining triggers in one workflow is reliable on current versions [11].
- Run-management APIs also exist (list/get runs, cancel run, rerun job, download job logs, list/download/delete artifacts, `GET /actions/run`) — added/expanded in v16 [7][9].

### 1.3 Repository webhook model — outbound only; dispatch is the inbound seam

- Forgejo webhooks are **outbound**: repo/org/system events (push, issues, releases…) POSTed to a payload URL (Forgejo/Gitea/Gogs JSON formats, chat integrations) [6]. There is **no inbound generic-webhook trigger** and no `repository_dispatch` equivalent found in docs or swagger [1][6][7].
- Therefore an external "album changed" ping has exactly three sanctioned inbound seams: **(1)** the dispatch API above (the right one), **(2)** a git push (e.g. commit a dirty-flag file — note pushes authored with the automatic `FORGEJO_TOKEN` never trigger workflows, which both prevents loops and means automation must use a PAT to trigger via push) [5], **(3)** issue/PR events (abuse, not recommended).

### 1.4 Runner provisioning on Kubernetes

- **No official k8s installer or chart**: official install docs cover binary, Docker container, and distro packages only [3][20]. Core runner backends: `docker` (incl. podman), `lxc`, and `host` (no containerization — docs warn "a single job can permanently destroy the host") [18]. The runner source on `main` has **no Kubernetes backend** (checked tree + go.mod, 2026-10-31) [19][23].
- **Community k8s shapes (2026)**:
  1. **DinD sidecar charts** — wrenix/forgejo-runner (ArtifactHub 0.7.6, runner appVersion 12.7.3, OCI-published from Codeberg) [27]; deployed as runner + `docker:dind` containers in one pod, **privileged** [28][29]; official compose docs use the same privileged-DinD pattern [20]. dtechvision's chart offers a `kubernetesBackend` toggle but pins runner appVersion 6.4.0 and writes a `container.mode: kubernetes` config key that doesn't exist in the current runner config schema → treat as stale [19][30].
  2. **Native k8s via the experimental plugin engine** — runner **v13.1.0 (2026-08-31)** added a gRPC execution-backend protocol (`plugin.v1alpha`: Create/Start/Exec/CopyIn/CopyOut/Remove); the Forgejo team explicitly labels it experimental/alpha and "not fully committed" [22]. Third-party plugins: sjones512/forgejo-runner-kubernetes (MIT, targets runner v13.2.0; one ephemeral Pod per job, steps streamed via `pods/exec`; **no** service containers, docker-based actions, or persistent workspace (emptyDir only); job image must contain sh/bash/tar (+node for JS actions); **no gRPC auth → NetworkPolicy mandatory**; "production use is not recommended") [24], and eleboucher's runner-k8s-plugin (chart 13.2.1) [26]. Upstream rejected merging a core k8s backend in favor of this plugin architecture [25].
  3. **Production practitioner report** (Simon Shine, 2026-10-25; 54 tasks over 2 weeks): runner 13.2.0 + eleboucher plugin as a native sidecar; jobs become `batch/v1` Jobs (`restartPolicy: Never`, one job per node via required anti-affinity, capacity 1×3 replicas); leaving DinD cut jobs 266s→126s and 294s→227s; the real driver was **cgroups**: privileged dockerd placed job containers outside `kubepods` with `memory.max=max`, and Talos's OOM controller killed Cilium instead of the build; namespace still labeled `pod-security: privileged`; registration via `forgejo-cli actions register` into a Secret (idempotent reattach); rough edges: alpha protocol, one 13-minute instance-wide `FetchTask` panic caused by copying an Actions-secret DB row (ciphertext bound to row id), log noise; idle footprint ~20Mi + 15Mi + ~1m CPU per replica [26].
- **Security posture for this lab**: DinD needs `privileged: true` — directly against the repo's drop-ALL-caps hardening rule; VSHN paused their managed-runner product precisely because "running privileged pods on a shared cluster cannot be made safe without additional infrastructure changes" [31]. For a runner serving **one trusted site repo**, the **`host` backend in a dedicated runner pod** needs no privilege at all: jobs execute as processes in the pod, and PVC mounts give persistent workdir/cache [18][19]. (Docker-using workflows are then off the table — this pipeline needs none.)
- Runner polls the instance every ~2s (`fetch_interval`) — no inbound ports on the runner; it only needs egress to the Forgejo API [19]. Registration tokens are available via API at instance/org/repo level (`GET …/actions/runners/registration-token`), so GitOps-able bootstrap is possible; a **repo-scoped runner** (registered to just the site repo) is the least-privilege shape [7].

### 1.5 Secrets & variables

- Encrypted key/value secrets at **repo, user, and org** level (UI: `/{owner}/{repo}/settings/actions/secrets` etc.; stored encrypted in the Forgejo DB; write-once — values can never be displayed or edited after set); exposed as `${{ secrets.KEY }}`; non-secret `vars` likewise [5].
- Full API CRUD: `PUT/DELETE /repos/{o}/{r}/actions/secrets/{secretname}`, org equivalents, variables endpoints [7] → Bitwarden can stay the source of truth with a one-shot seeding job (fits the repo's ExternalSecret+Bitwarden rule better than manual UI entry).
- Automatic token: `FORGEJO_TOKEN` (aliased `GITHUB_TOKEN`), repo-scoped write, and an **anti-recursion rule**: no workflow is triggered by changes authored with it [5].
- Runner v13 removed the `DOCKER_USERNAME`/`DOCKER_PASSWORD` registry-auth hack → private job images need `container.credentials` in the workflow [1][21].

### 1.6 Cache & artifacts — the decisive fine print

- **Cache is runner-local**: "The cache is stored by the runner itself and never sent to Forgejo" [3]. `actions/cache` (data.forgejo.org mirror) works, with repo-scoped keys (runner ≥6.3), optional zstd, and an **external cache server** option (`cache.external_server` + shared secret) for multi-runner sharing [2][19]. Default location `$HOME/.cache/actcache` → **on k8s this directory must be on a PVC** or cache is lost on every pod reschedule [19]. If the runner has caching disabled, `actions/cache` fails with a misleading "only supported on GHES >= 3.5" error [2]. No documented size cap or eviction contract — "caching makes no guarantees that a cache will be populated" [2] → a multi-GB derivative library on cache alone is best-effort.
- **Artifacts**: server-side, 90-day default retention (`ARTIFACT_RETENTION_DAYS`), storage backend configurable incl. **S3-compatible (minio)** via `[actions.artifacts]`/`[storage]` [3][4]. **But artifacts cannot be accessed from other workflow runs (open issue #8004)** [2] → artifacts are unfit as cross-run state; S3 artifact storage helps server disk, not pipeline state.

### 1.7 Containers/tooling on runners — custom image is the standard pattern

- Jobs run in the label's default image (`label:docker://image`) or a per-job `container.image` override (with `credentials`, `entrypoint`, `volumes` restricted to the runner's `valid_volumes` allowlist, `options` incl. `--memory` on runner ≥11.2) [1][18][19].
- Images once pulled are **never auto-updated** → pin digests; "many actions require node to run" (e.g. `actions/checkout@v7`) → the job image must include Node [1][18].
- For this pipeline's toolchain: base on **hugomods/hugo** (the maintained successor to the stale klakegg/hugo; extended edition; CI variants bundling Node/npm/Git; multi-arch; rebuilt within hours of Hugo releases) [32][33], add **netlify-cli** (Node ≥18.14; Netlify's CI guidance is a local dev-dependency install + lockfile + Renovate) [34], plus `git`, `zstd` [2], and `curl`/`jq` for the sync glue. In **host-backend mode**, bake all of it into the runner pod image itself (runner binary + toolchain), since jobs share the pod's filesystem [18].

## 2. Immich webhook reality (the crux)

### 2.1 v3 Workflows architecture — actions are WASM plugin methods

Workflows (preview since v3.0.0, UI at Utilities → Workflows) chain **trigger → filters → actions**; API-manageable (`/workflows`, `/workflows/{id}`, `/workflows/triggers`, `/workflows/{id}/logs`, `/workflows/{id}/share`) [35][43]. A step is `{method: "<plugin>#<name>", config: {...}, enabled}` — executed by WASM plugins (extism) loaded into the server; methods needing network/DB access must declare `hostFunctions: true` and an `allowedHosts` list, both **enforced server-side** ("Calling host functions is not allowed without setting methods[].hostFunctions=true…", "Hostname did not match any listed in methods[].allowedHosts…") [35][38][40]. Available host functions: `searchAlbums`, `createAlbum`, `addAssetsToAlbum(s)`, `httpRequest`, `bulkTagAssets` [38].

### 2.2 The webhook action — EXISTS, source-verified (resolves RESEARCH.md's flagged low-confidence item)

The built-in `immich-plugin-core` (v2.0.1 on main) ships method **`webhook` — "Trigger Webhook: POST/PUT event data to any URL"**, `hostFunctions: true`, `allowedHosts: ["*"]`, config schema `{url (required), headerName, headerValue, method: POST|PUT}` [36]. Implementation: `httpRequest(url, {method ?? POST, body: JSON.stringify({type, trigger, data}), headers: {'Content-Type': 'application/json', [headerName]: headerValue}})` — **fire-and-forget, no retry/backoff, exactly one optional custom header** (enough for `Authorization: token …` or a shared-secret header) [37][42]. Landed as PR #29258 (`feat: webhook workflow action`) in v3.0.0-rc.3, June 2026, incl. the server migration adding per-method `allowedHosts` [41][42][43]. The June recap frames it exactly as push-vs-pull integration [42]. The workflow event payload (`data`) is the asset context (`AssetV1`) with the trigger name and workflow/step ids [39].

### 2.3 Trigger surface — and the album gap

- `WorkflowTrigger` (SDK source + OpenAPI spec v3.4.0-rc.0 on main, fetched 2026-10-31): **`AssetCreate | AssetMetadataExtraction | AssetOcrExtraction | AssetTagged`** — with `PersonRecognized`/`AssetPersonV1` present-but-commented-out in source [35][39].
- **No album trigger of any kind.** jrasm91 (June 2026): "I am currently working on an 'added to album' trigger… the biggest issue right now is the album asset table is often very high volume, so it's taking a bit of time to add some bulk capabilities into the workflow engine… album events are super important for many workflows, which is why it is on the top of the list" [42]. Sept/Oct 2026 recaps and v3.1–v3.3 release notes shipped person-sharing, album editor improvements, and workflow step fixes — **no album trigger** [44][45][46].
- Core-plugin filters can't substitute: filename/timezone/location/date/type/**tags**/EXIF/OCR — **no album-membership filter** [36]. Practical native signals for a publish pipeline: `AssetTagged` + `assetTagFilter` (e.g. tag `web`) → webhook (fires on curation acts); `AssetCreate` → webhook (fires on **every** upload — phone-backup storms; no way to scope to an album) [36][39].
- Album-level change detection stays API-side: `GET /albums` `lastModifiedAssetTimestamp`/`assetCount` probes and `POST /search/metadata {updatedAfter}` (RESEARCH.md A1/R2.3 verified findings) [35].

### 2.4 General webhook feature request #13181 — still open, direction confirmed

Discussion #13181 ("Expand the notification system with webhooks", Oct 2024) is **still open** at 2026-10-31 (latest comment Feb 2026). Maintainer bo0tzz's steering: "There's already a system in place to send websocket messages for events… more likely that we expand this system to cover more events and support sending them out on a webhook, rather than adding webhook support to the notification system" [47]. The v3 workflow webhook action is the de-facto realization of that direction for asset events; album events remain the open frontier [42][47].

### 2.5 socket.io events API — the real album-event seam (source-verified)

- NestJS socket.io gateway at **`/api/socket.io`** (websocket transport only) [48].
- `ClientEventMap` includes **`on_album_update: [albumId]`** plus asset events (`on_upload_success`, `on_asset_update/delete/trash/restore/hidden/stack_update`), `on_notification`, and V2 sync events [48].
- Relay chain, verified in source: `album.service.ts` emits internal `AlbumUpdate {id, userIds, recipientIds}` on **album metadata update, bulk asset add, and asset remove** [50][52] → `NotificationService.@OnEvent('AlbumUpdate')` → `websocketRepository.clientSend('on_album_update', userId, albumId)` to **each album user's room** (clients join a room named by their user id) [48][49].
- Auth: the gateway handshake runs `client.request.headers` through the **same `authService.authenticate` as the HTTP API** (`uri: '/api/socket.io'`, non-admin, non-shared-link) [51] → an in-cluster Node shim can connect with standard Immich credentials in handshake headers (`extraHeaders`). Whether `x-api-key` is accepted on the socket handshake specifically is the expected behavior of that shared stack but was **not** found documented — spike-verify; fallback is a login-JWT/cookie session (Open question 4).
- This covers **exactly the user's ask** ("Immich calls a hook whenever an album is changed") one layer removed: Immich pushes `on_album_update` to any connected client of the album's owner; the shim turns it into a debounced Forgejo dispatch. Note it fires for membership AND metadata edits (rename/description) — the shim's dirty-set + the sync job's own diffing absorb that naturally.

### 2.6 Community bridges

- **No native n8n Immich trigger node** exists; community Immich workflows (e.g. the couple-album template) are schedule/poll + HTTP-request based, and practitioner API guides still teach 5-minute polling loops with "Immich doesn't have native webhooks yet" framing (pre-v3 or ignoring the preview) [53][54]. n8n remains usable as a shim host (Webhook node receiving the Immich workflow webhook, or a schedule node), but adds no capability over a small dedicated shim — and the lab already runs n8n if a no-code surface is preferred (RESEARCH.md "Adjacent" noted the same).
- No maintained socket.io-listener bridge tool found; the shim is greenfield but ~100 lines (socket.io-client + debounce + fetch to the dispatch endpoint).

## 3. End-to-end trigger architecture options

| # | Shape | Components | Auth | Failure modes | Verdict |
|---|---|---|---|---|---|
| **(i)** | Immich workflow webhook → Forgejo dispatch API **directly** | Immich workflow only | PAT (`write:repository` [12]) in the webhook step's header config | **Payload mismatch is fatal**: dispatch requires body `{ref}` [7][10]; Immich posts fixed `{type,trigger,data}` [37] → 4xx. Also PAT visible in Immich workflow config (not a secret store); per-asset bursts; only asset triggers exist [39] | **Does not work as imagined** — no translating receiver |
| **(ii)** | In-cluster **shim**: socket.io listener (`on_album_update`) and/or webhook-receiver endpoint → debounce (5–15 min trailing) → `POST …/dispatches {ref:"main", inputs:{albums}, return_run_info:true}` | Shim Deployment (~100 LOC) + PAT secret + (for webhook leg) Immich workflow | Immich API key/JWT on the socket handshake [51]; Forgejo PAT [10][12] | Shim down = missed events (cron leg backstops); Immich restart drops sockets (reconnect); socket x-api-key acceptance needs a spike; bursts handled by debounce + workflow `concurrency` group [1] | **The event-driven winner**; only way to get album-level push today [48][49][50] |
| **(iii)** | **Runner-side cron only**: hourly `on: schedule` workflow does incremental pull (`updatedAfter` + per-album `lastModifiedAssetTimestamp` probes); `on: push` covers "files changed" | None beyond the workflow | Immich API key as repo secret [5] | Schedule fragility (§1.1) [1][13][14][16]; freshness floor = cadence; wasted runs when nothing changed (cheap: probe-then-exit) | **The phase-1 spine** — zero new moving parts |
| **(iv)** | Debounced album-dirty **flag** + cron pickup (shim only writes a flag; next cron run consumes it) | Flag store (file in repo via API / Netlify Blob / KV) + cron | Same as (ii)+(iii) | Strictly more complex than (ii) on Forgejo — dispatch **is** the debounced pickup; flag-store becomes a second state surface; FORGEJO_TOKEN pushes don't re-trigger (anti-recursion) so a PAT is needed for push-based flags [5] | Skip |

**Recommended composite**: (iii) spine + `on: push` + `on: workflow_dispatch` in one workflow, with `concurrency: {group: deploy, cancel-in-progress: false}` so runs queue rather than race [1]; add (ii) in phase 2 for album-level near-realtime; optionally feed (ii) from an `AssetTagged`+`webhook` workflow for tag-curation latency [36][39][42]. Watchdog: external alert (HA/Grafana/OpenChamber) if no successful run in ~2× cadence — neutralizes the schedule-fragility class entirely [13][14][16].

**Versus the original CronJob recommendation** (RESEARCH.md R2.1 (d)): the runner route wins where the user suspected — schedule+push+dispatch duality in one declarative file [1], native repo checkout, Actions UI/logs (365-day retention, rerun/cancel APIs, job summaries) [2][3][7], encrypted repo secrets [5], and an inbound event seam (dispatch) that a CronJob fundamentally lacks (a CronJob can only be re-shaped into event-driven mode by adding a shim that creates Jobs or flips flags — i.e., building a worse dispatch). The CronJob wins on: fewest moving parts, an unprivileged vanilla pod (no DinD, no runner-version coupling — note runner v13's breaking removals [21]), PVC state as a first-class citizen, and no dependency on Actions-scheduler health [13][14][15][16]. Since Forgejo+runner are arriving anyway, the balance tips clearly to the runner — with the two conditions below (PVC-backed state; no privileged DinD).

## 4. State & idempotency between runner runs

What must persist: the derivative library (~200–500 MB at settled scale, RESEARCH.md R2.1 math), Hugo's `resources/_gen` cache [55], and the sync-state cursor (last-run `updatedAfter`, per-album `lastModifiedAssetTimestamp` — small JSON).

| Option | Mechanism | Durability | Fit |
|---|---|---|---|
| **PVC + `host` backend** | Jobs run in the runner pod; `host.workdir_parent` + `cache.dir` on a PVC; hugo project (incl. `resources/_gen`) and derivative library as plain directories [18][19][55] | PVC = CronJob-grade | **Best** — identical state model to the earlier CronJob+PVC design; single-writer by construction (capacity 1) |
| PVC + docker backend `valid_volumes` | Allowlist the PVC mount in runner config; job `container.volumes` mounts it [1][19] | PVC | Good; DinD privilege caveat applies [20][31] |
| `actions/cache` only | Runner-local `cache.dir` (default `$HOME/.cache/actcache`); repo-scoped keys; zstd [2][19] | **Best-effort** — "makes no guarantees"; lost on pod reschedule without a PVC; no documented size cap | Fine for `resources/_gen`/deps; **not** for the derivative library as sole store |
| External cache server | `cache.external_server` + shared secret [19] | Depends on backing store | Only needed for multi-replica runners; overkill here |
| Artifacts (incl. S3/minio backend) | Server-side, 90d [3][4] | Durable but **unreachable cross-run (#8004)** [2] | Unfit for state; OK for build outputs/diagnostics |
| State committed to the repo | `FORGEJO_TOKEN` push (won't re-trigger workflows [5]) | Git-durable | Good for the **cursor JSON** (auditable history); useless for media |
| Netlify Blobs | RESEARCH.md R2.1 (d) finding | External KV | Still available as an off-cluster cursor backup |

**Idempotency** is unchanged from the settled design: content-hash filenames (`{assetId}-{checksum8}`) + Netlify's digest-based `deploy --prod --no-build` make re-runs and overlapping windows safe (RESEARCH.md R2.1 (d)/R2.3 findings). Concurrency: `cancel-in-progress: false` + capacity-1 runner = strictly serialized deploys; Forgejo concurrency itself is "best-effort" [1] — the runner's single-slot capacity is the real guarantee.

**Make-or-break vs CronJob+PVC**: with row 1 (or 2) the runner route **matches** the CronJob's state story; with cache-only state it is **worse**. Everything hinges on giving the runner pod a PVC — which is natural in a bjw-s chart (`persistence` + `globalMounts`) and is the one non-negotiable of the runner design.

| Secrets | Forgejo encrypted secrets (repo/org), API-seedable from Bitwarden [5][7] | ExternalSecret+Bitwarden (repo standard, single bookkeeping) | Split — worst of both |
| State (library/_gen/cursor) | PVC on runner (host backend) = parity; cache-only = weaker [2][3][19] | PVC first-class, trivial | Either |
| K8s security posture | host backend: clean; DinD: **privileged** (against lab policy) [20][31]; native-k8s plugin: alpha [22][24] | Unprivileged vanilla pod (drop ALL caps) | CronJob side cleaner |
| Moving parts | Forgejo + runner + toolchain image (+shim phase 2) | CronJob + image | Most |
| Version coupling | Forgejo quarterly majors [8]; runner v13 broke `set-output` etc. [21] | None beyond base images | Both |
| Netlify deploy | `netlify deploy --prod --no-build` in workflow (digest upload — RESEARCH.md R2.1 (d)); Netlify git-build integration does NOT support self-hosted Forgejo → CLI is mandatory | Same CLI leg | Same |
| Marginal cost for this user | ~1 chart + 1 image (Forgejo/runner coming anyway) | 1 chart + 1 image | 2 charts |

**Hybrid note**: a "CronJob engine + Forgejo front" split duplicates secret/state plumbing across two systems for no capability gain; the honest choice is runner-pipeline (recommended, conditions below) vs the original CronJob (still perfectly valid if Forgejo slips or DinD-only proves unavoidable on the target cluster).

## 6. What it would take — component list (runner route)

1. **Forgejo instance** (user-owned prerequisite): ≥ v15 LTS recommended (dispatch API needs ≥ v11 [8][12]); Actions enabled (default since v1.21) [3].
2. **Site/pipeline repo on Forgejo**: Hugo config/templates/content (text-only; images never in git — RESEARCH.md R2.1) + `.forgejo/workflows/site.yml`:
   `on: {push: {branches:[main], paths:[...]}, schedule: [{cron: '17 * * * *'}], workflow_dispatch: {inputs: {albums, force}}}`; `concurrency: {group: deploy, cancel-in-progress: false}` [1]; job `runs-on: <runner label>`; steps: checkout → sync (probe albums, `updatedAfter` pull, `size=preview` derivatives — RESEARCH.md R2.3 call chain) → `hugo --gc` → `netlify deploy --prod --no-build` (CLI leg: RESEARCH.md R2.1 (d)) [34].
3. **Runner deployment** (new `charts/forgejo-runner` per repo conventions, or wrap the wrenix chart [27]): **recommended shape = dedicated pod, `host`-backend label, no docker/dind** [18]; bjw-s `persistence` PVC mounted at the runner's `host.workdir_parent` + `cache.dir` [19]; resources sized for hugo builds (≈1 CPU/1–2Gi burst); registration token from ExternalSecret (API-issued [7] or `forgejo-cli` flow [26]); repo-scoped registration for least privilege [7]. DinD variant only if docker-based workflows become a need (accept privileged + isolated namespace [20][31]); native-k8s plugin variant: watch, don't adopt (alpha) [22][24][26].
4. **Toolchain image** (`containers/` per repo conventions): forgejo-runner binary (pinned, Renovate) + hugomods/hugo extended base [32][33] + Node ≥18.14 + netlify-cli (dev-dep + lockfile style) [34] + git, zstd [2], curl/jq. Host-backend mode ⇒ everything in one image; docker mode ⇒ runner image + separate job image via label `container.image` [18][1].
5. **Secrets**: Forgejo repo secrets `IMMICH_API_KEY` (least-privilege key: `asset.read/view`, `album.read`, `tag.read` — RESEARCH.md R2.3), `NETLIFY_AUTH_TOKEN`, `NETLIFY_SITE_ID` [5]; seed via `PUT …/actions/secrets/…` from Bitwarden values to keep one source of truth [7].
6. **Phase-2 shim** (optional, small Deployment): socket.io client on `/api/socket.io` (auth per spike, Open question 4) listening `on_album_update` [48][49][51] + optional HTTP receiver for `AssetTagged`→webhook workflows [36][37][42]; trailing debounce 5–15 min; `POST …/dispatches {ref:"main", inputs:{albums:"<ids>"}, return_run_info:true}` with PAT (`write:repository`) [7][10][12]; reconnect-with-backoff; health probe.
7. **Immich workflow (phase 2, optional)**: trigger `AssetTagged`, step `assetTagFilter {tags:[web], matching:any}`, step `immich-plugin-core#webhook {url: shim, headerName: X-Webhook-Secret, headerValue: …, method: POST}` [36][37][42].
8. **Watchdog**: alert if no successful `site.yml` run in 2× cadence (Grafana/HA; run status via `GET …/actions/runs` [7]) — covers the schedule-fragility class [13][14][16].
9. **Repo integration trio**: chart entry + ApplicationSet values entry + proxy entry (Forgejo UI/runner are internal; proxy only if externally reachable) + `custom-values/` for Bitwarden UUIDs — per helm-chart-creation conventions.
10. **Renovate**: pins for runner image, toolchain image, hugo/netlify-cli versions [21][34].

## 7. Contradictions & weighing

1. **"Immich has no native webhooks"** (practitioner guides [53][54]) vs **webhook workflow action shipped v3.0.0-rc.3** (primary: [36][37][41][42][43]) → primary wins; secondary sources are pre-v3 or ignore the preview feature. The real limitation: asset-trigger-scoped only [35][39].
2. **"Runner has a Kubernetes backend"** (dtechvision chart [30]) vs **no k8s in runner core** [18][19][23][28] vs **alpha plugin protocol** [22][24][25][26] → the chart is stale (appVersion 6.4.0, config key absent from the current schema [19]); truth = core backends docker/lxc/host, k8s-native only via experimental plugins.
3. **Schedules "just work"** [1] vs **silent-disable/missed-fire reports** [13][14][15][16] → supported feature, fragile leg; mitigate with watchdog + dispatch fallback.
4. **Cache parity with GitHub** [2] vs **"cache is stored by the runner itself"** [3][19] → clarification, not contradiction: cache durability = runner-disk durability; PVC or external cache server required for anything precious; guarantees are best-effort [2].
5. **Socket handshake auth** — shared auth stack implies API-key/JWT acceptance [51] vs ambiguous community hints → spike-verify (Open question 4).
6. **User's mental model "Immich calls a Forgejo hook on album change"** vs reality → three independent blockers, each source-verified: no album trigger [35][39][42], no Forgejo inbound-webhook trigger [6], and webhook-payload/dispatch-body mismatch [7][37]. The shim architecture (§3 ii) is the faithful implementation of the user's intent.

## 8. Implications for the plan

1. **Switch the orchestrator recommendation** from standalone CronJob (RESEARCH.md R2.1 (d)) to the **Forgejo-runner pipeline** with two hard conditions: (a) PVC-backed runner state (§4), (b) no privileged DinD — host backend preferred (§1.4). The Netlify leg (`deploy --prod --no-build`, digest upload, Image CDN URL emission) and the sync logic (search/updatedAfter/derivative pull, hash-stable filenames) carry over **unchanged** from RESEARCH.md R2.1/R2.3 — only the vehicle changes.
2. **Phase the trigger legs**: phase 1 = `schedule` + `push` + `workflow_dispatch` (no shim, no Immich-side config); phase 2 = socket.io shim (+ optional `AssetTagged`→webhook workflow); phase 3 (free upgrade) = swap the shim's album polling for Immich's native album trigger **when it ships** (WIP, "top of the list" [42]) — the workflow itself never changes.
3. **Netlify git-build integration is off the table** for a Forgejo-hosted repo (Netlify supports GitHub/GitLab/Bitbucket) → the CLI-deploy leg is mandatory, not just preferred (named finding; consistent with RESEARCH.md R2.1 (d) which already made the CLI primary). PR-preview deploys, if wanted, are runner-side draft deploys.
4. **Secrets bookkeeping**: keep Bitwarden as source of truth; seed Forgejo repo secrets via API in a one-shot job or documented runbook (§6.5) — record this as a DECISIONS.md convention deviation-with-reason.
5. **Runner chart**: build `charts/forgejo-runner` (bjw-s, host backend, PVC, ExternalSecret registration token) rather than adopting DinD community charts wholesale — matches repo conventions and the hardening posture (§1.4, §6.3).
6. **Watchdog is part of the plan**, not an afterthought (§6.8) — it is the mitigation for the only genuinely worse-than-CronJob property of the runner route (schedule fragility).
7. **Upgrade discipline** extends to two more versioned surfaces: Forgejo quarterly majors [8] and runner majors with breaking changes (v13 removed `set-output`/`set-env`/`add-path` and DOCKER_* registry auth) [21] — pin both, Renovate both.

## 9. Open questions (best-guess answers + impact)

1. **Which cluster hosts Forgejo (and thus the runner)?** Best guess: **home** cluster — next to Immich (webhook/socket latency, in-cluster DNS) and the existing media workloads. Impact: chart category (`services/home/prod/`), proxy entries, network reach for the shim. (Card checklist lists gpu+home services.)
2. **DinD vs host backend vs waiting for the plugin engine?** Best guess: **host backend, dedicated runner pod, single trusted repo** — only shape that satisfies the repo's security posture without alpha software [18][22][31]. Impact: if the user wants docker-building workflows on the same runner later, a second (DinD, isolated-namespace) runner must be added.
3. **Forgejo version to deploy?** Best guess: **v15 LTS** (EOL 2027-07) or current v17 stable; dispatch API needs ≥ v11 — no constraint either way [8][12]. Impact: LTS = fewer quarterly upgrade churns for a homelab.
4. **Does the socket.io handshake accept `x-api-key`?** Best guess: **yes** (handshake headers flow through the same `authService.authenticate` as HTTP routes [51]) but undocumented; a community hint suggests API keys were rejected in a mobile-client context. Impact: shim credential design (API key vs login-JWT session refresh); verify in a 30-minute spike before building the shim; fallback works either way.
5. **Wait for Immich's native album trigger instead of building the shim?** Best guess: **build phase 1 now (cron+push+dispatch), keep the shim optional** — the trigger was WIP in June 2026 with real engineering blockers (album_asset volume) [42] and hadn't shipped by v3.4.0-rc.0 [35]; hourly cron may well be "fresh enough" (user previously accepted hourly/daily cadence — RESEARCH.md settled constraints). Impact: the shim may become unnecessary; nothing built for phase 1 is wasted.
6. **Debounce window & burst policy?** Best guess: **10-minute trailing debounce in the shim + `concurrency: cancel-in-progress:false` + capacity-1 runner**; a bulk-tagging session collapses into one deploy [1][19]. Impact: Netlify credit/bandwidth spend (CLI digest-upload keeps it delta-sized — RESEARCH.md R2.1 (d)).
7. **Derivative library on PVC vs re-pull each run?** Best guess: **PVC** (host-backend workdir) — Netlify's digest upload already minimizes wire cost; re-pulling hundreds of previews hourly wastes Immich I/O. Impact: PVC sizing (≈1 GiB start at settled scale), backup story (regenerable from Immich — no backup needed).
8. **Who owns Forgejo repo secrets rotation?** Best guess: Bitwarden remains truth; rotation = re-run the seeding job (API `PUT` is idempotent) [7]. Impact: runbook line; Forgejo secret values are write-once in the UI [5].
9. **Should the sync-state cursor live in git (committed by the workflow) or only on the PVC?** Best guess: **PVC + periodic git commit** (auditable history; FORGEJO_TOKEN pushes don't re-trigger [5]). Impact: trivial either way; git copy aids disaster recovery of the cursor.
10. **Runner replicas?** Best guess: **1** (capacity 1) — serializes deploys by construction; cache/workdir sharing across replicas needs the external cache server [19]. Impact: a hung job blocks the queue until `timeout-minutes` fires [1]; set it.
