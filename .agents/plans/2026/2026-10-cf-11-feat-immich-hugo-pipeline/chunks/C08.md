# C08: forgejo-host-runner image — pinned Go toolchain (hugo module download on the runner)
size: S   wave: 4   depends_on: [C02]   ADDED 2026-11-05 (plan amendment — C07 dev r1 live finding)

## Goal

The live site (CuratedForest.com on Forgejo) imports two hugo modules
(`lkhrs/hugo-dark-visitors`, `onweru/compose` per its `hugo.yaml`). hugo
0.151.0 resolves/downloads modules with a `go` binary on PATH — the C02
`forgejo-host-runner` image ships none (Dockerfile-verified by C07 dev r1,
which reproduced the failure clone-side: `hugo -D --gc` stops at
`failed to load modules: binary with name "go" not found in PATH`). Without
this chunk the first runner build of `deploy.yml` (both legs: PR→farm and
merge→prod) is a guaranteed-red module-download failure. Ship a pinned,
sha256-verified Go toolchain in the image.

## Tasks

- [ ] Pin the latest stable Go at implementation time (verify live from the
      official release index, e.g. https://go.dev/dl/ or the versions
      JSON) and its official .sha256 (C02 precedent: the hugo ARG is
      digest-verified with `sha256sum -c` on the written digest file —
      hadolint pipe-safe).
- [ ] Dockerfile: download + verify + extract the official tarball to
      `/usr/local/go` (root at build time; runtime reads it as uid 1000),
      expose on PATH for the runtime user, and add a build-time
      `RUN go version` assertion (fail-loud, C02 pattern).
- [ ] README: one entry for the Go toolchain — the reason (hugo module
      download at runner build time), the pin, and that the module cache is
      NOT baked in (per-site modules; first build pays the download;
      actions/cache warm-up is on the plan's follow-ups list).
- [ ] No chart/version changes (release.yaml + docker-build own the tags);
      no other C02 surface touched.
