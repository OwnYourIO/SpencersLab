# C05: charts/forgejo-run-watchdog — schedule-failure watchdog (INCLUDED phase 1)
size: M   wave: 3   depends_on: [C04]

## Goal

Close the runner route's one genuinely worse-than-CronJob property: schedule
triggers are the fragile leg of Actions-type systems (silent-disable class,
RESEARCH-forgejo-runner §1.1). Owner answer 3 INCLUDES the watchdog in phase
1 (no longer deferrable) and answer 7's DAILY cadence raises its weight: one
missed schedule = one stale day, so the watchdog is the compensating control
(called out where the cron is defined — C06's sync.yml notes). A small
**gpu-cluster** CronJob (co-located with C04, R8) checks that the site repo's
workflows keep succeeding and notifies when they don't.

## Behavior contract

- Hourly CHECK CronJob (`concurrencyPolicy: Forbid` — the check stays hourly;
  only the sync cadence is daily), image pinned
  `docker.io/curlimages/curl:<tag>` (renovate), script via ConfigMap:
  1. Freshness check, in preference order:
     a. Forgejo runs API: `GET {forgejoUrl}/api/v1/repos/{owner}/{repo}/actions/runs`
        (PAT from the SAME `cf-sync-forgejo` Bitwarden item as C04 —
        `write:repository` covers reads) → newest successful run of the sync
        workflow within `watchdog.maxAgeHours` (default **48 = 2× daily
        cadence**; value-tunable; owner may tighten once cadence settles).
     b. FALLBACK (if the runs endpoint 404s — run-list API may need Forgejo
        ≥v16; target instance version unverified): Netlify deploys API
        `GET https://api.netlify.com/api/v1/sites/{siteId}/deploys` with the
        NETLIFY token (same items as C04) → newest `ready` deploy within
        `watchdog.maxAgeDays` (default 3 — prod deploys are merge-driven, so
        this leg is a liveness floor, not a freshness promise).
  2. Stale → notify: `POST {watchdog.notify.url}` with a JSON body (run name,
     last-success age, pointer to Actions UI). Channel is a VALUE, not a
     hardcode: owner points the URL at whatever receiver they prefer
     (HA/n8n/gotify/ntfy — HA itself lives in services/grow, so no in-cluster
     assumption is made). Optional bearer via a Bitwarden item ONLY if the
     receiver needs it (skip the item otherwise).
  3. Healthy → exit 0 silent. Re-alerting hourly while stale is acceptable and
     simpler than state (values comment says so).
- Same chart conventions as C04: drop-ALL, reloader, no ingress, version 1.0.0,
  **gpu** wiring with OVERRIDE_VIA_CLUSTER_ANNOTATION sentinels reusing C04's
  items (`forgejo-pat` + `netlify` — uuid parity with C04's annotation keys;
  NO new mandatory Bitwarden items).
