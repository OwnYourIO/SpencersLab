# C05: charts/forgejo-run-watchdog — schedule-failure watchdog (INCLUDED phase 1)
size: M   wave: 3   depends_on: [C04]

## Goal

Close the runner route's one genuinely worse-than-CronJob property: schedule
triggers are the fragile leg of Actions-type systems (silent-disable class,
RESEARCH-forgejo-runner §1.1). Owner answer 3 INCLUDES the watchdog in phase
1 (no longer deferrable) and answer 7's DAILY cadence raises its weight: one
missed schedule = one stale day, so the watchdog is the compensating control
(called out where the cron is defined — C06's sync.yml notes). A small
**gpu-cluster** CronJob (co-located with C04, R9) checks that the site repo's
workflows keep succeeding and notifies when they don't.

## Behavior contract

- Hourly CHECK CronJob (`concurrencyPolicy: Forbid` — the check stays hourly;
  only the sync cadence is daily), image pinned
  `docker.io/curlimages/curl:<tag>` (renovate), script via ConfigMap:
  1. Freshness check, in preference order:
     a. Forgejo runs API: `GET {forgejoUrl}/api/v1/repos/{owner}/{repo}/actions/runs`
        (PAT from the SAME `hugo-build-forgejo` Bitwarden item as C04 — owner
        naming rule 2026-11-02; C04's closed records and shipped comments name
        the same item under its pre-rename label) →
        `write:repository` covers reads; newest successful run of the sync
        workflow within `watchdog.maxAgeHours` (default **48 = 2× daily
        cadence**; value-tunable; owner may tighten once cadence settles).
     b. FALLBACK (if the runs endpoint 404s — run-list API may need Forgejo
        ≥v16; target instance version unverified): Netlify deploys API
        `GET https://api.netlify.com/api/v1/sites/{siteId}/deploys` with the
        NETLIFY token (same items as C04) → newest `ready` deploy within
        `watchdog.maxAgeDays` (default 3 — prod deploys are merge-driven, so
        this leg is a liveness floor, not a freshness promise).
  2. Stale → notify: `POST {watchdog.notify.url}` with a JSON body (run name,
     last-success age, pointer to Actions UI). Channel is a VALUE, not a
     hardcode: owner points the URL at whatever receiver they prefer
     (HA/n8n/gotify/ntfy — HA itself lives in services/grow, so no in-cluster
     assumption is made). Optional bearer via a Bitwarden item ONLY if the
     receiver needs it (skip the item otherwise).
  3. Healthy → exit 0 silent. Re-alerting hourly while stale is acceptable and
     simpler than state (values comment says so).
- Same chart conventions as C04 (whose shipped shape is APPROVED — mirror
  it): drop-ALL, reloader, no ingress, version 1.0.0. **GPU delivery
  premise (corrected per DECISIONS COORD FACT-RULE 2026-11-01 — the old
  plan text here named the dead cluster-annotation mechanism):** the chart's
  top-level `bitwardenIds:` keep the `OVERRIDE_VIA_CLUSTER_ANNOTATION`
  sentinel STRINGS as inert shadowed defaults (live fleet practice,
  searxng/neo4j); the REAL uuid delivery is a `forgejo-run-watchdog:
  bitwardenIds:` app block in `custom-values/gpu/prod-values.yaml` (filled
  `OVERRIDE_NEEDED` slots), which base's charts appset projects into the
  release's valuesObject (that file arrives via the
  `services.gpu.customValuesUrls` annotation — the gpu annotation that
  actually feeds uuids; `services.gpu.bitwardenIds` parameter projection
  removed fleet-wide since `aa817da6b`). Reuses C04's items (`forgejo-pat` +
  `netlify` — slot parity with C04's `forgejo-secret-seed:` app block; NO
  new mandatory Bitwarden items).

Findings (severity order):

**BLOCKER-1 — runs leg measures REPO age, not run freshness (core detection broken in steady state).**
`templates/configmap-watchdog-script.yaml:82` extracts the timestamp with
`grep -o '"created_at":"[^"]*"'`. The pinned baseline — Forgejo 15.0.10+gitea-1.22.0, verified
against the live instance's own `/swagger.v1.json` on git.spencerslab.com AND the Forgejo
v15.0.10 source (`modules/structs/action.go`) — serializes `ActionRun` timestamps as
`"created"`/`"started"`/`"stopped"`; there is NO `created_at` key on the run record. The grep
therefore matches the nested `"repository"` object's `created_at` — the REPO's creation date.
Red proof (offline harness: the rendered check.sh + stub curl + a live-shape fixture with a
successful sync run 23h old, inside the 48h threshold): the script prints
`stale: last successful sync run is 274h old (threshold 48h)` and dispatches `sync.yml` —
274h is the repo's age, not the run's. Consequences: (a) once the site repo is >48h old
(i.e. permanently, in steady state) the watchdog judges STALE and re-dispatches the daily sync
HOURLY even when the schedule is healthy — inverting the compensating control this chunk
exists for (RESEARCH-forgejo-runner §1.1/§3) and forcing 24×/day extra sync runs +
immich-sync PR churn; (b) within the first 48h after repo creation it judges fresh
regardless of actual run freshness (false-silence window over the very period a brand-new
schedule is most fragile). The Netlify fallback leg is unaffected (Netlify genuinely uses
quoted-string `created_at`/`published_at` — verified vs the Netlify API docs), so the bug is
confined to the primary leg. Everything else in the runs leg was verified correct against the
same live swagger: wrapper `{workflow_runs, total_count}`, `status:"success"` is a valid
terminal serialization (enum `[unknown, waiting, running, success, failure, cancelled,
skipped, blocked]`), `workflow_id` = workflow FILENAME (`sync.yml`), dispatch endpoint
`POST …/actions/workflows/{workflowfilename}/dispatches` with required `ref`.
Fix direction (dev): extract the run's OWN field — `grep -o '"created":"[^"]*"'` cannot
substring-match the nested `"created_at"` (or prefer `"stopped"`, the completion time).
This is a CODE fault, not a validation fault: the chunk scoped t2/t3 as construction tests
pending a live repo with runs, and the dev's Notes-for-dev duty was "pin expectations to the
embedded Gitea-1.22 API baseline" — the timestamp key was pinned to the GitHub shape instead.
The t2 extension in the fix round should pin the field name (t2 today only asserts "time
arithmetic present", which is how this passed).
