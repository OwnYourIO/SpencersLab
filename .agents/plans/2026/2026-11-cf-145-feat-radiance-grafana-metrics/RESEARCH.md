## Problem model

The radiance fleet exhibits every failure mode of "short-lived target" monitoring at once. Four independent mechanics produce the one symptom ("rate panels empty at narrow ranges; the dashboard only fills at 24h"):

- **(a) Window-vs-age math.** `rate()`/`increase()` need **≥2 samples inside the window** and return *nothing* (not 0) below that [2][8]. The window Grafana actually sends is `$__rate_interval = max(step + scrapeInterval, 4 × scrapeInterval)` — the docs phrase it as "guarantees … at least four scrape samples" [5][6], the source formula is per [7]. At this lab's 60s autodiscovery default (`feature-annotation-autodiscovery/values.yaml:12` and `charts/radiance/values.yaml:245`), a pod's first rate point is only computable after its **2nd scrape (~2 min + ready-delay: the keep rule scrapes only Running/Ready pods — `_pods.alloy.tpl:60-68`)**, after model load. `rate()` then *extrapolates to the window ends*, so a 2-sample series yields a plausible-but-smoothed value, not an honest "no data" [2].
- **(b) Identity churn.** Autodiscovery with the shipped pair (`k8s.grafana.com/scrape` + `metrics.portNumber` → `charts/radiance/values.yaml:274-275`) sets `__address__ = podIP:8000` (`_pods.alloy.tpl:161-174`) and **never sets `instance` unless the instance annotation is present** (`_pods.alloy.tpl:101-103`) — so Prometheus defaults `instance = podIP:8000` (EXPLORE fact #24, plan R6). Every lane swap/restart mints a new series set. `radiance.json` (v1.17.0, fetched) then hard-filters **every panel** with `instance=~"$instance" AND model_name=~"$model_name"`, where `$instance = label_values(radiance:engine_steps_total, instance)` (multi, includeAll, refresh=on-time-range-change). A stale selection (old podIP gone from the option list, e.g. after a 15m-range refresh) matches nothing → the whole dashboard blanks even though data exists (Grafana refresh semantics [13]; vLLM upstream simply has no instance variable — [26][27]).
- **(c) Legitimate absence.** replicas-0 lanes export nothing; the last sample goes **stale after the 5-minute lookback** and queries then return *no value*, not 0 [1][2][9]. Counters restart at zero on new pods (reset-adjustment only works *within* a continuing series; when the identity changes there is no series to adjust [2]). No query can conjure samples that were never produced — see contradictions §CLASH-1.
- **(d) Scrape-side identity vs restart.** Labels that survive a pod restart are only those **not** derived from pod identity: `job` (falls back to the pod label `app.kubernetes.io/name` = `radiance` for both releases — `_pods.alloy.tpl:86-99`, plan R5b), plus any `pods.labels`-mapped workload label (`_pods.alloy.tpl:204-209`) and the cluster label appended by the pipeline. `pod` (set from `__meta_kubernetes_pod_name`, `:70-72`) and `instance=podIP` change every restart; `namespace` doesn't.

The owner's 6h census (3 different series sets: 2, 4, 56 samples — launch brief) is this model, confirmed: all four mechanics compose at the two-R9700 lane-swap cadence.

## Q1 — Stable target identity: what OUR stack supports (no chart code change needed)

**Annotation inventory shipped by k8s-monitoring 4.5.5 feature-annotation-autodiscovery** (`feature-annotation-autodiscovery/values.yaml:41-77`, verbatim keys): `k8s.grafana.com/scrape`, `/job`, `/instance`, `/metrics.container` (pods only), `/metrics.path`, `/metrics.portName`, `/metrics.portNumber`, `/metrics.scheme`, `/metrics.param_<key>` (URL params), `/metrics.scrapeInterval`, `/metrics.scrapeTimeout`. There is **no `keepLabels`-style annotation** in this version (grep-clean) — upstream docs listing: [20][21].

**Endpoint-level relabeling is reachable WITHOUT ServiceMonitors**, in three escalating shapes, all applied *pre-scrape inside `discovery.relabel`* (so `__meta_*` labels are available [22]):

1. **`k8s.grafana.com/instance` annotation** (`_pods.alloy.tpl:101-103`) — copies the annotation's value verbatim to `instance`. The value is **static per pod template**, but the pod template is helm-rendered: `charts/radiance` can ship `k8s.grafana.com/instance: '{{ .Release.Name }}:8000'` (or `…:8000-{{ .Chart.AppVersion }}`) → instance becomes **`gpu-ai-radiance:8000` / `gpu-ai-radiance-q27:8000`**, stable across restarts/podIPs and lane-unique. Cheapest structural fix; touches only the C01 annotation region (see caveat below).
2. **`annotationAutodiscovery.pods.labels`** (`_pods.alloy.tpl:204-209`; wrapper `charts/k8s-monitoring/values.yaml:162-169`) — map any pod label to a metric label without touching `instance`, e.g. `lane: app.kubernetes.io/instance` (helm release name label, set by app-template charts). Adds stable dimensions; does not fix existing `$instance`-filtering in an upstream dashboard.
3. **`annotationAutodiscovery.extraDiscoveryRules`** (`values.yaml:177-182`, injected last — `_pods.alloy.tpl:217-219`) — raw `rule {}` blocks (full relabel grammar [22]) that can rewrite `instance` for matched targets, e.g. `source_labels: [__meta_kubernetes_pod_label_app_kubernetes_io_instance]` → `replacement: "$1:8000"`, gated by a `job="radiance"` keep. Applies cluster-wide from the wrapper values (every cluster runs the same `charts/k8s-monitoring`) — gate rules accordingly. (Post-scrape `extraMetricProcessingRules`, `values.yaml:208-212`, has **no `__meta` labels** — wrong layer for identity.)

Also reachable: **service-role autodiscovery** — annotate the *Service* instead of the Pod: the service route (`_services.alloy.tpl:91-93` instance annotation; port selection `:108-141`) discovers targets whose address is the **Service DNS name + port** ("generally useful for blackbox monitoring of a service" — Prometheus SD config docs [35]), i.e. natively churn-proof `instance` for a replicas-0/1 lane. Honest caveat: scraping through a ClusterIP means kube-proxy load-balances scrapes and per-pod attribution dies at replicas>1 — Prometheus itself labels this the blackbox pattern [35]. Fine for single-replica engines; flag before adopting fleet-wide.

**What the chart CANNOT do at 4.5.5 via annotations:** a `replacement: $pod-name`-style instance template (the instance annotation copies static text; no meta interpolation in that rule — `_pods.alloy.tpl:101-103`). Templated continuity needs route 1 (helm-side templating), route 3 (alloy-side relabel), or ServiceMonitors.

**ServiceMonitor/PodMonitor route (already live on gpu-ai):** `prometheusOperatorObjects.enabled: true` (`charts/k8s-monitoring/values.yaml:140-143`) feeds Alloy's `prometheus.operator.servicemonitors` component (`feature-prometheus-operator-objects/templates/_service_monitors.alloy.tpl:5-…`, endpointslice role), which honors operator CR semantics — per-endpoint `relabelings` (pre-scrape) and `targetLabels`/`podTargetLabels` (metric-label copy) [23][24][25]. It offers the same identity powers as route 3 but per-workload, with job=`<ns>/<monitor>` naming; the owner ruled against it for radiance in cf-145 (D-8/OQ-1), and plan R7 bars the ScrapeConfig idiom here.

**What OTHER lab dashboards' targets use** (repo-verifiable): the cadvisor/kubelet/kube-state feature templates **never relabel `instance` at all** (grep-clean: `feature-cluster-metrics/templates/_kubelet.alloy.tpl`, `_cadvisor.alloy.tpl`, `_kube_state_metrics.alloy.tpl`) — `instance` is the *exporter's* address (kubelet nodeIP:10250, k-s-m pod:8080) and workload identity arrives as **metric labels** `namespace/pod/container/node`. The lab's Kubernetes Views dashboards (gnetId 15757-15761, `services/monitoring/prod/values.yaml:542-571`) group by those labels and never filter `instance`. One lab-specific gap: `kube_pod_labels`/`kube_pod_annotations` are DROPPED in telemetry tuning (`charts/k8s-monitoring/values.yaml:89-94`), so pod-label→KSM joins are not available here as an identity source.

## Q2 — PromQL patterns for young/churning series

- **`$__rate_interval` semantics** (the honest version): window = max(step+scrape, 4×scrape) [7], "≥4 scrape samples" [5][6]. It sizes the window to the **scrape cadence**, never to the **series age** — a pod younger than ~2 scrapes yields nothing regardless [2][8]. Wide ranges only "fill in" two ways: the bigger step inflates the window (window ≥ step+scrape, so a 24h view queries multi-minute windows), and a 24h span still contains the DEAD podIP series — old-instance series exist historically even when no live pod has their address. Neither mechanism makes a YOUNG series draw sooner. The fix is Q1 identity + framing, not range widening.
- **Myth guard (brief asked):** "rate() needs a full window of history" is FALSE — 2 samples anywhere in the window produce a value, **extrapolated** to the window ends [2]; conversely "using $__rate_interval means you never think about windows" is also false (see above; issue [7]).
- **Staleness/absence:** last sample before pod death stays queryable for the 5-min lookback, then the series is marked stale and returns *nothing* [1]. That is why "current throughput" cannot be read as a falling-to-zero line without extra work — Prometheus refuses to invent the zero [1][2].
- **Honest "show last known value" idioms** (the `rate(...) or vector(0)` chain is explicitly NOT one of them — see contradictions §CLASH-6 [19][30][31]):
  1. **`last_over_time` needs a per-second series to hold** — on raw counters it returns the last *counter*, not a rate. So the pattern is **record first**: `record: radiance:decode_tokens:rate5m` (`sum by (job, cluster, model_name) (rate(radiance:decode_tokens_total[5m]))`), then a stat panel `last_over_time(radiance:decode_tokens:rate5m[1h])` (instant query, `Last *`) survives a pod going quiet for up to the recording window. `last_over_time`/`present_over_time` are documented range functions [2]; rule semantics/gaps: [3].
  2. **Engine-side rate vs scrape-side rate** (pattern name the brief asked for: "instantaneous/self-reported rate"). SGLang ships exactly this: `sglang:gen_throughput` — a **gauge** "generate throughput (token/s)" labeled `model_name`, readable instantly with zero history [28]. vLLM instead derives rates from counters/histograms and exposes instantaneous *state* gauges (`num_requests_running/waiting`, `kv_cache_usage_perc`) [29] — its own dashboards use only counters+`$__range`/`$__interval` windows [26][27]. If radiance really exposes a `*_tokens_per_second` gauge, an instant stat is the correct narrow-range widget (see open questions — the shipped dashboard JSON contains **no `*_per_second` series** and EXPLORE fact #11's catalog lists none; owner-leg verification required).
  3. **"Since-restart" framing**: the counters ARE since-restart; `sum(increase(x[$__range]))` (already the dashboard's stat pattern) is the right shape for a panel whose time range is set to the pod's life — i.e. pair with a panel-relative `timeFrom` (Q3), not with wider dashboard ranges.
  4. **Offline/lane-state framing:** `absent()` / `absent_over_time()` [2] and `present_over_time(...)` [2] drive "lane offline" states; the info-metric join pattern (`*info` gauge carrying labels, joined with `on(...) group_left`) is the documented technique for fleet membership panels [19]; Prometheus even ships experimental `info()` for it [2][4]. `up{job="radiance"}` per target is the existence signal the autodiscovery chain itself always produces.
- **Recording rules: what they fix and don't** [3]: they precompute a long-window rate as its own 1m-spaced series (so narrower ranges still *join* cleanly, dashboards get cheaper, and `last_over_time` has a rate to hold). They **do not** backfill missed evaluations (slow group evaluation literally *skips* iterations → gap in the recorded series), do not run during pod absence, and on a **remote-write receiver** (this lab's central Prometheus, `services/monitoring/prod/values.yaml:95`) the docs warn metric-availability delays make tight rule intervals risky — give groups a sane `interval` (1m) and windows ≥ a few scrape periods [3].
- **Grafana-side panel options that matter:** Standard options **No value** renders text/values when the query returns nothing [11] (with the known stat-panel noValue quirk [12]); **Value mappings** turn 1/0 into "lane up/down" words; **Panel min interval / Max data points** stabilize step across screen widths (documented [10]) — a min-interval of `1m` at 60s scrape keeps `$__rate_interval` from ballooning and makes step deterministic; stat panels with **Last *** reduce "empty because last bucket is thin" artifacts (stat panel doc).

## Q3 — Dashboard design for off-capacity fleets (replicas-0 fleets)

- **vLLM upstream's actual answer** (the closest shipped precedent to this dashboard — same metrics namespace, fetched raw): identity = `model_name` label (`Deployment_id` variable = `label_values(vllm:request_success_total, model_name)`), **no instance variable anywhere**, `sum by (model_name)(rate(...))` first-rate-then-aggregate, and a **default range of `now-12h`** [26][27]. Translation for this lab: the project that owns the metric family chose model-granularity and wide defaults, and never asks a human to select a target address.
- **Panel-relative time ranges** are a first-class Grafana feature: each panel can override the dashboard range (`timeFrom`/`timeShift` — "Override the dashboard time range with one specific to the panel", current consolidated time-settings UI [14]; JSON schema fields documented [15]). Standard shop pattern: dashboard stays 15m for live widgets, the history/rate rows carry `timeFrom=now-24h` (+ `timeShift` for "same time yesterday" comparisons — [14]).
- **Stale-options variables:** set **Refresh = On time range change** (radiance.json already does — repo fact below), use **Include all option + Custom all value `.+`** so the All selection is a regex, not a materialized list [13], or define the variable as `query_result(topk(…, sum(rate(x[$__range])) by (…)))` so options are computed *over the visible range* — the documented pattern, with a community variant using `last_over_time` windows [5][34]. For a lane that has been off 6h, range-scoped options simply stop offering dead podIPs.
- **Scale-to-zero presentation:** in Knative-style fleets zero replicas is a *normal state* [33]; community dashboards don't fight the staleness math — they present state (up/absent/info rows, "offline since" using `timestamp(last_over_time(...))` variants [4]) and use `last_over_time` on recorded series for "last known throughput" stats. No documented feature makes `rate()` render across an absence window; that's the load-bearing limit.
- **Datasource lookback:** Grafana's Prometheus datasource does not extend Prometheus's 5-min lookback per-panel; the per-query override lives server-side (`lookback_delta` query param) [1] — treat lookback changes as global and risky, not as a dashboard trick.

## Q5 — What the engine cannot fix; upstream asks worth filing

- **Not engine-fixable by design:** absence (replicas 0 ⇒ no process ⇒ no series), scrape-identity (`instance` is Prometheus's target-address convention [32][35]), the 2-sample floor, and reset semantics — a new pod's counters legitimately restart [2]. The engine's *only* structural lever is **self-reported instantaneous rates** (SGLang's `gen_throughput` gauge [28] — the documented precedent — and llama-swap's per-response `tokens_per_second` extraction, PR #910, cf-105 [64]) and **label discipline** (put lane/model identity on the metrics, which radiance already does with `model_name`).
- **How vLLM handles pod churn:** it doesn't instrument target identity at all — metric-label identity (`model_name`/`served_model_name` [29]) + wide default ranges + per-range `increase` stats [26][27]; the prometheus-operator convention for stability is `job=<monitor>` + operator-relabelled stable `instance`/targetLabels [24][25]. A "stable-instance or since-restart counter" request is therefore an **anti-ask upstream** (counters are since-restart already; stability belongs to the scrape layer).
- **Worth filing at radiance upstream:** (1) add `radiance:decode_tokens_per_second` / `prefill_tokens_per_second` **gauges** mirroring the SGLang `gen_throughput` idiom [28] — instantly readable at narrow ranges, immune to scrape identity; (2) ship the dashboard without a mandatory `instance` filter (group by `model_name`, vLLM shape) or default the instance var to All-with-regex; (3) document a `radiance:info`-style info metric (value 1, labels: lane/model/build) for fleet-membership panels [19].

## Contradictions & limits (incl. the myths)

- **CLASH-1 "$__rate_interval guarantees 4 samples" ≠ "young pods will plot."** The docs' guarantee is a *window-size* statement [5][6]; the window formula itself is `max(step+scrape, 4×scrape)` [7], and rate still needs 2 samples **of that series** [2][8]. No Grafana version or macro closes the age gap — that is the load-bearing limit of this whole problem class.
- **CLASH-2 stable-instance wishes vs target-identity doctrine.** Prometheus convention: `job`+`instance` identify a *scrape target*; faking a workload identity into `instance` is common (the very annotation [20][21] exists for it) but the community guidance [32] — including its dated "Prometheus 2 closes dead series" claim, superseded by staleness markers [1] — says put continuity in labels, keep instance honest. Weigh: rewriting instance is legitimate and shipped as a first-class option; keep the *pattern* consistent lab-wide (vLLM dashboards don't filter instance; cadvisor jobs don't relabel it — repo facts above).
- **CLASH-3 chart comment vs lab reality (provisioning).** grafana-chart values note: sidecar "can't be used together with dashboardProviders/dashboards" [repo extracted values:955-956]; the lab runs all three (`services/monitoring/prod/values.yaml:197-273, 489-690, 691-705`) and both surfaces deliver. Treat the sidecar-overlay option as *de-facto supported, de-jure contested* — the inline-`json:` route (#2 above) is the uncontested one.
- **CLASH-4 recording rules as compaction vs documented gap behavior.** [3]: skipped evaluations on slow groups, no backfill, remote-write availability delays — a recorded series is *cleaner*, never *denser* than reality.
- **Consensus (all five perspectives agree):** (i) readable "live" numbers for a churning/off fleet come from **self-reported instantaneous metrics + state/info framing**, not from widening windows; (ii) continuity must live in **metric labels that exist at discovery or inside the engine** (`model_name`, release-derived labels), never in podIP-derived `instance`; (iii) the dashboard is the right place for honesty controls (No value, thresholds, relative panel time), not the place where absence can be engineered away.
