  when it has a blocking dependency edge whose target card is not in **Test** or

  Test `jNYNdCPPkX8Bs95s4`, Finished `DHw56fMKy3qyfudz4` — ride STATE.json

  OQ2): `is-blocked-by` stored on the DEPENDENT card is the primary shape; the
  gate ALSO honors the inverse (`blocks` stored on the dependency side) via
  WeKan's inverse map — manually-drawn edges may point either way. Only
  `blocks`/`is-blocked-by` edges gate (related-to/fixes/duplicates never do).
  Keyed on card `_id`, NEVER card_number (identity rule). Archived dependency
  targets never block. A skipped candidate is reported in the RESULT/claim
  comment (card id + blocking card id + its list) so the walk is auditable.

  degraded}}` — the full card map is NOT persisted to STATE.json. Degrade law:
  `tools/list` probe first — `preload_board` absent ⇒ today's per-list reads
  unchanged + the gate skipped with a RESULT note; never a hard failure.
- [ ] T3 **Grouped-sibling flow** — new section: when a card's relationships
  (Red Strings dependency edges — kinds 2+3, `blocks`/`is-blocked-by` ONLY;
  kind-1 follow-up lineage is parentId and NEVER a grouping trigger, OQ1
  ruling) name companion cards, the run pulls their asks into its OWN plan,
  moves the siblings to **Executing** at start and to **Review** at end
  (coord-owned moves, one summary comment each).
  Siblings ride the run's OWN claim — never claimed separately (one session,
  one card; the walk skips Executing, so no double-pick). Degrade: until edges
  exist, a run may operate from a plan-enumerated id list (this ticket's first
  instance does exactly that — plan Run protocol section).
- [ ] T4 **Follow-up protocol update**: (a) the Follow-up cards section's
