## Conventions
- "Tests" in this repo = validation scripts under `tests/` (structural/grep/bash), `helm lint`/`helm template` renders, sentinel sweeps, and service-trio grep checks. There is no unit-test suite (AGENTS.md "Pipeline specifics").
- Work happens on the feature branch `refactor-forgejo-runner-per-instance-apps` in the coordinator's worktree; merge/push to main is the user's decision alone. The worktree starts on detached HEAD at main tip — the first dev chunk creates+attaches the branch (established pattern).
- Secrets: ExternalSecret + Bitwarden only. Sentinel `OVERRIDE_VIA_CUSTOM_VALUES` in chart/service values; real UUIDs only in `custom-values/<category>/prod-values.yaml`.
- Chart versions: never hand-bump — release.yaml bumps on merge to main. The refactor keeps `version: 1.0.1` and updates only the `description`.
- Image tags stay pinned (runner 13.2.0, docker 29.9.1-dind); Renovate's built-in helm-values manager tracks both pins in the single values.yaml.
- `tests/services/dev-forgejo-runner.sh` stays the ONE runner contract script (predecessor ruling) — agent-test rewrites it red-first to the new two-Application contract; the other tests/services scripts are untouched regression.

## Decisions
- 2026-10-24 plan: Deployment shape = ONE single-instance chart (`charts/forgejo-runner`) deployed TWICE by the dev ApplicationSet via the existing `chart:` alias mechanism (verified: `charts/base/templates/appset-charts.yaml` lines ~24-26 carry a `chart:` key; live precedent `external-secrets-bitwarden-kube-system` in services/proxy-local/prod/values.yaml). Rejected: keeping the two-controller one-chart shape (status quo — the user wants per-instance Applications), and two separate charts (code duplication of the whole runner contract).
- 2026-10-24 plan: App names = `forgejo-runner-dev` + `forgejo-runner-infra`, BOTH aliased with `chart: forgejo-runner` (symmetric, explicit). Rejected: one plain `forgejo-runner` + one alias (asymmetric). Consequence: ArgoCD apps/helm releases `dev-forgejo-runner-dev` + `dev-forgejo-runner-infra`; the old app `dev-forgejo-runner` is pruned by the appset when its `charts:` entry disappears.
- 2026-10-24 plan: Resource naming = everything named by the release name. Verified by prototype render: with a single controller/service, app-template 5.0.1 names SA/STS/Service exactly `<Release.Name>` (single-resource naming omits the identifier suffix); the chart template sets ExternalSecret `metadata.name` and `spec.target.name` to `{{ .Release.Name }}`. All cluster-scoped-per-namespace names are thus disjoint between the two releases in `default`. Rejected: `global.fullnameOverride` per app (extra slice coupling, no benefit) and reusing the library name helper (see FRICTION: `bjw-s.fullname` does not exist in 5.0.1; `bjw-s.common.lib.chart.names.fullname` is not callable from parent-chart templates).
- 2026-10-24 plan: The persistence entry's secret name = `name: "{{ .Release.Name }}"` in the chart's values.yaml — app-template 5.0.1 tpl's `persistence.<id>.name` for `type: secret` (library `_volumes.tpl` line ~79), so static values.yaml can still be release-derived. One `runner-creds` entry with `globalMounts` (whole secret at the static pod-local path `/run/secrets/forgejo-runner` + config.yaml subPath at `/data/config/config.yaml`) — the per-controller persistence ENTRIES of the old chart existed only because persistence is global across controllers (predecessor friction); with one controller per release, one entry with globalMounts is correct. `CREDENTIALS_DIRECTORY: /run/secrets/forgejo-runner` is pod-local and needs no per-release uniqueness.
- 2026-10-24 plan: Values shape = ONE sentinel `bitwardenIds.runner-token` + ONE `runner.url` per chart install. Chart default `runner.url` stays `http://dev-forgejo-http.default.svc:3000` so the chart renders standalone (documented as a render-time stand-in). Rejected: no chart default (breaks standalone render).
- 2026-10-24 plan: Per-app values flow = TOP-LEVEL slices `forgejo-runner-dev:` / `forgejo-runner-infra:` in services/dev/prod/values.yaml carrying each instance's `runner.url` — verified that `appset-charts.yaml` builds the per-app values blob ONLY from `merge $extraValues (index $.Values $appName)` (top-level key), never from the `charts.<appName>` entry. This fixes the predecessor wart where the URL pins under `charts.forgejo-runner.runners` were inert (F02 finding: chart defaults applied at deploy time). Rejected: carrying URLs in the `charts:` entries (they would be silently ignored — the exact wart being fixed).
- 2026-10-24 plan: Real UUIDs move in custom-values/dev/prod-values.yaml from `forgejo-runner.bitwardenIds.{forgejo-runner-token,forgejo-runner-infra-token}` to `forgejo-runner-dev.bitwardenIds.runner-token` (= d3dafd1a-3d88-454e-88d4-b4ec010ae2c2) and `forgejo-runner-infra.bitwardenIds.runner-token` (= b1add65b-44fb-4c8b-b7ad-b4ec010afc71). Same items, same UUIDs, no Bitwarden-side change. (Item-name comments disagree between the shipped sites — chart says items `forgejo-runner` + `dev-forgejo-runner-infra` (B4 + ruling-2 naming), custom-values says `dev-forgejo-dev-runner` + `dev-forgejo-prod-runner`; the UUIDs are the truth, dev preserves the existing per-site comment wording rather than re-litigating names.)
- 2026-10-24 plan: config.yaml `server.connections` gets ONE entry with key `default` (replacing the per-instance `dev`/`infra` keys) — each release now owns its whole config; `default` is the documented single-connection key for runner v13.
- 2026-10-24 plan: ONE atomic chunk (C01, size L). Chart rework and service/custom-values rewire cannot ship separately: chart-alone breaks the live app's value keys (renamed sentinel/url keys resolve to nothing), rewire-alone deploys the old two-controller chart twice into one namespace (ESO/target-Secret name collisions). Rejected: a compatibility bridge (extra code to remove later, and the runners are already down live — no stability window to protect).
- 2026-10-24 plan: The two instances stay byte-identical except url + Bitwarden item (same act label set, resources, timeouts 30m/5m, grace 300, dind pin, fsGroup 1000) — nothing else is parameterized per instance.
