await base.StopAsync(cancellationToken) (BackgroundService contract) so

ordering provably cannot break the snapshot-last/shutdown sequence — dev
decides on code read, documents choice. T2: AC ordering care: base.
StopAsync AFTER the custom legs (disconnect, snapshot stay where the

running' warning, shutdown wall-time meaningfully < previous ~11s
(measure), snapshot.complete + exit 0 preserved; fresh compile 0w/0e; suite

### Semantic audit (ordering subtleties — the fix's whole point)
- **(a) base-first in BrokerPublisher — VERIFIED.** .NET 10 source
  (release/10.0 `BackgroundService.StopAsync`): cancels the stopping CTS
  **then `await _executeTask.WaitAsync(ct)` (SuppressThrowing)** — base
  both cancels the token and waits for ExecuteAsync. `ExecuteAsync` itself
  does NOT await `_run` (it parks on `Task.Delay(Timeout.Infinite,
  stoppingToken)`), so the belt-and-braces `await _run.WaitAsync(StopWait)`
  stays the loop-completion wait; with the token cancelled the loop exits
  in ms, so the 10 s timeout (and its warning) never fires — smoke-verified
  (0 warn lines, 0.162 s). Reconnect interleaving constructed by hand —
  after base returns the token is cancelled, and NO path reaches
  `ConnectAsync`: the only re-entry is `continue` after `WaitSessionAsync`
  (gated by the `while (!ct.IsCancellationRequested)` check) and the
  fall-through after `BackoffDelayAsync` (gated by `if
  (ct.IsCancellationRequested) return;`); a mid-flight `ConnectAsync`
  throws OCE → `catch (OperationCanceledException) { return; }`. The
  disconnect runs AFTER base (after the loop has unwound), so the
  disconnect can never end a session the loop still owns — the C11
  base-LAST defect (disconnect ends the session → loop `continue`s →
  `ConnectAsync` on the not-yet-cancelled token → reconnect + retained-
  online re-publish + abnormal session death at exit → LWT) is structurally
  closed. Residual edge (a CONNACK landing in the cancellation window): the
  loop takes the Success path into `WaitSessionAsync` (returns at the
  token check), exits; the consequence is one redundant same-value
  retained-`online` re-publish BEFORE the clean disconnect — the entity was
  already online, the clean disconnect fires no LWT (offline via
  expire_after, the C03 design) — no post-disconnect blip, no LWT, matches
  the spec's "graceful = no LWT expected". Backoff token-awareness (T2):
  `BackoffDelayAsync` = `Task.Delay(backoff, ct)`, `WaitSessionAsync` =
  `Task.Delay(250 ms, ct)`, `ConnectAsync(…, ct)` — no bare `Task.Delay`
  anywhere in the file (deviation 2 claim holds).
- **(b) supervisor: base-first cancels the stoppingToken — loop termination
  VERIFIED; kill-sequence reachability finding below.** The loop breaks on
  the token at every point: the `while (!stoppingToken.IsCancellation
  Requested)` top, the linked per-iteration CTS (cancels via the link —
  watchdog `while (!ct.IsCancellationRequested)` + `Task.Delay(100, ct)`
  OCE → return; read loop `ReadAsync(…, ct)` OCE; assign `Task.Delay(5 s,
  cts.Token)` OCE), the respawn `Task.Delay(delay, stoppingToken)` OCE →
  `break` (a loop mid-45 s escalation delay leaves it immediately — the
  dev's claim holds). `ShutdownChildAsync` is called UNCONDITIONALLY in the
  override (after base), the `_shutdownStarted` guard is intact (idempotent
  re-entry → `_shutdownDone.Task`), and its internal kill sequence (TERM 5 s
  grace → SIGKILL → `WaitForExit` → `_audio.Writer.TryComplete()`) is
  byte-identical. **Finding (the base-await interaction):** because .NET 10
  base ALSO awaits `ExecuteAsync`, by the time `ShutdownChildAsync` runs
  the loop has already finished its iteration — including `child?.Dispose()`
  and `_child = null` — so the kill sequence reads `_child == null` and
  skips its TERM/SIGKILL leg on the hosted stop path (the 5 s exit wait
  inside `WaitChildOrWatchdogAsync` short-circuits: `Process.WaitForExit
  Async(ct)` transitions to cancelled on token cancellation — release/10.0
  `UnsafeRegister → TrySetCanceled` — so the loop unwinds fast, no 5 s
  block). Consequence for the live-child path (the real-deployment stop):
  the child is no longer explicitly killed; `Process.Close()` (via the
  loop's `child?.Dispose()`) closes the STDERR pipe (AsyncMode) but NOT
  the stdout pipe (SyncMode — `Process.Close()` skips referenced sync
  streams; the Process finalizer is suppressed), so the child survives the
  host stop (its writes land in the 64 KB pipe buffer ≈ 1.5 s, then block)
  and dies by EPIPE at process exit (or earlier if it writes stderr into
  the closed stderr pipe). **No path leaves the child alive past process
  exit — the stated regression bar (an orphaned snapclient child surviving
  SIGTERM) is NOT met**; the old code's graceful TERM-first leg is replaced
  by this EPIPE death (the R3 implication-7 kill-before-pipe-close
  ordering is inverted on this path, but the guarded outcome — the child
  gone, the pipe unread, no survivor — holds: the consumer is gone, the
  child has nothing to flush, the container teardown is the backstop).
  Not a regression per the spec's bar; recorded as minor M2 below for the
  owner's follow-up call.

### Findings (non-blocking)
- **M1 (minor, comment accuracy — the class C12 exists to fix):**
  `SnapClientSupervisor.cs` StopAsync comment: "the sequence owns the
  child-gone-before-pipe-close ordering" is not true for the R3
  "pipe read end" (the OS stdout pipe) on the hosted stop path — the OS
  stdout pipe closes at process exit (and the stderr pipe at the loop's
  `child?.Dispose()`) while the child is still alive; the sequence's own
  close is only the internal channel completion (`_audio.Writer.
  TryComplete()`), which does not signal the child. Suggested fix: scope
  the clause to the sequence's own channel close, or state the actual
  hosted-path child disposition (EPIPE at/before process exit, bounded).
  Not blocking: the sequence's own ordering is intact and the child never
  survives.
- **M2 (minor, owner-notification):** the live-child stop path no longer
  runs the designed TERM-first kill leg (base awaits ExecuteAsync → the
  loop nulls `_child` before the kill sequence reads it → the leg is
  skipped); a live child survives the host stop and dies by EPIPE at
  (or just before) process exit — bounded and self-contained (the stated
  regression bar is not met), but a deviation from the R3 implication-7
  ordering on that path, and the kill sequence's TERM/SIGKILL code is
  now dead on the hosted path. Follow-up options if the owner wants the
  TERM-first leg back: keep a last-child reference the loop does not null
  on the stop path, or snapshot `_child` into the kill sequence before
  base awaits. Owner's call; does not block cycle 4 (the container
  teardown is the backstop and the child has nothing to flush).
