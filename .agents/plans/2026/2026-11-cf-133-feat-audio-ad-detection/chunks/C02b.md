# C02b: Auto-capture + curator (candidate capture, auto-promote on recurrence, manual promote lane, list/prune)
size: M   wave: 2   depends_on: [C02a]  (intra-wave: runs after C02a)

## Goal
The Q3 owner-ruled catalogue growth path with the 2026-11-24 owner override:
non-matching spans of the stream are cut to candidate WAV segments on the PVC
(`/models/candidates/`); **candidates that recur independently are
auto-promoted into the live catalogue** (fingerprint + insert, marked
`auto_promoted: true` so a human can audit/prune via `list`/`prune`), with the
manual `promote` (file or `--dir`) kept as the manual lane. Guardrails are
config with sane defaults (recorded best-guesses — not re-asked): min
independent sightings, min inter-sighting gap, per-day auto-promotion cap,
fingerprint-proximity dedup before insert.

## Tasks
- [x] Capture state machine (consumes C02a's `IStreamState` + config):
      - a non-matching span (no confident match for ≥ `CAPTURE_MIN_SPAN_SECONDS`,
        default **30** — a standard 30 s spot; the 120 s `NewOccurrenceAbove`
        ceiling is a seam control, not a span threshold) starts a capture window
      - the span is gated by RMS: `CurrentRmsDb` must be above
        `CAPTURE_RMS_FLOOR_DB` (default **−45 dBFS**) — TV-off / source-off
        silence sits far below and must not fill the dir; a span that dips
        below the floor while open is discarded on close, not split
      - the span ends at the first confident match after the non-match, or at
        `CAPTURE_MAX_SPAN_SECONDS` (default **300** — beyond 5 min is an
        off-air / program boundary, not a spot)
      - on close: cut the span with **5 s pre / 5 s post roll** from a ring
        buffer (holds 10 s + margin of resampled 5512 mono audio; the pre-roll
        is the audio before the span start, covering the <1.5 s `MatchedAt`
        edge jitter, R1 §1) and write it as a candidate
- [x] Candidate writer: 44-byte-header WAV, 5512 Hz mono s16le (the worker's
  own resampled stream — hand-rolled, no extra package), written to
  `$MODEL_DIR/candidates/<group>_<UTC-timestamp>_<duration>s.wav` (group = the
  tapped group's name/short id, e.g. `famtv_20261124T031245Z_42s.wav`);
  `aad_capture_candidates_total` increments on each write; a failed write is
  logged, never fatal to the query loop
- [x] **Auto-promotion on recurrence (owner override 2026-11-24 — supersedes
  the never-auto-promote posture)**: on each candidate close, the candidate is
  fingerprinted and compared (fingerprint proximity) against previously seen
  candidates; a candidate qualifies for auto-promotion when the guardrails —
  all env config, Post Research threshold tweaks = value-only change — all
  hold:
  - `AUTO_PROMOTE_MIN_SIGHTINGS` (default **2**): the audio was seen ≥2 times
    as distinct recurrences — repetition across episodes/pods is the ad signal
    (R1's `NewOccurrenceAbove` recurrence evidence; a single sighting never
    promotes)
  - `AUTO_PROMOTE_MIN_GAP_HOURS` (default **24**): the qualifying sightings are
    ≥24 h apart (cross-episode/cross-pod repetition, not back-to-back re-runs)
  - **fingerprint-proximity dedup before insert**: the candidate must not be
    within the proximity threshold of an already-known catalogue track (a
    known ad re-airing is not a new one) nor of a previously promoted
    candidate (one entry per distinct ad, not one per re-airing)
  - `AUTO_PROMOTE_MAX_PER_DAY` (default **20**): per-day auto-promotion cap to
    bound drift-feeding (a genuinely repeating non-ad, e.g. a program jingle,
    is a bounded, auditable exception); cap-hit skips count
    `aad_auto_promotions_capped_total`
  - on qualification: fingerprint + insert into the live catalogue with
    `kind=ad` + **`auto_promoted: true`** meta (meta: `captured_at`,
    `source_group`, sightings count) + `Snapshot($MODEL_DIR)` +
    `aad_auto_promotions_total` increment; the candidate file is marked
    promoted (so `list` shows the flag)
- [x] Manual `promote` lane (STAYS, the manual path for single-shot candidates
  or owner-dropped files): `promote --file <candidate.wav>` /
  `promote --dir <dir>` — decode (candidate WAVs decode directly; `--dir` for
  arbitrary owner-dropped formats uses `FFmpegAudioService` — the R1 §4
  canonical insert shape) + fingerprint + insert with `kind=ad` meta
  (`captured_at`, `source_group`; **no `auto_promoted` flag** — manual
  origin) + dedup guard (skip if already known) + `Snapshot($MODEL_DIR)`;
  non-zero exit on per-file failure
- [x] `list` subcommand: candidates (name, duration, size, age, **auto_promoted
  flag**) plus auto-promoted tracks (name, meta, promotion time, sightings —
  the human audit surface); `prune` subcommand: applies the candidate
  retention policy on demand (`--older-than <days>` override) **and** deletes a
  named promoted track (`prune --track <name>` — audit/prune of auto-promoted
  entries) + `Snapshot($MODEL_DIR)`
- [x] Retention: `CAPTURE_RETENTION_DAYS` (default **14**) and max **200**
  candidates (whichever trips first; oldest pruned first) — pruned on startup
  and periodically (e.g. hourly)
- [x] Metrics: `aad_auto_promotions_total`, `aad_auto_promotions_capped_total`
  (registered in C02a alongside `aad_capture_candidates_total` — note: the
  C02a metrics registration task covers the three counters; if C02a landed
  with only the capture counter, this chunk extends the registration)

  auto-promote-on-recurrence, not human-gated — this supersedes the
  never-auto-promote posture of the earlier Q3 deviation entry. The manual
  `promote` lane stays. The `auto_promoted` flag + `list`/`prune` audit

  recurrence-promotion precedent; if its findings warrant threshold tweaks,
  that is a **value-only change** (the thresholds are env config, no code
  path change).

  **never** a liveness/readiness input (R4 §3/§5 rule — silence never means
  unhealthy; the LWT + `expire_after` model owns liveness).
- Candidate WAVs are the worker's own resampled stream (5512 mono s16) —
  `promote --file` decodes them with a 44-byte-header read, no FFmpeg needed;
  only the arbitrary-format `--dir` path pulls `FFmpegAudioService`.
- Ring buffer depth: 10 s (5 pre + 5 post) + margin of 5512-float mono =
  ~55,120 floats ≈ 220 KiB — trivial.
- The recurrence/sighting tracker persists per-candidate sighting times
  (in-memory + a small JSON sidecar next to the candidate file is fine —
  it must survive a worker restart without re-fingerprinting everything);
  retention runs on a low-priority path (startup + hourly timer + on-demand)
  — never on the hot chunk loop.
- Auto-promotion inserts run on the same low-priority path as retention —
  never on the hot chunk loop.
- UNCOMMITTED in place on main; no commits (run posture).

**BLOCKER-2 — two consumers split one `BlockingCollection` (breaks the single-consumer
premise of the approved C02a design; degrades both features in production).**
`RealtimeQuery` consumes `_pipeline.Chunks` via
`new BlockingRealtimeCollection<AudioSamples>(_pipeline.Chunks)` — source-verified
v18.0.0: its `GetAsyncEnumerator` loops `collection.TryTake(...)`, i.e. a Take-based
consumer. `CaptureMachine.ExecuteAsync` does
`await _pipeline.Chunks.TryTakeAsync(...)` on the SAME collection.
`BlockingCollection` (default `ConcurrentQueue` backing) delivers each item to exactly
ONE caller — it is thread-safe for concurrent readers, not a fan-out. The CaptureState
class comment "BlockingCollection is multi-reader safe" is the category error. Consequences:
(a) the realtime query sees a random subset of chunks — its stream clock advances at a
fraction of real time, so `MatchedAt` drifts further behind wall clock (R1's <1.5 s
accuracy contract breaks), and `NewOccurrenceAbove(120)`, the 120 s staleness ceiling
and the 5 s coverage bar are all miscalibrated by the skew factor; the hot-source
re-enumeration (C02a's approved contract) additionally loses chunks the capture machine
took meanwhile; (b) the capture machine's ring and span body carry ~1.857 s gaps per
stolen chunk — pre/post rolls go partially stale and candidate WAVs have holes, degrading
the auto-promote fingerprint/dedup/recurrence decisions. **Fix (scoped):** fan out at the
producer — `AudioPipeline` writes each chunk to BOTH a query queue and a capture queue
(two bounded `BlockingCollection`s, both `CompleteAdding` in the same `finally`; a
non-blocking `TryAdd` on the capture leg is the alternative if the capture leg must never
block the realtime leg — the capture take-loop is light, so awaiting both `AddAsync`s is
acceptable). The fix necessarily touches `AudioPipeline.cs` (a C02a file) — legitimate.
Also correct the now-wrong comment in `CaptureState.cs`.
