# C01: Container + worker skeleton
size: M   wave: 1   depends_on: []

## Goal
A buildable `containers/audio-ad-detection/` image: the multi-stage Dockerfile
plus a .NET 10 Generic-Host console that launches and supervises the snapclient
child, reads the PCM pipe, serves `/healthz` + `/readyz` + `/metrics`, and on
startup re-points its snapcast group at `SNAP_STREAM_ID` when that value holds
a real group id. No fingerprinting or MQTT yet — the worker stays alive in an
"acquiring" state.

## Tasks

      mcr.microsoft.com/dotnet/sdk:10.0` → `FROM mcr.microsoft.com/dotnet/runtime:10.0`
      (no `:latest`); build stage `dotnet publish -c Release -r linux-x64
      --self-contained false`; runtime stage `wget` of

      cleanup in the same RUN; non-root user uid 65532 (explicit groupadd +

      (NOT the NAudio meta-package), MQTTnet 5.2.0.1603,
      Microsoft.Extensions.Logging 10.x + console provider

      `tcp://home-snapcast:1704`, `SNAP_HOST_ID` default
      `audio-ad-detection`, `SNAP_SAMPLE_FORMAT` default `5512:16:*`,
      `SNAP_STREAM_ID` **no worker default — required value supplied by the

      (a) anonymous, Q1; the recorded fallback (c) costs no code change),

      per the plan's config surface)
- [ ] SnapClientSupervisor: foreground child (no `--daemon`), argv per R2
      implication 1 (`--player file:filename=stdout --sampleformat
      $SNAP_SAMPLE_FORMAT --logsink stderr --hostID $SNAP_HOST_ID $SNAP_URL`,
      volume 100%); stdout tight read loop (≥1-byte reads, 4-byte frame-parity
      accumulator — stereo s16 frame = 4 B, parity tracked across reads); stderr
      drained on a background thread; stdout never logged
- [ ] Byte-cadence watchdog (R2 §2 shape): startup grace ~10–30 s; kill after
      ~500 ms (10 ticks) of zero bytes; extended to minutes while stderr recently
      logged `Reconnecting`/`Connecting to host` (server-outage tolerance);
      SIGKILL (a #1563-hung process spins — SIGTERM's io_context stop may never
      run) + respawn with the same args; escalation counter ≥3 kills in 5 min →
      alert log + 30–60 s respawn delay; stderr tail keywords `Version `/
      `Connected to` / `Reconnecting` / `Snapclient terminated.`; kill counter
      exported to the metrics surface
- [ ] Startup stream assignment (Q2, R2 §5 mechanics): after connect (or on
      respawn, best-effort, non-blocking), one-shot JSON-RPC `POST $SNAP_RPC_URL`
      (BCL `HttpClient` — no extra package): `Server.GetStatus` → find the group
      whose `clients[]` contains the pinned `--hostID` → `Group.SetStream
      {id: <group>, stream_id: $SNAP_STREAM_ID}` — only when `SNAP_STREAM_ID`
      holds a real value (not empty / `TBD-owner`); log the outcome
      (`stream assigned` / `unassigned — config-order`)
- [ ] SIGTERM handler (PosixSignalRegistration): stop reader → TERM the child
      (~5 s grace, then SIGKILL via `Process.Kill(entireProcessTree)`) → exit
      (MQTT + Snapshot legs land in C03)
- [ ] Health + metrics: `System.Net.HttpListener` on `0.0.0.0:$HEALTH_PORT` —
      `/healthz` (process alive + child alive), `/readyz` (skeleton: true once
      the audio read loop is up and the pipe is delivering; C02a/C03 extend
      it), `/metrics` (hand-rolled text exposition, no extra package:
      `aad_audio_rms_db` gauge placeholder + `aad_snapclient_kills_total`)

## Notes for dev
- R2 implication 1 is the argv authority — do NOT write `5512:16:1` (the CLI
  rejects numeric channels at startup; the README's own example uses the `*`
  form). Q6 answered: `5512:16:*` is the default boundary.
- Q4 answered: the csproj pins SoundFingerprinting **18.0.0** — the Post
  Research round verifies the 18.0.0 realtime-contract parity; if it finds a
  blocker, the recorded fallback is the 17.4.x pin (one-line swap), per the
  plan's risk note.
- The file player is a recorder (R2 §1): 50 ms ticks, always exactly `needed`
  bytes (1,100 B/tick at 5512), silence on underrun — the stream is
  time-continuous; the read loop never treats a short read as EOF (a blocking
  pipe read returns ≥1 byte until the writer closes; EOF = child death).
- stderr MUST be drained concurrently — a full stderr pipe blocks the child
  (classic child-process deadlock).
- The runtime image has no ASP.NET Core shared framework (R3 §1): stay on the
  `HttpListener` shape (A), do not pull in Kestrel.
- The `Group.SetStream` call is a one-shot startup best-effort (R2 §5: it
  sends a fresh CodecHeader → a #1563 exposure event — do it deliberately,
  never in a hot loop); a failure is logged, not fatal (config-order still
  works).
- First cold forge build risks the 30-min ceiling (R3 §5) — keep the
  `dotnet restore` layer stable (csproj before source COPY) so warm builds are
  fast.
- This run is UNCOMMITTED in place on main with zero coordinator commits
  (card Lifecycle omits Worktree Creation) — work in the landing checkout, no
  commits.

**SIGTERM ordering (R3 implication 7):** verified in source. `PosixSignalRegistration` sets `context.Cancel` (host stop → `StopAsync` → `ShutdownChildAsync`) and the handler's explicit task hits the same idempotent entry (`Interlocked.Exchange(_shutdownStarted)`), so the single ordered teardown runs once: `_loopCts.Cancel()` → `kill -TERM` (5 s grace; the comment correctly notes .NET has no managed TERM signal, `kill` via coreutils is the portable shape) → `Kill(entireProcessTree)` if still alive → `WaitForExit` → only then `_audio.Writer.TryComplete()`. `RunAsync` cannot return until the host stop (which awaits `StopAsync`) finishes, so the child is dead and the pipe read end is closed after the child is gone — the SIGPIPE race is avoided. `ExecuteAsync` re-checks `_shutdownStarted` before every `StartChild` and the respawn delay cancels on the stopping token, so no child is launched mid-teardown; total teardown (5 s grace + kill + wait) sits well inside the 30 s K8s grace.
