### Semantic audit
- **Read order (T1) — VERIFIED.** `ReadExitState` is called at line 177, the
  `child?.Dispose()` at 180, `_child = null` at 181: both members are read on
  the pre-dispose object, on the owning thread, and the read sits ahead of the
  `stoppingToken.IsCancellationRequested` break, so the stop path reads it too
  (live child → `HasExited` false → `(null, lifetime)` → no exception, and the
  break means the value is unused there — correct). In HEAD the read was
  `RespawnDelay(child.ExitCode)` *after* the dispose (git show
  HEAD:…:lines 170-181) — that is the crash, and only on the natural-exit
  branch (the stop branch broke first), which is why it took the live
  server-stops-client pattern (cycle 5) to surface it.
- **Catch honesty.** `ReadExitState` catches `InvalidOperationException` only —
  the documented disposed/unstarted-process throw (`NotSupportedException`
  needs a remote machine; `ExitCode`-not-exited is pre-guarded by `HasExited`).
  The unknown-code result is documented at the call site and in the helper's
  comment, and degrades to the normal delay rather than inventing a code. No
  `catch (Exception)` anywhere in the new code, no swallowed error class.
- **Normal path can't be masked.** On a natural exit the ternary evaluates
  `HasExited` (true) then `ExitCode` (cached, cannot throw) — the try costs
  nothing and no real code is replaced by `null`. The single call site is
  line 191, gated on `exitCode.HasValue`, so the escalation and normal branches
  each log exactly one line per respawn: watchdog-killed children still get
  their `watchdog: … SIGKILL + respawn` warning (382) plus the discriminator
  with `code=137`; escalated children get only the error line (by design —
  the hang, not the code, is the news); the stop break adds `shutdown in
  progress — not respawning`; spawn-failure iterations log `snapclient spawn
  failed` and take the null-code branch. No duplicated and no silent respawn
  path beyond that null branch (nit N1).
- **Signature change is diagnostics-only — VERIFIED.** `RespawnDelay(int,
  double)` adds `lifetimeSeconds` to the warning and to nothing else: the
  escalation predicate is still `EscalationDue()` over `_killTimes`, populated
  only by `RecordKill()` in the watchdog branch (line 381). Byte-identical to
  HEAD for (a) exit-0 children (1 s delay, one warning), (b) crash codes
  139/137 (1 s unless escalation is due), (c) the kill-counter coupling. The
  `child is not null` guard was replaced by `exitCode.HasValue`, which is
  equivalent on every reachable path except a live-but-not-stopping child
  (watchdog settle timeout + failed kill) — there it now takes the 1 s delay
  instead of reading an `ExitCode` that would have thrown. Strictly safer.
- **(d) ten fast natural exits do NOT escalate — pre-existing design, now
  reachable.** Escalation counts kills, never exits, so a server-driven
  stop/start flap respawns at 1 s forever. That matches the ruled posture
  (watchdog for #1563 *hangs*; clean stops are config-order noise the owner's
  L2.5 `SNAP_STREAM_ID`/`Group.SetStream` leg removes) and C13 must not change
  it — but it is a latent flap, so it goes on the owner roll as M2 rather than
  back to dev.

- **M2 (minor, design note for the owner roll):** natural-exit flapping is
  invisible to metrics — `aad_snapclient_kills_total` only counts watchdog
  kills, so a 1 s respawn loop (any code) shows in logs alone, and `/healthz`
  can read 200 between exits. Candidate follow-up (owner's call, next to C12's
  M2 child-death-mechanism note): feed sub-second-lifetime exits into the same
  escalation window, or add a respawn counter to the metrics surface.
- **N1 (nit):** the unknown-code respawn branch (190-192) takes 1 s with no log
  line at all. Reachable only when the child was never started or never reaped
  — arguably worth a `LogDebug` for the postmortem record. Not required here.
- **N2 (nit):** `lifetimeSeconds` overstates by up to the 250 ms watchdog settle
  + the exit-wait tail. Diagnostic-only; the comment says "run length in
  seconds at this read", which is exactly what it is.
