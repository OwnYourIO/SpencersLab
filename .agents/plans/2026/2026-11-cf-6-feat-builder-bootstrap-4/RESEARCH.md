# RESEARCH — cf-6-feat-builder-bootstrap-4
Acquiring helm + chart-releaser for the `containers/forgejo-runner` bake with ZERO get.helm.sh fetches from the cluster path.

Date: 2026-11-23 · Role: `agent-research` (storm method, interviews run in-session) · Brief: STATE.json intake + coordinator launch.

## TL;DR
1. Replace both bake-fetch RUNs with **`COPY --from=` of digest-pinned tool images**: helm from `docker.io/alpine/helm:3.22.1` (binary at `/usr/bin/helm`), cr from the **official helm-org image** `ghcr.io/helm/chart-releaser:v1.10.1-amd64` (binary at `/usr/local/bin/cr`). Every registry class involved is **proven-reachable from the exact runner host** by live pod state — no pre-probe required.
2. Helm tarballs are **NOT** GitHub release assets (verified: v3.22.1 assets are 870-byte GPG sigs only) → the "fetch helm from GitHub" family is **dead**; but the official release body publishes the linux-amd64 sha256, and a one-time offline binary-hash cross-check re-anchors the community image to the official checksum chain.
3. Fallback if the owner refuses any community-published image: build on the **GitHub fallback lane** (get.helm.sh is fine there) and **copy ghcr→instance** from the bootstrap lane (all proven egress); costs a two-step dance and a ghcr package-visibility leg (UA-10).
4. apt-via-Buildkite repo is real but ships only **3.22.0**, not 3.22.1 (verified) — backup only. Changing the act base is dead (act-24.04 has no helm, verified upstream).
5. Keep: ARG version asserts, digest-authority convention, Renovate (its dockerfile manager natively tracks `FROM`/`COPY --from` image refs).

## Reliability notes
- **Overall confidence: high.** Every load-bearing fact was read this session from a primary source (GitHub API JSON, Docker Hub API, registry `/v2/` endpoints, Forgejo docs, helm docs, catthehacker's own build scripts, live cluster pod specs, the ticket's own EXPLORE evidence). Only two residual assumptions, both flagged and both non-gating.
- **Weakest claim:** "the dind daemon's own pulls reach docker.io as easily as the kubelet's did" (the proven Hub pulls were kubelet-side: the runner pod's `docker:29.9.2-dind` and `redis` images). Same host, same NAT, same outbound path → inferred-very-strong; confirmed by one `docker pull` line in a job (P2 below, optional) or simply by the first lane dispatch.
- **Possible bias:** the supply-chain lens dominates ranking criteria (the launch brief weights E5 explicitly), which under-weights the pure-convenience of the status-quo-with-GitHub-builds (family D); owner ruling D33/R-B history actually shows convenience has already been traded away once, so the bias is bounded.
- **Open gap (no source covered it):** whether the get.helm.sh block is *documented* anywhere upstream (no public status page found), and whether Forgejo **generic-package anonymous GETs** work on a public org — relevant only if family C is picked; docs show only authenticated examples.

## Perspectives (who argued what, from the sources)
- **Supply-chain engineer:** binary identity matters more than binary *transport*; digest-pinned content-addressed pulls (cr official image) are strictly stronger than tarball+sha256sum files; a community image is acceptable **only** when the embedded binary can be tied back to the official checksum once, offline, and re-asserted at build. Pushed back hardest on `alpine/helm`.
- **Homelab GitOps practitioner:** the fix must be one Dockerfile diff, merged once, rebuilt by the lanes that already exist, with Renovate bumping forever and zero recurring laptop steps. Pushed back on anything requiring two-lane sequencing (D) or a sync job (C).
- **CI-egress-scarred platform engineer:** trust only class-proven paths; a CDN/WAF that policy-blocks one host today can broaden tomorrow, so the design must have **no single-host acquisition chokepoint** at build time. Pointed out the status quo *also* carries an unproven arm (the cr fetch from github.com's asset CDN never executed in run #215 — the Dockerfile's own comment says so) and that the fleet already practices mirror-on-reachable-registry (`ecr-public.aws.com` pins in charts).

## Key findings (ranked, with proof status)
1. **PROVEN — helm/helm GitHub releases carry NO binary assets.** v3.22.1's assets are exclusively `*.asc` GPG signature files (870 B each); the release body links the "common platform binaries" on get.helm.sh and publishes each tarball's sha256 inline — linux-amd64 = `896cf63684a42a723d61c980369d6e588330927deb13676ca0d85006dd6da0ea`. Family 2 (helm from GitHub assets) is **dead**; but the release notes (api.github.com — a class the cluster already reaches per intake) are a reachable official **checksum source**. [S1][S2]
2. **PROVEN — the ONLY official Helm CLI artifact host is get.helm.sh; there is no official helm-CLI container image.** `ghcr.io/helm/helm` → 403/absent, `quay.io/helmpack/helm` → 401/absent, `docker.io/helm/helm` → 404 (live probes). So every image-based route for helm is necessarily third-party. [S10]
3. **PROVEN — chart-releaser DOES ship an official helm-org image, on two proven registries.** `.goreleaser.yml` publishes `ghcr.io/helm/chart-releaser` **and** `quay.io/helmpack/chart-releaser` (cosign-signed, multi-arch); `v1.10.1-amd64` exists with manifest digest `sha256:f04f886affa5ba55b004788591b56f35bfd79abca9f85f0cb2f61c2f90bbe84c` (index `sha256:51758f90...`); the image's Dockerfile places the binary at **`/usr/local/bin/cr`** (alpine 3.24 base, static `CGO_ENABLED=0` build). cr's leg needs NO github.com CDN at all: `COPY --from=ghcr.io/helm/chart-releaser:v1.10.1-amd64@sha256:f04f886a... /usr/local/bin/cr`. ghcr class is proven from the runner daemon (base pulls fine, intake); quay class is proven at the site (live pods). [S4][S5][S6][S22]
4. **PROVEN — cr's current source URL is sound *as a source*, unproven *as an egress*.** The v1.10.1 GitHub release carries `chart-releaser_1.10.1_linux_amd64.tar.gz` (31,787,128 B) with digest `sha256:ce46baf9975d10193b7070b2b7406750c3f664181e36df3f3bbb4a00be40dc1b` — **byte-equal to the Dockerfile's `CR_SHA256` pin** (C01 review stands). But whether `github.com` → `objects.githubusercontent.com` asset redirects survive this egress was never tested: run #215 died on the helm arm before the cr arm ran (the Dockerfile comment says exactly this). Status: **NEEDS-ONE-PROBE (P3)**, and moot if cr moves to the ghcr image. [S3][S23]
5. **PROVEN — `docker.io/alpine/helm` ships the official linux amd64 helm binary at `/usr/bin/helm`, current through the exact pin.** Repo: active, 75.3 M pulls, auto-built by GitHub Actions on every helm release, source public at `github.com/alpine-docker/helm`; its Dockerfile wgets `${BASE_URL:-https://get.helm.sh}/helm-v${VERSION}-linux-${ARCH}.tar.gz`, extracts, and installs `mv linux-${ARCH}/helm /usr/bin/helm` — i.e. the community image **rehosts the official tarball contents** rather than rebuilding from source. Tag `3.22.1` exists (pushed 2026-10-16, one day after the helm release), amd64 manifest digest `sha256:83dd7afc7510c2076ec63637e427c465b022d53c2e6984305dc0041f04652068`, index digest `sha256:8191701ad1f82ee3695c87211fcbfe6d7b1bb7df92ac1c8de9ccdb0995a6a2c1`. Maintainer: community (`ozbillwang`, alpine-docker org) — **not** the Helm project. [S7][S8][S9]
6. **PROVEN — docker.io and quay.io are reachable registry classes from this very host.** The runner pod itself runs `docker.io/library/docker:29.9.2-dind` (its sidecar) and `data.forgejo.org/forgejo/runner:13.2.0`; other gpu pods run `docker.io/library/redis`; infra pods run `quay.io/keycloak/keycloak`, `quay.io/jetstack/cert-manager-controller`, `docker.io/chrislusf/seaweedfs`, `code.forgejo.org/forgejo/forgejo`; one argo workload even pins `ecr-public.aws.com/docker/library/redis` (an existing lab mirror-on-reachable-registry precedent). Combined with the intake's proven ghcr pulls, the block is **targeted at get.helm.sh specifically** — exactly the ticket's verdict, now with the complement: the replacement classes don't need probing at the kubelet level. [S22][S23]
7. **DEAD — "change the base so no bake is needed".** catthehacker's act images install node/moby/git-lfs/jq/yq/python and **no helm** (upstream `act.sh` read in full; the repo's script inventory has no helm-carrying variant; the lab's own Dockerfile exists precisely because of this). No maintained act-compatible image with helm+cr was found. Family 5 eliminated with evidence. [S13][S14]
8. **WEAK — apt route exists but doesn't have the pin.** helm.sh documents a community apt repo at `packages.buildkite.com/helm-linux/helm-debian/` (a non-blocked host; official docs even give the pinned GPG key-id check). The `binary-amd64/Packages` index was read live: 20 debs, newest v3 = **3.22.0-1**, no 3.22.1 (and patch coverage is spotty — 3.22.1's CVE-dependency bump never landed; v3 line is in maintenance). Also a community *repackaging*, not the official tarball. Backup only. [S2][S15]
9. **PROVEN (API shape) — a self-hosted mirror is buildable on existing surfaces.** Forgejo generic packages: `PUT/GET https://<host>/api/packages/{owner}/generic/{package}/{version}/{file}` with token/basic auth; `409` on duplicate file names; the API is same-origin to the builder (proven path — the lanes already hit `/v2/` on the same host). Practical design note: an in-Dockerfile fetch would need build-time auth (secret surface), so the clean pattern is a **lane step that stages the file into the build context, then plain `COPY`**. Size posture: `[packages].LIMIT_SIZE_*` knobs exist; 16–32 MB debs/tarballs are in the ordinary range; uploads stream with a 32 MiB in-memory window. OCI artifacts via oras are supported (the upload fix is tracked in codeberg #8070), or simply a tiny real image in the instance container registry — but every C variant still needs first acquisition from A or D. [S16][S17][S18][S19][S20]
10. **PROVEN — Renovate covers the image-based pin natively.** The dockerfile manager extracts `FROM images`, `COPY --from images`, `RUN --mount from=images` and even apk/apt pins inside RUN; the repo's built-in docker datasource machinery is already in heavy use (llama-swap/ownyourio rules in `renovate.json`). A family-A Dockerfile therefore keeps the lab's E2/E4 posture without custom managers, and the existing "Hold the helm v3 line" rule keeps v4 out (extend it to the new image name if needed). [S21][S23]

## PROVEN vs INFERRED vs NEEDS-ONE-PROBE (owner's probe list)
- **PROVEN (read this session):** findings 1–10 above; cr tarball digest == `CR_SHA256`; class-level reachability of ghcr/docker.io/quay.io/data.forgejo.org/ecr-public from the runner's site/host; helm+cr binary paths in both candidate images.
- **INFERRED (strong, from intake + docs):** the block is get.helm.sh-only (its CDN/WAF policy on this IP/ASN — intake's 3-run discrimination); GitHub-hosted runners can reach get.helm.sh (different ASN; the lane was never dispatched for this image); dind-daemon Hub pulls behave like kubelet pulls (same netns path, one hop more).
- **NEEDS-ONE-PROBE (each ~1 min, none gate family A):**
  - **P1 (offline, re-anchors A's trust — do once):** on any get.helm.sh-reachable machine: download `helm-v3.22.1-linux-amd64.tar.gz`, `sha256sum -c` against [S1]'s published value, extract, `sha256sum` the binary; then `docker create/cp` `/usr/bin/helm` out of `alpine/helm:3.22.1@sha256:83dd7afc...` and compare the two binary hashes. Equal ⇒ the community image's binary **is** the official binary; bake the binary-sha into the Dockerfile as the permanent assert.
  - **P2 (optional, daemon-class):** first bootstrap dispatch's build log — the `FROM docker.io/alpine/helm` pull either succeeds or it doesn't. (Skip P1-vs-P2 sequencing: the build IS the test.)
  - **P3 (only if the cr leg stays github.com):** `curl -sSIL --max-time 30 https://github.com/helm/chart-releaser/releases/download/v1.10.1/chart-releaser_1.10.1_linux_amd64.tar.gz` from a job — settles the never-executed arm (and tests the `objects.githubusercontent.com` class generally).
  - **P4 (only if D is chosen):** dispatch `.github/workflows/docker-build.yaml` with `containers=forgejo-runner` — simultaneously proves the GitHub→get.helm.sh leg and produces the first copyable artifact; then the UA-10 visibility step.

## Where the perspectives disagree, and how to weigh it
- **A vs D (trust):** supply-chain prefers D (official host end-to-end); GitOps prefers A (one diff, one lane). **Weigh toward A:** the official *checksum* chain is reachable from the cluster (GitHub release notes [S1]), so P1 converts A's only trust gap into a byte-exact anchor — after which A and D carry the same bytes; D keeps get.helm.sh as a *build-time* dependency of the GitHub lane, i.e. the class of failure that killed three runs, merely behind a healthier egress.
- **A vs C (durability):** egress-scarred prefers C (no external registry at build). **Weigh toward A now, C later-if-needed:** C's first fill needs A or D anyway, adds auth plumbing and a sync job, and buys insurance against a *hypothetical* second block; A already removed the *actual* single-host chokepoint by spreading across ghcr+docker.io (two independent operators). If the block ever broadens, C is the designed escalation and P1's hash anchor transfers to it unchanged.
- **Consensus:** get.helm.sh is out of the cluster path for good; cr should move to the official ghcr image regardless of the helm choice (it erases the last proven-vs-unproven fetch asymmetry in the current Dockerfile); every replacement must keep digest/sha authority + version asserts + Renovate; the run-3 host-net retry family is retired by ruling (STATE.json deferred note).

## What everyone agreed on (load-bearing core)
The three dispatch deaths are upstream policy, not cluster fault (intake discrimination); ghcr + docker.io + quay.io + data.forgejo.org + api.github.com all work from this path (live evidence); the official helm binary is v3.22.1 = tarball sha `896cf636...` [S1]; cr v1.10.1 binary identity is already verified twice over [S3][S5]; and a bake whose tool sources are all content-addressed and reachable is strictly *better* than the pre-incident state, not just less broken.

## The non-obvious connection
The fleet already answered this problem once for Hub throttling, not blocking: `argocd-redis` pins `ecr-public.aws.com/docker/library/redis` — a mirror-on-a-reachable-registry pattern [S22]. Family C is that precedent generalized to get.helm.sh, and family A is its cheap special case (let someone else's registry BE the mirror). Also helm's own docs now push exactly one non-get.helm.sh official-adjacent route (the Buildkite apt repo [S2]) — meaning the Helm project itself is diversifying binary distribution just as v3 enters maintenance-only life (no further v3 minors after the announced line [S1]) — archive-friendly for a lab pinned to v3 by ArgoCD parity (D38).

## So what — for the planner of run -4
Rewrite the two bake RUNs as multi-stage `COPY --from` pulls: `FROM docker.io/alpine/helm:3.22.1@sha256:8191701ad1f82ee3695c87211fcbfe6d7b1bb7df92ac1c8de9ccdb0995a6a2c1 AS helm-bin` + `FROM ghcr.io/helm/chart-releaser:v1.10.1-amd64@sha256:f04f886affa5ba55b004788591b56f35bfd79abca9f85f0cb2f61c2f90bbe84c AS cr-bin`; install `/usr/bin/helm` and `/usr/local/bin/cr` to `/usr/local/bin`, keep the `helm version --short | grep -q "^v${HELM_VERSION}"` and `cr --version` asserts, retire the get.helm.sh curls; decide (with the owner) whether to add the P1 binary-sha assert; re-pin `tests/containers/forgejo-runner.sh` literals in the same commit; extend the Renovate hold rule to `alpine/helm` if v4 ever appears on the tag list; no workflow or chart changes are needed for the build itself (labels still consume the instance-registry trio; the bootstrap lane is untouched). Record: D33's "source must change" is now executed by removing the fetch, not relocating it; the run-3 host-net family stays retired.

## Implications for the plan (decisions to make differently)
1. No retry/MTU work has any remaining value against a policy block — do not re-temper the path (already the verdict; this closes it).
2. The design target shifts from "make the fetch survive" to "make zero external fetches happen at cluster build time except content-addressed registry pulls" — registry pulls have proven-class redundancy (two operators instead of one).
3. If the owner's ruling is "official publisher only", plan family D instead (chunks: GitHub lane dispatch probe → ghcr public/UA-10 → bootstrap copy step) — ranked second, fully viable, ~2× the plumbing, one recurring manual beat per release unless a copy-trigger is automated.
4. Family C stays the sanctioned escalation path if a second host ever blocks; P1's anchor makes A→C migration lossless.

## Adjacent (short)
- Helm 3 is maintenance-only (release body: next 3.x patch 3.22.2 was slated 2026-11-11; no further v3 minors; Helm 3 EOL blog linked) — the lab's v3 hold (renovate.json rule + D38) will age into archive territory; community images like alpine/helm retain old tags durably, get.helm.sh so far too, but pinning by digest (A) is the archive-stable choice.
- `dtzar/helm-kubectl` and similar exist as alternative community homes for the same binary if alpine-docker ever stalls; quay's `helmpack/chart-releaser` gives cr a second official registry.
- The builder lane's runner has capacity 1 and a 30-min ceiling; A's added pulls (~70 MB, then cached in the persistent layer store) are noise against the ~10 GB base.
