## Notes for dev

- The init container's `command` replaces the image ENTRYPOINT (k8s
  semantics: `command` overrides the entrypoint, `args` appends) — the 0.30
  entrypoint's NUMA-bind/bandwidth-sweep/banner [94] deliberately does NOT
  run in the init (the sweep touches the GPU device path; the init is
  device-free by design; the R2 record carries).
- The init script's quoting: the values YAML string carries the `sh -c`
  body with the embedded python `-c` strings — keep the body ONE quoted
  YAML value (the llama-swap "exec line must stay ONE physical line" law,
  the SanitizeCommand precedent, applies to our render: a multi-line args
  value is a single rendered string; the line breaks inside are shell
  continuations, not k8s arg splits).
- The marker file lives on the 500Gi claim (the `/models` root) — visible
  to the runbook's step-2 `ls` (the staging fact + the both-sha provenance
  in one glance); its double-sha keying is the D13 re-fetch law.
- The `runAsUser: 0` on the init is the PVC-ownership fact, NOT the GID-
  486 device law — the comment must say so (the main container's
  privileged shape stays confined to the main container; a reviewer's
  first question will be "why is the init root and unprivileged" — the
  comment answers).
- The Q8 contingency is NOT staged here: the `RADIANCE_QUARK_BF16_MTP` env
  is a main-container mtp-toggle var (the D25/D26 record, C02's comment
  surface) and the rewrite re-land is the runbook's recorded fallback
  (C05) — the init's command never references either.
- The GGUF file + the llama.cpp trees on the claim are untouched (the
  class-10 rung's ground — the do-not-delete law carries from the R1
  plan).
