# C07: Automatic single-card preload — one server read, delivered on the claim answer
size: M   wave: 3   depends_on: [C06]

## Goal
When a run claims a card, the card's full working detail lands in the session without a fan-out: description, labels, custom-field values (with the C01 slug stack parsed), every standard checklist with item titles and check state, and the card's own dependency lines. Today that costs `get_card` + `list_checklists` + N×`get_checklist` + a dependency read, and the coordinator pays it blind after the claim.

## Tasks
- [ ] `containers/wekan-mcp/wekan_mcp/server.py`: new read tool `get_card_details(board_id, card_id)` returning `{id, card_number, title, description, list_id, swimlane_id, archived, sort, parent_id, label_ids, labels: {id: name}, custom_fields: {name: raw value}, slug_stack: [parsed slugs…], current_slug, checklists: [{id, title, items: [{title, finished}]}], dependencies: [{to_id, type, color}]}`. **`get_card` stays byte-identical** — existing consumers and the `tools.sh` shape pins don't churn; the new tool is additive and read-only.
- [ ] Schema home + formatter: the card block's format gets one normative home — a "Card details block" schema section in `skills/wekan-mcp/SKILL.md` (mirroring how the Board context block schema is owned there), with the plugin's formatter mirroring its bytes and a parity leg (the `skill-surface.sh` t3 pattern) holding them together.
- [ ] Plugin leg (`.opencode/plugin/board-context/index.ts`, hand-managed): after a **successful `pipeline_claim` by a board-coord agent in this session**, append the formatted card-details block to that tool's result — the same `ctx.tool.hook("execute.after")` precedent `aislop-gate` uses. Reuse the plugin's existing MCP client/URL discovery; keep never-throw, keep a bounded budget (its own constant, independent of `FETCH_TIMEOUT_MS` so the prompt-hook budget is untouched), fire at most once per claimed card, and degrade to "no block appended" with one stderr line.
- [ ] boards skill: the claim-time paragraph says the block arrives on the claim answer and lists what it replaces (the kickoff checklist consumption and the dependency reads for **this** card); the degrade law is the same family rule — absent tool / failed call / no block ⇒ the coordinator does its own `get_card` + checklist fan-out, notes it in RESULT, never stalls. Keep the `Preload consumer at claim` "never the hook" sentence intact — that pin is about the **prompt** hook budget; state in one clause that the claim-time leg is a tool hook with its own budget, not the prompt prefetch.
- [ ] Probe law: the run checks `tools/list` for `get_card_details` before relying on it (the deployed `:v87` build has neither this nor `preload_board`).

## Notes for dev
- **Verify hook reachability first.** Whether OpenCode v2.1.4 surfaces `tool.execute.after` events for tools another plugin registered (`pipeline_claim` lives in `pipeline-locks`) is unproven. If it is not reachable, the sanctioned fallback is in the contract, not in your discretion: the boards skill mandates one `get_card_details` call at claim and the plugin leg is dropped from this chunk — report that as a deviation and let coord fold the DECISIONS entry. Do not add a second prompt hook.
- Never hold credentials: reuse `makeCallTool`/URL discovery; OIDC is disabled on these deployments.
- Keep the block footer explicit ("collected <stamp>, from get_card_details") so a stale block is visible, and format the stamp through pipeline-locks' `localIso` (the single formatter rule, cf-96 OQ4).
- The deployed build lacks the tool: every leg is offline; live verification is USER-owned (step 2).
