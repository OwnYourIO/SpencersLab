**Combined apply (C04 + C05 land in ONE merge — what to expect):**
- Secret key set: `{config.yaml, token}` → `{config.yaml, token, uuid}`. `uuid` is
  the raw 36-char login username ⇒ ~48 b64 chars. `config.yaml` bytes unchanged
  (1280 — the render inputs are the same fetched values; the policy changes only
  which keys are *kept*), `token` value unchanged. The one key present in both the
  fetched set and `template.data` is `token`, and the template re-emits exactly
  `{{ .token }}`, so Merge-vs-Replace cannot produce a value conflict here.
- **Rollouts: expect 1, plan for 2.** Trigger 1 is git-owned: the pod-template SC
  change makes the STS controller recreate pod -0 (new revision). Trigger 2 is
  operator-owned: the ESO spec change reconciles promptly, the Secret data changes
  (new key), and `reloader.stakater.com/auto: "true"` on the STS (values.yaml:61,
  render line 52-53) stamps a reloader rollout. They coalesce only if the reloader
  patch lands before the STS controller's first reconcile. A third rollout is
  possible if this app's selfHeal strips the reloader's pod-template annotation
  (argocd-cm is not in this repo — cannot be checked from the tree; the dev appset's
  ignoreDifferences note at services/dev/prod/templates/appset.yaml:22-24 covers
  system-upgrade Plans, not StatefulSets).
- **No ordering makes the combination worse in outcome than either change alone.**
  The two adverse-looking orderings both converge: (a) reloader-first → the first
  bounce runs on the OLD pod template, so the EACCES crash-loop gets one more cycle
  before C05's fix appears (noise, not regression); (b) reloader-last → the daemon is
  restarted again *after* it has already declared. (b) is safe by design: the daemon
  calls Declare on every start and the server matches by uuid, so a restart is a
  re-attach, not a re-registration (NOTES.txt:15-17, RESEARCH F1/F2) — that is the
  one place where the plan's prose happens to already cover the interaction.
