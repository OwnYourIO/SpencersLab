# Plan: Update WeKan to chart 12.64.0, deploy FerretDB as migration target

## Goal
Update the two home-cluster WeKan instances (`wekan` + `boards`) from chart
9.99.0 / `ghcr.io/wekan/wekan:v9.99` to chart 12.64.0 / `v12.64`, keeping the
existing MongoDB running, and deploy the new chart's FerretDB **idle** beside
it as the ready-made migration target. WeKan keeps consuming MongoDB via the
kept `secretEnv` MONGO_URL; `externalDatabase.url` mirrors it. When the data
is migrated (mongodump/mongorestore — both databases speak the MongoDB wire
protocol), flipping the URL completes the move. No adaptation is made for the
existing MongoDB itself: it is left exactly as it is.

Background: WeKan chart >= 10.86 no longer bundles the groundhog2k MongoDB
chart (it ships FerretDB instead). Renovate's `renovate/wekan-12.x` branch
(version-only bump) is insufficient on its own: merged as-is it would deploy
FerretDB defaults with no coherent database URL wiring. A prior version-only
attempt (v11.53.0, 2026-09-07) was reverted the same day.

Live state on home cluster (default namespace):
- Deployments `home-wekan` + `home-boards`, both `ghcr.io/wekan/wekan:v9.99`,
  served at `wekan.spencerslab.com` / `boards.spencerslab.com`. Both share
  one database.
- StatefulSet `home-mongodb` (`docker.io/mongo:7.0.34`, groundhog2k chart
  `mongodb-0.7.6`), Services `home-mongodb` + `home-mongodb-internal`, PVC
  `mongodb-volume-home-mongodb-0` (2Gi). Rendered today by BOTH wekan
  subcharts of the `home` umbrella (byte-identical duplicates — the live
  `home` Application carries `RepeatedResourceWarning` conditions for it).
- Both instances share it via `secretEnv` `MONGO_URL=mongodb://home-mongodb:27017`
  (manual fix for the old chart's broken computed URL, wekan/charts#54).
  **No `/dbname` in the URL** — the live data sits in the database Meteor
  picks when no path is given; the chart's `/wekan` example would point at
  an empty database.
- The `home` Application's live syncPolicy has **no `automated` block**
  (no prune, no selfHeal) — resources that drop out of the manifests are NOT
  automatically deleted. That is why the v11 merge/revert never touched the
  StatefulSet (age 271 days).

Chart research (wekan.github.io/charts, tgz extracted to /tmp/opencode):
- 9.99.0: bundles groundhog2k `mongodb-0.7.6`; computes MONGO_URL from
  Bitnami-style per-pod DNS (never resolved — #54); a `secretEnv`/`env`
  MONGO_URL suppresses the computed one (#6289 gate).
- 12.64.0: no mongodb dependency; `ferretdb:` templates in the chart itself
  (Service name `<release>-ferretdb` = `home-ferretdb` here, fixing #54);
  computed-URL precedence: `externalDatabase.url` > legacy `mongodb.url` >
  ferretdb (only when enabled and no external URL) — so with
  `externalDatabase.url` set, `ferretdb.enabled: true` deploys FerretDB but
  WeKan still dials the external URL; `directConnection=true` is appended
  when missing (harmless for single-node MongoDB, required for FerretDB —
  wekan/wekan#6582).
  - FerretDB templates use the parent chart's name helpers: the aliased
    `boards` instance derives `app: boards` labels/selectors while `wekan`
    derives `app: wekan`. Two instances rendering `home-ferretdb` would
    therefore emit the same-named StatefulSet with DIFFERENT immutable pod
    selectors — so FerretDB is enabled on exactly one instance.
  - FerretDB image: `ghcr.io/wekan/ferretdb:latest`, pullPolicy Always (the
    chart's deliberate choice — tracks wekan/FerretDB releases).
  - Old `mongodb.architecture`/`replicaSet`/`service.nameOverride` values
    keys are unknown to the new chart and ignored (left in place, inert).
- All other templates (service, data-pvc, secret, hpa, ingress,
  serviceaccount) are byte-identical between the versions.

## Migration path (later, when ready)
1. Dump + restore (both speak the MongoDB wire protocol, per the chart's own
   note): `mongodump` from `home-mongodb` → `mongorestore` into
   `home-ferretdb:27017` (via port-forward or exec — user-run).
2. Point both instances at FerretDB: set `externalDatabase.url` (and the
   `secretEnv` MONGO_URL, or remove the secretEnv so the chart computes it)
   to `mongodb://home-ferretdb:27017/<db>?directConnection=true` in both
   `wekan:` and `boards:`.
3. Verify boards load, then retire MongoDB (the cluster resources are no
   longer in git — delete the StatefulSet/Services manually when done).

## Risks / notes
- **Unrendered MongoDB:** after this change nothing in git renders
  `home-mongodb`; it keeps running because the `home` app has no automated
  prune/selfHeal. Do NOT sync this app with prune enabled (UI checkbox /
  `argocd app sync --prune`) and do not re-enable automation on `home`
  until the database situation is finalized — either would delete the
  running MongoDB. It is also no longer self-healed or visible in app
  diffs until migrated.
- **One-way data migration:** once WeKan 12.x runs its DB migrations,
  reverting the chart to 9.99 against the migrated data will not work.
  User accepted proceeding without a mongodump backup.
- FerretDB tracks `ghcr.io/wekan/ferretdb:latest` (chart default, pullPolicy
  Always) — expected for this chart; a restarted pod always gets the current
  release.
- Syncs on this app are manual; the first sync after merge rolls wekan +
  boards to v12.64 (WeKan runs DB migrations on boot — brief downtime per
  instance) and starts the idle `home-ferretdb`.
- Merge to `main` / PR creation is user-owned.
