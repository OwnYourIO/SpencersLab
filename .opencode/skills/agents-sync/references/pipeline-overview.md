# agent-* pipeline set for OpenCode v2

This repo: 5 pipeline agents = 5 roles × 1 variant (the plain set; the `-bmad` overlay was removed 2026-10-18), plus the standalone agents (`plan`, `code`, `ask`, `debug`, `review`) and the `0-pipeline` → `7b-docs-dev` SDLC stage agents, 2 `/pipeline*` commands, and the plan templates. All of them are generated by rulesync from `.rulesync/` sources.

Roles: `coord` (primary), `plan`, `dev`, `test`, `review`.
Variants: only the plain (base) set ships in this repo. The mechanism for overlays remains: overlay names lead with the overlay marker (`agent-dev-bmad`, not `agent-dev-<domain>-bmad`) so no plain name is a prefix of its overlay's agent names — exact matching is verified on v2.0.24 (see known-issues #1), and prefix-free names stay safe under any prefix-like behavior (wildcard rules, saved approvals, UI grouping). An overlay coordinator launches only its overlay's subagents. `/pipeline` + `/pipeline-resume` target the plain variant.

## Install / regenerate

`rulesync generate` produces all tool surfaces from `.rulesync/` (targets/features per `rulesync.jsonc`); edit the sources there — role prompts, permission blocks, commands, rules — rather than the generated files, then regenerate. Commit sources **and** generated surfaces together. `generate --delete` sweeps orphans (renamed/removed agents); run generate twice to confirm the second run is a no-op.

## Domain context

Agent files do **not** duplicate repo context — MCP servers, layout, git rules, plans, and verify commands live only in `AGENTS.md` (generated from `.rulesync/rules/`, auto-loaded into every session), and every agent gets a short pointer at it. The one accepted duplication is **skills**: every agent file carries its own `## Skills` section (plan-driven loading first, then any role-pinned MUST-load list, then dynamic picks). To change repo context, edit `.rulesync/rules/` and regenerate; to change which skills an agent loads, edit the agent source and regenerate.

## How the pipeline runs

1. `/pipeline <request>` → `agent-cord` resolves (or creates via `agent-plan`) the feature folder `.agents/plans/<yyyy>/<yyyy-mm>-<type>-<slug>/` (blanks from `.agents/plans/templates/`). If `plan_status != "approved"`, Phase 1: `agent-plan` plans into the folder and presents the plan to the user; cord continues only once `STATE.json` shows `approved` — never approves on the user's behalf. `/pipeline-resume` picks up the active ticket.
2. Per chunk, in wave order, one at a time: test (writes failing tests) → dev (implement) → test (runs the verification commands/full suite) → review → (dev fix → test → review, max 3 rounds).
3. Every subagent returns a `RESULT` block; the coordinator copies it into the ticket's `STATE.json` before doing anything else, and appends reported `friction:` items (plus its own) to the ticket's `friction.md` with the resolutions used — every agent reads that file at run start, so known workarounds are not rediscovered. The user triages entries later (`open` → `fixed`/`ignored`); entries are never deleted.
4. A chunk is `done` only with dev DONE + verification shown passing in commands_run + review APPROVED.

Chunking rules live in the plan prompts: S tasks grouped up to 3, M/L alone, every chunk mergeable on its own, `depends_on` → topological `wave` order. Plans record verification commands under "Commands" — this repo has no unit-test suite, so those are the validation commands from `AGENTS.md` (`helm lint`, `helm template`, trio/custom-values grep checks).

## Permissions summary (v2 ordered rules, last match wins)

| agent | edit | subagent | shell | MCP |
|---|---|---|---|---|
| cord | `.agents/plans/**/{STATE.json,DECISIONS.md,friction.md}` only (starts from deny-all) | plan/dev/test/review of same variant | none (deny `*`) | none (deny `*`) |
| plan | `.agents/plans/**` only | none | git reads allowed, else ask | `admin*` deny; `readonly*`/`global*` allow |
| dev | everything except `tests/`, plans; context files per-table (see `references/permissions.md`) | none | git reads + `helm lint/template` allowed, else ask | as plan |
| test | only `tests/**`, `*/tests/**` | none | as dev | as plan |
| review | `.agents/plans/**` only | none | git reads allowed, else ask | as plan |

Every role can ask the user questions with the `question` tool — questions only reach the user when explicitly asked, so all prompts say to use the tool when blocked on a decision only the user can make (pipeline subagents prefer `open_questions` in the RESULT block first). Skills are unrestricted everywhere.

MCP tools are permissioned as action `<server>_<tool>`; unsupported characters become `_`, so the prefix rules `readonly*` / `admin*` / `global*` match both `readonly-foo` and `readonly_foo` spellings.

## Things to verify on your build (known v2 issues as of 2026-10)

1. Frontmatter `permissions:` was silently ignored on 2.0.12–2.0.14 and, on later builds, whenever an unknown key is present. **Verified loaded and enforced on v2.0.24 (2026-10-14, live probes)**: a coordinator attempting cross-variant launches got `Permission denied: subagent` for the other variant's agents while its own four succeeded; its `subagent` tool schema listed exactly its 4 same-variant agents (the list is permission-filtered). Matching is whole-value (exact for patterns without `*`). These files use only `description`, `mode`, `color`, `permissions`. Check with:
   `opencode api get /api/agent/agent-dev` → rules must appear in top-level `permissions`, not `request.body.permissions` (against the server that owns the repo location — pass `x-opencode-directory: <repo>` when querying a shared/background service; `opencode api --standalone` may answer before agents load and return an empty list).
   If not applied, move each block to `agents.<id>.permissions` in the OpenCode config.
2. Do a live test: `opencode run --agent agent-review "write hello.txt"` must be denied.
3. Shell is `ask` for dev/test outside the allowlist (git read commands and `helm lint/template`). For unattended runs, add your exact commands as `allow` rules in the agent sources; keep the allowlist narrow.
4. Commands live in `.opencode/commands/` (generated): `/pipeline`, `/pipeline-resume`. They route to `agent-cord`, and the `!`…`` line discovers the tickets' STATE.json files and injects them at kickoff.
5. In OpenChamber, never start a message with `/skillname` (404 bug); mention skills mid-message or let the agent call the `skill` tool. (This is why the agent prompts say never to START a message with `/skill-name` even though skills are force-loaded via `/` in their lists.)
6. Reviewer, test and dev are `mode: subagent`; switch to `mode: all` in the source if you want to drive one directly from the agent picker.
